# 窗口标题噪声：先量，再定规则

Status: done（静置规则已实现，默认 1.5 秒，见 [ADR-0008](../../docs/adr/ADR-0008-window-title-must-hold-still.md)；待两天真实运行复核）

## 问题

`desktop.window.foreground` 现在只要标题读数变了就结束旧 Record、开新 Record。有些窗口的标题本身在动（滚动字幕、下载进度、终端里的命令与百分比），这类变化会切出大量短 Record，而它们不表达任何观测对象的变化。

## 已经排除的做法

**文本 diff 阈值**（编辑距离小于某个值就认为是同一个标题）不做。理由：

- 距离小 ≠ 语义相同。`Report.txt` 与 `Repost.txt` 距离 2，是两个文件；`Now Playing - A` 与 `ow Playing - AN` 距离大，却是同一首歌在滚动。判据和要判的东西不是一回事。
- 不可传递。A≈B、B≈C 但 A 与 C 差得很远，于是一条 Record 的 value 会随着比较链慢慢漂移，而 Range Record 的 value 是固定的，只延长区间。要么保留第一个读数（那这条 Record 的标题是错的），要么改 value（那 Record 的语义就变了）。
- 它把「读数是否变化」这件确定的事，换成一个需要调参、且每个应用都不一样的模糊判断。

## 方向

变化的**语义**用不了，就用变化的**时间形态**：真实的标题变更之后标题会停下来，噪声不会。所以规则应该是时间域的静置确认（新读数稳定住才承认），而不是文本相似度。参数由探针数据决定。

同时，macOS 侧有比文本更可靠的身份来源：`MacAccessibilityNative` 已经持有 focused window element，并在 `AXFocusedWindowChanged` 时替换它。「换了窗口」和「同一个窗口改了标题」不需要靠标题字符串去猜。

## 探针（已实现）

```bash
./scripts/heartbeat-dev probe window-title --duration-seconds 300
```

- 不连 Hub、不写数据库、不起容器；读数据库等于用被当前规则改写过的结果去评估规则。
- 宿主机不给 Accessibility 权限时可以退一步：`--from-database --since ... --until ...` 把数据库里的窗口 Record 导成同样的读数格式，走同一套分析。代价写在明面上——那是投影之后的 Record，答不了「原生通知有没有漏送」，换来的是覆盖好几天而不是一次会话。
- 同时记录原生通知与轮询两路读数，才能分清「标题真的在变」与「通知没送到」。
- 默认不保存标题原文：只有长度、指纹，以及相邻标题的共同前缀 / 共同后缀 / 是否互为旋转。滚动字幕在形态上就是等长旋转，进度条是超长共同前缀，这两类噪声不看原文也认得出。
- `window-title-churn.json` 里带候选静置参数（0.25/0.5/1/2/5 秒）的模拟结果：各留下多少条 Record、压掉多少次变化、代价是标题陈旧多久。
- 探针读标题也要 Accessibility 权限，权限属于启动它的终端程序。整段读不到标题时探针明确报无效并非零退出，不会把它说成「标题很稳定」。

## 定参数的判据

探针数据要能回答：

1. 噪声与真实变更在**保持时长**上是否分得开。若噪声集中在亚秒、真实变更普遍保持数秒以上，静置阈值就取两者之间；若两者重叠，说明单靠时间域不够，再谈按应用归一化。
2. 静置 1 秒左右能压掉的变化占比，以及此时标题陈旧的最长一段有多长。这是唯一要权衡的代价。
3. 有多少次变化是**只有轮询看到**的。如果占比不低，说明 AX 通知本身会合并或漏送，规则不能只挂在通知上。
4. 抖动是否集中在少数应用。若是，按应用配置的价值高于全局调参。

## 行业参照

- **ActivityWatch**：watcher 用 heartbeat + `pulsetime` 合并「同一个 data 且时间接近」的事件，靠的是值相同 + 时间窗口，不是文本相似度。<https://docs.activitywatch.net/en/latest/buckets-and-events.html>
- **ActivityWatch `aw-watcher-window`**：轮询式采集，`poll_time` 决定分辨率，`exclude_title` 决定是否采标题。噪声与隐私都交给采集频率与开关，而不是事后猜。<https://docs.activitywatch.net/en/latest/configuration.html>
- **ActivityWatch `aw_transform.simplify`**：`simplify_string` 用正则把标题里的计数、未读数、FPS 之类前缀剥掉。归一化放在变换层，是按应用写死的规则，不是通用阈值。<https://docs.activitywatch.net/en/latest/_modules/aw_transform/simplify.html>
- **ManicTime**：可以按标题里的词限制追踪，并用 tracker plugin 从标题里抽出文档名。成熟工具把标题当成需要解析和过滤的字段。<https://docs.manictime.com/win-client/tracking> / <https://docs.manictime.com/win-client/tracker-plugins>
- **Prometheus 告警**：`for` 要求条件连续成立一段时间才真正触发，`keep_firing_for` 让状态在消失后多保持一会儿，专门用来防抖。静置确认与滞回在监控领域是标准做法。<https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/>
- **BGP Route Flap Damping（RFC 2439）**：对反复抖动的来源累加惩罚值、随时间衰减，越过抑制阈值就冷却一段时间。适用于「少数来源疯狂抖动」的情况，代价是抖动期间的信息被丢弃。<https://datatracker.ietf.org/doc/html/rfc2439>

## 实测数据（2026-09-16，数据来源：本机数据库，非探针）

宿主机没给探针 Accessibility 权限，于是退一步用数据库里已经攒下的读数。数据是旧构建写的 `desktop.application.foreground`，标题还在 `value.window.title` 里，全量 3462 条 Record 折成 4547 条读数，覆盖约 46.6 小时。

先说这份数据答不了什么：它是投影之后的 Record，被旧的切分规则改写过，看不到被旧逻辑合并或丢掉的原始读数，也分不清一次变化是原生通知送来的还是轮询读到的（判据 3 只能等探针）。另外相邻 Record 里有 159 对 value 完全相同，那是旧构建的缺陷残留，本轮拆 Track 已经修掉。

能答的三条都答得很干脆：

- **抖动高度集中**。1221 次同应用标题变化里，Chrome 666 次、终端 441 次，两个应用占 91%。
- **两种噪声在时间形态上和真实变更分得开**。终端的 spinner 帧共 255 次，保持时长 p10 0.95 / p50 0.96 / p90 0.97 / 最长 1.05 秒，窄得像时钟；其余变化 p10 0.00 / p50 0.84 / p90 9.26 / 最长 387 秒。
- **亚秒 burst 是循环，不是信息**。相邻变化间隔都不到 1.05 秒的连续段共 257 段（Chrome 175、终端 58），吃掉 714 次变化（占 58%）、累计 434 秒；最长一段 37.56 秒里 42 个读数只有 3 个不同标题，50 段出现过值回访。Chrome 那些则多是「URL 先出来、页面标题随后覆盖」的中间态——压掉中间态，留下的正是那次导航的终值。

所以静置阈值取 **1.5 秒**：必须高于实测最长的 spinner 帧 1.05 秒才压得住，又远低于真实变更的 p50 0.84 秒之后那段长尾。全量模拟下它把 4370 个读数值收成 3620 条 Record，压掉 704 次变化，累计标题陈旧 464 秒，占总时长 0.28%。

模拟报告里「最长陈旧 20.48 秒」不必当成代价：陈旧统计把 spinner 的每一帧都算作不同的值，那 20 秒其实是 spinner 连烧期间我们一直显示首帧，而那些帧语义上就是同一个标题。

用户指定的 12:33–12:50 那 17 分钟单独看是不够的：只有 30 条读数、13 次同应用标题变化、3 次落在 1 秒内，够做一次 sanity check，不足以把阈值钉在 1.05 与 1.5 之间。

**实现时的一个硬约束**：Record 的起始时间要取这个标题**第一次出现**的时刻，不是确认通过的时刻。静置只延迟写入，不改区间，否则每条窗口 Record 都会平白短掉 1.5 秒。

## 已实现的规则

`DesktopRecordProjector.ObserveWindowTitle` + `SettlePendingTitle`：候选标题活过 `--window-title-dwell-ms`（默认 1500）才转正，转正后区间从它第一次出现算起；没活过就被前一个区间吸收。应用切换立即承认；标题不可读、Away Signal、能力失败时，站够时间的候选会补记。前台应用 Track 不受影响。

结算发生在候选之后的第一条读数上，所以最新标题最晚延迟一个采样间隔（默认 5 秒）才写出来。静置设 0 等于关掉。

## 两天后怎么复核

跑够两天之后，先看新数据的形态，再决定 1.5 秒是留、是收紧还是放宽。导出与分析都在 Dev CLI 里，不再需要单独的脚本：

```bash
./scripts/heartbeat-dev probe window-title --from-database \
  --since '2026-09-16 13:00' --until '2026-09-18 13:00' --dwell-seconds 1,1.5,2
```

导出只带标题长度与指纹，不带原文（要原文得显式加 `--include-sensitive-evidence`），读数与报告落在同一个证据目录：`window-title-readings.json` + `window-title-churn.json`。新旧两种数据形态都认：新构建的标题在 `desktop.window.foreground`，应用身份从同一时刻的应用 Record 反查；旧构建的标题还在 `desktop.application.foreground` 的 `value.window.title` 里。

**基线要用同一条命令重算，别直接引用上面那节的数字。** 上面那节是一次性脚本算的，它把没有标题的应用 Record 也算成读数；Dev CLI 只导出真的带标题的 Record，两者口径不同。用工具口径重算的实现前基线（2026-09-14 06:10Z 起到 2026-09-16 06:36Z，2682 个读数值）是：1248 次应用切换、1433 次同应用标题变化、其中 792 次落在 1 秒内、停留时长 p10 0.22 / p50 0.96 秒；1.5 秒静置会把它收成 1827 条窗口 Record，压掉 806 次变化，累计陈旧 525 秒，占总时长 0.64%。

判据（对照工具口径的实现前基线）：

- **1 秒内的标题变化应当基本消失**（基线 792 次）。还剩很多，说明有抖动周期长于 1.5 秒的应用，要么调高阈值，要么按应用单独处理。
- **窗口 Record 数应当明显低于同期应用切换数 + 真实标题变更数**，且相邻 Record 不再出现 value 完全相同的成对记录。
- **停留时长分布的下沿应当抬到 1.5 秒以上**；若 p10 仍在零点几秒（基线 0.22 秒），说明有一路变化绕过了静置（第一嫌疑是「中断恢复后第一个标题立即承认」这条）。
- 重放页面上，一段连续的前台时间里不应再看到标题抖动切出的碎块，也不应出现缝隙。

拿到 Accessibility 权限后仍需用真探针复核一次「原生通知有没有漏送」——数据库读数答不了这条。

## 备选规则（等数据）

1. **静置确认**：`AXTitleChanged` 只标记 dirty，下一次采样确认时才读；读数与上次相同才承认。最简单，也最贴现有的采样—确认链路。
2. **滞回**：短标题变化要更长的静置时间，长时间稳定过的标题变化更快承认。
3. **按应用抑制**：只对被探针指认为高频抖动的应用加冷却，其余照常。
4. **按应用归一化**：剥掉进度、计数一类前缀后再比较。表达力最强，维护成本也最高，只有前三条都不够时才考虑。
