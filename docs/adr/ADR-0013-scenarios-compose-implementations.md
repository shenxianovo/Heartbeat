# ADR-0013：场景组合实现，运行设施共用

## 状态：已接受

## 日期：2026-09-20

## 背景

真实采集到落库场景加入后，两个原生场景各自管理 Compose、Collector 进程、状态等待和清理。继续为每种依赖或故障组合复制脚本，会使验证设施随场景数量膨胀。

按 Collector、Hub、API 项目固定测试层级，也不能表达接管、注册和上传实现的独立测试与组合测试。项目本身由实现组合而成，目录组织不应决定测试范围。另一种选择是建立任意依赖图与场景 DSL，但当前没有足够使用需求支撑其复杂度。

## 决策

测试按行为和实际接口选择要运行的实现。单独验证一个实现时提供必要依赖；组合验证时直接连接生产实现，不以串行运行独立测试替代真实连接。

场景负责前置条件、动作和行为断言。Developer CLI 内共享的运行设施负责隔离环境、子进程生命周期、状态等待与清理，场景按需调用。`EvidenceSession` 继续统一保存运行结果和证据；数据库中的领域含义由场景解释，不进入环境管理设施。

保留现有场景入口。只有独立验收目的才增加入口，条件变化优先留在场景或测试中；不为所有排列组合建立命令。

## 后果

- 独立测试与跨进程场景可以采用不同范围，复用同一生产实现和必要运行设施。
- 环境清理、取消与日志保留行为只维护一套；具体业务断言仍保留在对应测试或场景。
- 组合仍由具体代码明确连接，暂不提供通用拓扑配置或自动组合枚举。
- 真实原生快照、受控替身和人工操作的证据范围仍分别说明。
