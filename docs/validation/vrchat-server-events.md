# VRChat 服务器事件人工 E2E

## 状态与范围

2026-09-27：实现采用服务器 Pipeline + REST 核对。真实 VRChat 事件待用户人工验收；构建、静态检查和现有模拟认证/交付回归不代表这里已通过。不部署、不修改真实账号状态或请求好友操作。

入口：运行包含本次代码的服务器 Hub 和 Web，通过 `/hubs` 登录自己的 VRChat 账号，然后从概览首页的 VRChat 分组选取账号进入 `/objects/{id}?view=summary`，核对对应对象和时间范围。同时观察 `/objects/{id}` 的 VRChat 世界/可见同场 Record 和 Hub 采集/交付状态。不得将 Cookie、WebSocket URL、原始消息或完整日志作为验收证据。

## 用真实游戏逐项对照

1. 启动采集时自己已在世界 A，好友已在同一实例：首次快照之后应有自己位置与可见同场；从首次观测开始，不追溯之前的停留。
2. 自己进入/离开世界、切换同一世界的另一个实例：事件到达后应更新对应 Record。两实例的同场必须分开。连续采集不应每分钟产生一次位置 GET。
3. 一位位置可见的好友加入自己的实例，然后离开/退出游戏：其可见同场开始/结束；其他实例里的好友不应形成同场记录。网页只自动刷新，不会对 VRChat API 发请求。
4. 好友隐藏位置或变为 traveling/网站 active：停止可见同场依据，不声称知道其真实离开时刻。未知位置不能被填为仍在原实例。
5. 自己先离开，好友还留在原实例：原同场结束；之后重新相遇新建观测段。
6. 断开服务器到 VRChat 的网络再恢复：状态显示连接/核对失败及等待；恢复新建区间，中间不桥接。不要为了验证 429 主动制造请求洪水；自然出现限流时检查等待和恢复。
7. 服务器进程重启、会话失效后重新登录：Target 不变；采集中断保留空白，不重复密码登录，不把重启前后的相同位置直接拼接。
8. 后端短时不可用再恢复：Hub 已接受的记录可补传，同 ID 更新不会增加访问段数。
9. 分别在 PCVR 和 Quest 独立模式重复进入/换实例/好友进出，比较 API 可见覆盖。此版本不读取任何设备日志；非好友与隐藏位置不完整属于已知范围。
10. `/objects/{id}?view=summary` 选择 7/30/90 天和自定义范围；核对气泡、列表、实例类型组成、访问明细、相遇和热力图使用相同时间范围。同一对象跨 Collector 汇集；核对时长按区间并集计算，原始来源可追溯。
