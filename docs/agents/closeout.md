# 收口检查

每次动手结束前过一遍。只检查这次真正碰到的路径，没碰到的不用假设，也不用造问题。

这几条不是通用最佳实践，是这个项目**已经犯过**的错。前四条在旧的 `main` 分支上反复出现，后来成了重写的直接理由；第一、二条在重写里已经复发过一次。

| 检查 | 判据 | 已发生过的样子 |
|---|---|---|
| 新加的兼容分支写了退出条件吗 | 只写「legacy」注释不算。要写清兼容的是什么、还服务谁、什么时候删、谁验 | `tools/Heartbeat.Dev/DatabaseReadings.cs` 兼容过「拆 Track 之前」的旧数据形态——而净室重写根本没有旧数据 |
| 同一个契约有没有第二处权威 | 有第二处就得有对账手段（共享一处、或一条会红的测试） | `TimeMode`/`EndMode` 的枚举与字符串映射曾散在五处；协议 type 字符串曾在 Collector、Dev SQL、前端 registry、测试里各写一份 |
| 文档里有没有会腐坏的快照 | 测试条数、行数、耗时这类数字不写死。要看当下就让工具生成。带日期、写明命令、明说「这是一次记录」的快照不算腐坏 | 四份文档各写了一个测试数量，互相矛盾，而且都不对 |
| 「代码完成」有没有被当成「需求完成」 | 分清实现完成、自动验证完成、人工验收完成；宣称已实测就要有证据路径 | `docs/development.md` 曾写「已实测」，而 98 次验证产物里找不到对应场景 |
| 通用层有没有认识具名的可选组件 | 后端与 Hub 里不该出现某个具体 Collector 的名字 | 旧仓的通用校验层硬编码了具体协议 id，删一个可选组件要改宿主 |
| ADR 是不是该有一份 | 跨组件的责任归属、协议语义、数据权威位置——这三类必须有 ADR | 「Hub 拥有交付」这个决定实现了五天没有 ADR，靠一份说明文档撑着（后来补成 `ADR-0009`） |

## 发现了怎么办

- 影响这次任务正确性的：当场说清证据和影响，在范围内修掉，或者明确卡在哪。
- 紧邻且低风险的陈旧文档：跟着这次改动一起修。
- 具体但超范围的：在收尾答复里给证据和下一步，需要跟踪就按 `issue-tracker.md` 建 issue，建之前先搜 `.scratch/` 别重复。
