---
title: "EntitySchema"
description: "一种业务类型，以及它每一版的字段、约束与含义"
---

EntitySchema 定义一种业务类型，例如“本机应用”或“前台时段”。它是一个实体，EntityId 叫 SchemaId；它的每个版本是这种类型的一版字段、约束和含义，叫 Schema 版本。

每个业务版本都引用它保存时所用的 Schema 版本。类型后来增减了字段，旧数据仍按当时的 Schema 版本解释，不需要迁移。

本页的规则约束业务类型。Core 类型的结构由 Core 自己定义。

<ModelRelations node="EntitySchema" />

- **类别**：Core 类型，`category` 为 `entity_schema`
- **被引用**：业务版本的 `schemaVersionId`
- **决策**：[ADR · 实体模型](../../adr/entity-model.mdx)

## 字段 [#fields]

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `displayName` | 非空字符串 | 类型名称，见 [SCHEMA-4](#schema-4) |
| `description` | 非空字符串 | 业务说明，见 [SCHEMA-4](#schema-4) |
| `resourceName` | 字符串 | 类型的资源名，见 [SCHEMA-5](#schema-5) |
| `fields` | 字段名到字段定义的映射 | 业务实体的字段，引用也是字段 |

## 字段定义 [#field-definitions]

| 配置 | 适用的字段 | 含义 |
| --- | --- | --- |
| `type` | 所有字段 | 值的类型 |
| `description` | 所有字段 | 非空字符串，说明字段或数组元素的业务含义 |
| `required` | 所有字段，数组元素除外 | 字段是否必须出现 |
| `nullable` | 所有字段 | 字段出现时，值能否为 `null` |
| `fields` | `object` | 对象的成员，结构与顶层 `fields` 相同 |
| `items` | `array` | 数组元素的字段定义 |

| `type` | 值 |
| --- | --- |
| `string` | 字符串 |
| `boolean` | 布尔值 |
| `integer` | 整数 |
| `number` | 数值，可以包含小数 |
| `reference` | 目标版本的 `VersionId` |
| `object` | JSON 对象 |
| `array` | JSON 数组 |

## 示例 [#example]

下面的业务类型有三个字段：`title` 必须出现，可以为 `null`；`relatedVersionId` 是引用；`identifiers` 是对象数组，每个元素的 `sourceVersionId` 也是引用。

```json
{
	"displayName": "示例条目",
	"description": "一个带标题、实体引用和平台标识线索的示例条目。",
	"resourceName": "example-items",
	"fields": {
		"title": {
			"type": "string",
			"description": "条目的标题；未取得标题时为 null。",
			"required": true,
			"nullable": true
		},
		"relatedVersionId": {
			"type": "reference",
			"description": "与这个条目相关的版本，目标可以是任何类型。",
			"required": true,
			"nullable": false
		},
		"identifiers": {
			"type": "array",
			"description": "来源提供的平台标识线索；没有线索时为空数组。",
			"required": true,
			"nullable": false,
			"items": {
				"type": "object",
				"description": "一项平台标识线索，以及提供它的来源版本。",
				"nullable": false,
				"fields": {
					"scheme": {
						"type": "string",
						"description": "标识线索的种类，决定 value 的解释方式。",
						"required": true,
						"nullable": false
					},
					"value": {
						"type": "string",
						"description": "来源提供的标识原值，保留原文。",
						"required": true,
						"nullable": false
					},
					"sourceVersionId": {
						"type": "reference",
						"description": "提供这项线索的版本；来源没有保存为版本时省略。",
						"required": false,
						"nullable": false
					}
				}
			}
		}
	}
}
```

## 类型与 Schema 版本 [#types]

### SCHEMA-1 一个 EntitySchema 一种类型 [#schema-1]

定义

一个 EntitySchema 定义一种业务类型，它的每个版本是这种类型的一个 Schema 版本。同一类型的业务实体共用一个 EntitySchema，各有自己的 `EntityId`。

### SCHEMA-2 按 Schema 版本解释 [#schema-2]

执行方：后端、读取方

业务版本按它引用的 Schema 版本校验和解释：有哪些字段、哪些位置是引用、每个字段是什么含义，都由这个 Schema 版本决定。

### SCHEMA-3 只按声明校验 [#schema-3]

执行方：后端

后端只按已声明的 EntitySchema 校验业务实体。业务版本引用的 Schema 版本必须已保存。

### SCHEMA-4 名称与说明 [#schema-4]

执行方：写入方、后端

`displayName` 和 `description` 必须是非空字符串，后端检查这一点。`description` 还必须说明这种类型记下的业务事实、粒度和事实时间的取值，由写入方负责，人和 Agent 都靠它理解数据。

## 资源名与字段名 [#names]

### SCHEMA-5 resourceName 唯一 [#schema-5]

执行方：后端

`resourceName` 属于业务类型：同一个 EntitySchema 的各版本使用相同的 `resourceName`，不同的业务类型不得使用相同的 `resourceName`。EntitySchema 删除后，它的 `resourceName` 可以由新的业务类型使用。它用于发现和访问一种类型，用法见 [API](../../api/index.mdx) 和 [Storage](../../storage/index.mdx)。

### SCHEMA-6 resourceName 格式 [#schema-6]

执行方：后端

`resourceName` 只使用小写字母、数字和连字符，并以字母开头，例如 `local-applications`。

### SCHEMA-7 不用 id 字段 [#schema-7]

执行方：后端

顶层字段不得命名为 `id`。实体和版本的身份由[版本的成员](./version.mdx#members)提供。

### SCHEMA-8 引用字段的名字 [#schema-8]

执行方：写入方

`reference` 字段的名字以 `VersionId` 结尾，元素是 `reference` 的数组以 `VersionIds` 结尾，对象成员也一样。名字的前半部分写目标在这里的角色，例如前台应用时段引用本机应用的 `localApplicationVersionId`，与 Observation 的 `observerVersionId` 写法相同。

## 字段约束 [#constraints]

### SCHEMA-9 reference [#schema-9]

执行方：后端

`reference` 的非空值必须是 VersionId。顶层字段、对象成员和数组元素都可以是 `reference`。

### SCHEMA-10 字段定义必写项 [#schema-10]

执行方：写入方、后端

每个字段定义必须写明 `type`、`description`、`required` 和 `nullable`，这些配置没有默认值。数组元素写 `type`、`description` 和 `nullable`，不写 `required`。对象的每个成员也遵守这条规则。

`description` 必须是非空且不全为空白的字符串，由后端检查；它描述字段或数组元素本身，业务值允许为 `null` 不影响说明的必填要求。

写入方用 `description` 说明字段或数组元素的业务含义，以及适用的单位、取值解释、来源、引用目标与角色、省略和 `null` 的含义。读者应能结合所属类型的说明理解数据，不依赖原来的采集程序。后端不判断这些业务说明是否充分，也不从说明文字生成校验条件。

### SCHEMA-11 required 与 nullable [#schema-11]

执行方：后端

`required` 和 `nullable` 分别判断：`required` 决定字段能否省略，`nullable` 决定字段出现时能否为 `null`。

| `required` | `nullable` | 省略字段 | 值为 `null` | 类型匹配的非空值 |
| --- | --- | --- | --- | --- |
| `true` | `false` | 不允许 | 不允许 | 允许 |
| `true` | `true` | 不允许 | 允许 | 允许 |
| `false` | `false` | 允许 | 不允许 | 允许 |
| `false` | `true` | 允许 | 允许 | 允许 |

### SCHEMA-12 只收已声明字段 [#schema-12]

执行方：后端

业务实体只接受已声明的字段，对象成员也一样。字段定义只接受[字段定义](#field-definitions)中列出的配置。

### SCHEMA-13 省略与 null [#schema-13]

执行方：后端

“省略”和“值为 `null`”是两种状态：省略的字段读回时不出现，值为 `null` 的字段读回时是 `null`。

### SCHEMA-14 对象与数组 [#schema-14]

执行方：后端

对象用 `fields` 声明成员，数组用 `items` 声明元素；只有 `object` 有 `fields`，只有 `array` 有 `items`。数组的约束分层生效：

| 配置 | 约束什么 |
| --- | --- |
| 数组字段的 `required` | 数组字段能否省略 |
| 数组字段的 `nullable` | 数组本身能否为 `null` |
| `items.nullable` | 数组元素能否为 `null` |
| `items.fields` 中成员的配置 | 每个对象元素的成员 |

## 类型的演进 [#changes]

### SCHEMA-15 结构变了，出新版本 [#schema-15]

执行方：写入方

结构或约束改变时，形成同一个 EntitySchema 的新版本。增删字段、调整约束、改写 `displayName` 或 `description` 的措辞，都属于这种情况；SchemaId 和 `resourceName` 保持不变。

### SCHEMA-16 含义变了，建新类型 [#schema-16]

执行方：写入方

业务含义改变时，必须新建一个 EntitySchema，使用新的 SchemaId 和 `resourceName`。字段改名或改写 `description` 不得改变旧数据的含义。

### SCHEMA-17 旧数据按旧版本读 [#schema-17]

执行方：后端

新的 Schema 版本只作用于引用它的业务版本。已保存的业务版本继续按它引用的 Schema 版本解释。
