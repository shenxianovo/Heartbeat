Core 定义 Orisumi 中所有数据共用的结构：数据怎样标识、怎样更新、怎样互相引用，以及一份观测由哪几部分组成。各类型的细节在类型页，跨类型的规则在规则页。

## 实体与版本 [#entities]

Orisumi 中的每一项数据都是一个[实体](./model/entity.mdx)，例如用户本人、VS Code 这个本机应用、14:00 开始的那段前台时段。实体的内容保存在[版本](./model/version.mdx)中：每次修改形成一个新版本，旧版本原样保留。

引用指向某个确定的版本。所以一份观测引用的内容，事后不会改变。

业务字段中的文件，例如应用的图标，是[二进制内容](./model/binary.mdx)：版本中保存它的摘要，字节单独保存。

| 概念 | 回答的问题 | 身份 |
| --- | --- | --- |
| 实体 | 是哪一项数据 | `EntityId` |
| 版本 | 是这项数据的哪一次内容 | `VersionId` |
| 业务类型 | 是哪一种业务数据 | SchemaId，也就是 EntitySchema 的 `EntityId` |

## Core 类型 [#core-types]

Core 自己定义三种类型，其余实体都是业务实体，由 EntitySchema 定义类型。

| 类型 | 内容 |
| --- | --- |
| [Observation](./model/observation.mdx) | 一份陈述：谁负责、说了什么、依据什么、事实在什么时间成立。只有它保存事实时间 |
| [InputSet](./model/input-set.mdx) | 一次处理实际用到的版本 |
| [EntitySchema](./model/schema.mdx) | 一种业务类型；它的每个版本是一版字段、约束和含义 |

[Observer](./model/observer.mdx) 和观测内容都由业务实体承担，承担哪个角色取决于 Observation 怎样引用它。程序实例和人都可以是 Observer。

## 模型关系 [#relations]

<ModelRelations />

Observation 引用 Observer、观测内容和 InputSet。InputSet 引用它的输入，输入可以是任何版本。业务版本引用自己所用的 Schema 版本。每个版本还引用同一实体的前一版本。

## 谁决定什么 [#responsibility]

新增一个来源时，要写的是业务规则和读取来源的代码；数据怎样组织成实体和版本、程序怎样运行，都由公共的部分负责。四种职责如下，例子取自前台状态 Observer：

| 职责 | 决定或承担什么 | 例子 |
| --- | --- | --- |
| 业务规则 | EntitySchema、实体身份、粒度、何时形成新版本、事实时间的取值、结束条件、原始材料的保留、陈述冲突时以谁为准。一种业务类型的规则由使用它的 Observer 共用 | 同一设备上包标识和路径都相同的是同一个本机应用 |
| Observer 的业务代码 | 读取来源，解释材料，判断对象与观测的连续性，决定内容、事实时间和实际用到的输入 | 读到 VS Code 在前台，判断这一段到 16:00 结束 |
| 数据能力 | 认出和登记对象，组织实体、版本、固定引用、Observation、InputSet 和二进制内容；查询、删除；按 Core 的规则校验并保存，赋值保存时间 | 把 16:00 这一段的内容和 Observation 一起保存 |
| 托管方 | 管理程序实例和配置，提供运行上下文，启动、停止程序并报告运行状态；断网时留住写入，联网后转发 | 启动前台状态 Observer，交给它实例身份和设置 |

后端的 API 提供数据能力，它只检查结构，事实层面的判断由业务规则和业务代码负责。业务代码只发送：说出一个实体的完整内容、识别依据和事实时间，见 [API · Writing](../api/writing.mdx)。任何语言都能发 HTTP 请求，[SDK](../api/sdk.mdx) 只是方便。托管方的当前实现是 Runtime。职责不对应进程：一个程序可以直接运行，不经过托管方。这样分工的理由见 [ADR · 单向写入与托管的分工](../adr/data-capability.mdx)。
