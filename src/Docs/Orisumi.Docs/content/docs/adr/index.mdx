ADR（Architecture Decision Record）记录一项架构决定和它的理由。规则写在 Core、API、Storage、Observers、Hosting 和 Clients 中，ADR 解释为什么。

## 何时写 ADR [#when]

三类决定写成 ADR：

- 责任归哪个组件。
- 协议的语义。
- 某类数据的权威位置。

较小的决定写在对应的类型页、规则页或契约中。只涉及单个 Observer 的决定写在该 Observer 的文档中，模块的运行说明写在模块 README 中。

## 结构 [#structure]

| 部分 | 内容 |
| --- | --- |
| 背景 | 需要作出决定的问题 |
| 决定 | 确定的做法，每条一句 |
| 理由 | 为什么这样做，放弃了哪些方案 |
| 代价 | 接受了哪些成本或限制 |
| 规则位置 | 承载具体规则的文档 |

条件、例外和细节写在规则中，ADR 链接过去。ADR 可以属于任何一层，归层方式见 [设计层与变更流程](./documentation-authority.mdx#layers)。流程类决定在 Core 中没有页面，这类 ADR 在“决定”之后加一节“规则”，例如[设计层与变更流程](./documentation-authority.mdx)。文字见 [Core · Writing](../core/writing.mdx)。

## 命名 [#naming]

ADR 用英文 slug 命名，例如 `entity-model.mdx`，没有编号。引用时写标题并链接，例如 [ADR · 实体模型](./entity-model.mdx)；代码注释写 `ADR entity-model`。按侧边栏顺序读，每篇的背景只用到排在它前面的决定。

- 重写期间，ADR 直接改成当前的决定。合并、拆分或改名时，同时更新所有引用。
- 重写完成后，slug 固定。决定被取代时，新写一篇 ADR，并在旧 ADR 开头链接新的。
