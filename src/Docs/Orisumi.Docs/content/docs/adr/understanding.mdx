## 背景 [#context]

Orisumi 要回答一个人经历了什么，而记录里的对象大多来自软件：QQ 号、设备、本机应用。“这个 QQ 号是我”“这两个设备是同一台机器”“这个房间是书房”这些关系，来源不会给出。传统软件只能靠采集或人工录入，一个是拿不到，一个没有人愿意做。

语言模型能读这些证据并作出判断，一次判断的费用很低。应用识别已经这样工作了：模型把线索归到产品，判断直接生效。

模型会判错，也会变强。判断的结果不能像采集到的数据那样当成定论，换了更强的模型要能重新判断，用户发现错误时要能纠正，而且不用逐条审核。

## 决定 [#decision]

- 数据分三层：来源给出的证据，模型自带的世界知识，模型形成、用户纠正的私有理解。
- Observation 增加形成方式，说明这份陈述怎么来的：`direct`、`stated`、`computed`、`extracted` 或 `inferred`。
- 采集时只记下来源给出的内容，提到来源中的对象。来源没有给出的关系留给理解。
- 每次判断形成新的 Observation，新旧判断都保留。
- 模型的判断直接生效，用户只在发现错误时否定。
- 确认、否定和取代是同一种公共类型 Review。取代由形成新判断的 Observer 声明。
- 当前理解是没有被否定也没有被取代的陈述。用户确认过的陈述，模型的取代不生效。
- 撤销判断用否定。删除只用于用户要抹掉的数据。
- 依据里有被否定的陈述时，读取方标记它，并能找到被否定的那一条。这一阶段不自动重做。
- 模型发现的关系用公共类型 Relation 表达，不用预先定义类型。软件要用来计算的关系才单独定义。
- 事物的名字用公共类型 Name，来源、模型和用户都可以写。
- 世界知识和叙事在读取时由模型现取，不保存。
- 正在和用户工作的 Agent 也是 Observer，可以当场写下判断。
- 不同的模型和方法是不同的程序实例，便宜的模型做筛选，强模型做判断。

## 理由 [#rationale]

采集时判断关系是最难的做法：程序要在读到一条消息时就知道发送者是谁。分开之后，QQ 的采集只记 QQ 号，关系可以以后再判断，判断错了也不影响证据。证据过去就没有了，理解可以重做，所以两者的保存要求不同。

形成方式放在 Observation 上，是因为它属于一次陈述，不属于内容：同一句“123 是本人”，模型说是推断，用户说是亲口陈述。它不叫“事实”，因为直接读到的数据也只是来源的说法：VS Code 留在前台时，用户可能在开会。

判断互不覆盖，新模型才能和旧模型并存，用户才能看到认识怎样变化。

“当前认识”曾考虑写成单独的实体，由一个确定性程序按优先级维护。这走不通：`predicate` 是自由文字，程序分不清两条判断是否在回答同一个问题，只有形成判断的模型知道。所以取代由模型声明，当前理解只是一个查询，不需要额外的实体和程序。

用户平时不审核，因为逐条审核的负担大到没有人会做。用户只在发现错误时否定，否定作为输入留给下一轮模型，模型也就记住了这条。撤销不用删除，因为删除会连判断的依据一起移除，下一轮模型读不到否定，还会再犯。

世界知识不保存，因为模型每次现取总是最新的，入库之后反而会过期。叙事现写也是同样的道理，模型越强写得越好。

放弃的方案：

- **用户确认后才入库。** 用户要逐条处理，判断的数量上去之后没有人会做。
- **确定性程序写当前认识。** 见上文。
- **模型自报置信度进入 Core。** 不同模型的概率不可比。需要时放在业务字段中。
- **只分事实和推断两类。** 确定计算和模型提取都不是推断，也不是来源直接给出的。
- **保存每天的叙事。** 模型变强后要重写，保存下来的文字很快过时。
- **否定之后自动重做下游判断。** 这一阶段先标记，等有需要再做。

## 代价 [#costs]

- 模型的调用有费用。便宜的模型做筛选，再加上每月的免费额度，目前可以接受。
- 数据要发给云端模型。这是用户自己的数据，用户接受这一点。
- `predicate` 是自由文字，同一种关系可能有多种写法，页面上可能看到近义的多条。
- 模型可能写出用户否定过的结论，这时用户再否定一次。
- 只否定一段时，当前理解保留整条陈述，读取方要自己看时间。
- 重新理解过去的数据时，判断的数量会成倍增长。
- 推断再喂给推断时，错误会传递。读取方沿 InputSet 能查到，但要主动去查。
