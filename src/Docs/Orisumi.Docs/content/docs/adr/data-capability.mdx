## 背景 [#context]

新来源由 Agent 编写，用户验收，别人也能用自己的 Agent 写，语言不限。Observer 要运行在 Mac、Windows、服务器和手机上。笔记本断网时要继续采集，联网后补上。来源有四类：一次性的导出文件、持续跟读的文件、错过就没有的实时信号、从已有数据作出的推断。

所以衡量写入方式的标准是：Agent 能不能写对，写错了能不能发现。

此前的结构不符合这些要求。业务代码要用 `draft`、`reference`、`bindings` 这些操作自己编排版本，来源标识到 EntityId 的对应也由各 Observer 维护：前台状态 Observer 用一个登记文件，助手会话 Observer 用一个 SQLite 文件。曾有一次，同一台 Mac 上的客户端 Runtime 和服务器 Runtime 都运行了前台状态 Observer，两个登记文件分别生成了 EntityId，9 个应用各重复了一份。

## 决定 [#decision]

- 职责分为四种：业务规则、Observer 的业务代码、数据能力和托管方，见 [Core · 谁决定什么](../core/index.mdx#responsibility)。职责不对应进程或服务。
- 业务代码只发送，采集时不读后端。一次写入说出一份 Observation 的完整内容、形成方式，可选的识别依据、事实时间和实际输入，见 [API · Writing](../api/writing.mdx)。
- 写入接口是全部契约，能发 HTTP 就能写 Observer。[SDK](../api/sdk.mdx) 是可选的便利。
- 后端负责认出对象和形成版本。同一依据的内容相同时什么都不做，内容不同时形成新版本。
- 提到事物写识别依据，事物不存在时由后端创建。引用陈述写识别依据或 EntityId，后端解析成此刻的确定版本，解析不到时可空字段为 `null`，其余情况拒绝这次写入。
- 时间或内容变化时，形成这份 Observation 的新版本。
- 业务上的变化靠粒度表达，见 [IDENTITY-5](../core/rules/identity.mdx#identity-5)：日志型来源的变化是新的实体，快照型来源的变化是新版本，不增加部分写入、合并或条件写入。
- 进行中的事实是快照型的实体。结束后写入一次是特例，以后可以在开始、确认和结束时各写入一次，模型和接口不变。
- 业务类型的声明和程序实例的描述也通过写入接口交出，绑定在这个 Observer 上，所以离线启动不用等后端，新旧程序可以同时使用各自的 Schema 版本。之后的写入由后端填上当时描述的版本。
- 受托管的程序把写入发给 Runtime 的本地转发，由它按顺序交给后端。设备和后端是同一份接口，地址不同。
- 需要写入结果的程序直接连后端，同一个接口同步返回结果，例如[应用识别 Observer](../observers/application-identity/index.mdx)。
- 每个 Observer 一条有序的写入流。本地转发给每个请求编序号，后端保存这条流最后处理的序号，重发不会重复。
- 后端拒绝一次写入时，同一流中的其他写入继续，被拒绝的写入留在本地转发中，托管方通知用户，修好后可以重发。
- 识别依据保存在后端，一份依据最多对应一个实体，随实体删除。
- 托管方读取设备的稳定标识，放进运行上下文。用到设备的程序写入设备，用这个标识认出它，用户不用配置。
- 托管方管理程序实例和配置，启动和停止程序，报告状态。程序是一个普通进程：上下文从环境变量读取，标准输入关闭时结束，诊断写入标准错误。
- 所有读取方用同一组读取接口，设备端客户端只从托管方取得连接信息。

## 理由 [#rationale]

单向写入从断网的要求推出。Observer 如果要等后端返回 EntityId、VersionId 或查询结果才能继续，断网时就停了。把这些都交给后端，Observer 只说自己读到了什么，写入请求就可以存下来，晚一点再发。

这也让业务代码变短。Agent 写一个新来源时，不用学版本链、结果引用和操作顺序，只判断几件事：内容是什么、提到了哪些事物、用什么认出它、事实在什么时间成立。上一版的入口要在写入前查询依据、在一次变化中跟踪每个对象的最新结果、重读时比较内容。助手会话 Observer 按那个入口写出的编排代码和替换前一样长，还多了一处缺口：Claude Code 的工具结果只有 `tool_use_id`，跨段时找不到调用。

单向写入能成立，靠的是[一份 Observation 只有一个作者](../core/model/observation.mdx#observation-10)：后到的内容就是作者新的说法，后端可以按到达顺序接在当前版本之后，不需要写明依据的版本。用户的否定和模型的新判断都是新的 Observation，所以不会和 Observer 写入同一个实体，见 [ADR · 模型形成的理解](./understanding.mdx)。

部分内容和重读靠粒度解决。Codex 的日志不带标题，标题在只追加的索引文件里；Claude Code 的标题就在日志里。如果标题是会话的字段，日志会把标题写回空值，从头重读时旧标题又会形成一次版本。会话是事物，标题是单独的 Name，这两个问题都没有了，也不用增加“只有不存在才写”或按字段合并。一台 Mac 上的日志支持这一点：Claude Code 的会话中标题和 `entrypoint` 都没有变过，Codex 的 538 个会话中 51 个改过标题，每次改名在索引文件中有一行。规则简单到可以交给 Agent：来源有没有保留历史。应用识别也一样：判断是单独的 Observation，所以产品不用读出再写回，见 [ADR · 应用识别](./application-identity.mdx)。

把读取和写入分开也让 Observer 更简单。[Runtime](../hosting/runtime.mdx) 回到了写入路径上，但只存下请求、按顺序转发，不解释内容，也不形成版本，所以它和被替换的本地版本库是两件事。任何语言都不需要实现重试和断网，程序只换地址。手机没有 Runtime，由应用内嵌同样的转发逻辑。直接运行的脚本不需要它。

接口同时满足两种程序。采集程序写给本地转发，只得到“已收下”。需要结果的程序直接调用后端，同步得到每次写入的结果。两者是同一个接口，所以应用识别 Observer 这样要读到自己写入的程序不需要另一套操作。

序号让重发简单。写入流是有序的，后端只记一个数字，就能丢弃已经处理的请求，不用为没有识别依据的温度读数造身份，也不用保存每个请求的标识。

被拒绝的写入在 Schema 和程序一起发布时很少出现：字段写错这类问题在本地验收时就暴露了。上线后剩下的是来源超出 Schema 的承诺、存储的限制和目标被删除。助手日志中可能含 `\u0000`，这种字符串不能保存。这类问题不应该挡住后面的数据，错过的实时信号也不能再读一次，所以写入继续，被拒绝的留着。本地转发本来就存着这些字节，保留只是不删除。

识别依据保存在后端，是因为它们的共同连接点只有后端。依据保存在单独的表中，调用方给出四个值，后端不解释它们，所以不需要在 EntitySchema 中声明规则。里面有路径、会话标识这样的来源信息，所以随实体删除。之后读到同一个来源对象时，它是一个新实体：被删除的历史保持删除，采集继续。

设备是事物：程序不能等后端返回设备的 EntityId，所以设备也靠识别依据。硬件 UUID 在同一台 Mac 上对所有托管方都相同，也不随重装客户端变化，所以两个 Runtime 得到同一个设备，这正是当初 9 个应用重复时缺少的共同依据。本机应用的识别范围用这个标识本身，业务代码不需要知道设备的 EntityId。

管道协议对任何语言都是负担，程序要在读写 HTTP 之外再实现一套逐行的 JSON 消息。环境变量和标准输入的关闭在所有语言和平台上都有，也让 Observer 成为一个普通进程，本地可以直接运行。

放弃的方案：

- **业务代码用 `record`、`change` 组合操作，写明依据的版本。** 断网时写不了，一个来源能重读时业务代码要自己跟踪已有的状态。
- **每种语言的 SDK 各实现重试和断网。** 同样的逻辑要在每种语言中实现，也违背“能发 HTTP 就能写”。
- **Observer 把写入追加到本地文件，由 Runtime 读取。** 少一个端口，但直接运行的脚本和受托管的程序接口不同，也不能同步返回结果。
- **只保存最新一份的预览通道。** 进行中的事实不进版本链，但多一个概念，也和断网时的写入是两条路径。
- **EntitySchema 声明哪些字段构成身份。** 要新增 Core 成员，还要规定数组和引用字段怎样比较，接近一门规则语言。
- **公共的业务类型目录。** 目前只有一个作者。SchemaId 是 UUIDv7，Schema 自带说明，以后可以再加。
- **隔离别人写的程序。** 安装就代表信任，和普通软件一样。

## 代价 [#costs]

- 业务代码拿不到写入结果，也读不到还在本地转发中的数据。断网时客户端看不到这段时间的数据。
- 程序写错时，错误出现在被拒绝的列表里，不在调用处。所以 Agent 的验收要看这个列表。
- 用户删除一个实体后，本地转发中尚未送达的写入，或者日志被整份重读，会让这个对象作为新实体再出现。
- 进行中的事实在写入之前丢失：程序意外退出时，这一段没有了。
- 进行中的事实每写入一次多一个 Observation 版本。一分钟一次时，两小时是 120 个版本。
- 识别依据不能从版本重建。表丢失后，同一个来源对象会形成新的事物。
- Claude Code 的标题回到旧值时，依据相同，第二次变化记不下来。
- 重发被拒绝的写入时，它排在最后。同一份 Observation 的旧内容可能盖掉新内容。
- 受托管的程序用托管方的凭证写入，同一个托管方上的程序可以用彼此的身份。它们本来就以同一个系统用户运行。
