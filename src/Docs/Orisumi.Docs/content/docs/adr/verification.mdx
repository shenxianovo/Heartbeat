## 背景 [#context]

人和 Agent 都会修改代码。说“测试通过”时，要能查到实际运行了什么、结果是什么，测试说明和测试结果也要能对应。

## 决定 [#decision]

- Orisumi.Dev 组织构建、测试、质量扫描和证据保存。
- 构建失败、测试失败或扫描未完成时，验证失败。质量扫描的发现只供评审，不使验证失败。
- 每次运行都在独立目录中保存证据，包括失败和取消的运行。
- 文档站的 Case 定义验证目的，测试通过稳定的 `caseId` 关联 Case。
- Case 中的预期注明规则依据和对应检查；执行结果只支持实际检查的条件与范围。接受结论前，核对源码状态、规则、环境和参数，并列出未验证项。
- 原生测试报告是测试结果的权威来源，文档站只读取报告。

## 理由 [#rationale]

保存每次运行的清单和日志，“验证过什么”就可以查证。质量扫描常有误报，所以只供评审。

用 `caseId` 关联，重构测试时 Case 页面的关联不会断开。没有报告或没有匹配结果时，页面不显示通过。

同一 Case 可以关联多个测试，一个测试也可以检查多项预期。仅按 `caseId` 找到通过的结果，不能判断每项预期是否有对应的断言，所以 Case 另外说明检查范围。测试使用模拟读数、内存存储或静态数据时，结论也受这些条件限制。

旧报告描述旧运行。实现、规则或环境改变后，原来的检查可能不再支持当前结论；重新检查可以补充依据。变化本身不说明新的实现已经违反要求。

放弃的方案：

- **按测试方法名关联 Case。** 重命名方法就会断开关联。
- **文档站运行测试或把结果写入实体数据库。** 文档站会依赖测试环境，测试结果也会混进用户数据。

## 代价 [#costs]

- 需要在 Case 页面显示结果的测试要标注 `caseId`；直接验证 Core 的模型测试按规则编号关联。
- 文档站显示的是最新的报告，不是实时结果。
- 测试的输入、断言或名称改变时，要同步核对 Case 中的覆盖说明。
- 证据目录会持续增长，需要按保留规则清理。
