description: "进行中的 Observation 以观测预览实时可读：Observer 在本地的草稿中补全并决定何时结束，后端在内存中暂存最新的一份预览，结束后才保存为版本"
---

## 背景 [#context]

VS Code 从 14:00 起在前台，前台状态 Observer 每秒确认一次，16:00 切换应用。读取方要在这两个小时中就看到这一段，例如 Web 控制台显示正在使用的应用，另一台设备也能读到。如果每次确认都保存一个版本，两个小时会留下七千多个只差 `endAt` 的版本；如果等结束后才保存，读取方在 16:00 之前看不到这一段。

## 决定 [#decision]

- 尚未保存的 Observation 可以作为观测预览交给后端，供读取方实时读取。
- 只有 Observation 有观测预览。其他实体按版本提交。
- 原 Observer 形成观测预览并决定何时结束。进行中的 Observation 以草稿保存在 Observer 本地，那是权威；观测预览是草稿内容的副本，后端在内存中暂存每份 Observation 最新的一份。
- 观测预览不是版本：它没有 VersionId 和保存时间，不能被引用，也不改变实体的当前版本。
- 观测预览接在实体的当前版本之后。实体保存了新版本，后端就移除它的观测预览。
- 后端按 Observation 的规则校验观测预览，它引用的目标必须已保存。
- 后端暂存的观测预览可以丢失。后端重启或预览过期后，Observer 下一次写入时恢复。

## 理由 [#rationale]

追溯需要的是结束时的完整一段，延长过程中的每一秒没有追溯价值；实时读取需要的是最新的一份。所以实时可见交给观测预览，保留交给版本，进行中的时段不必为了被看见而保存成版本。

Observer 已经在本地保存进行中的观测，见 [ADR · 提交与 Runtime](./submission.mdx)。所以后端只需在内存中暂存一份副本，丢失后由 Observer 补上，不需要为它建表、迁移和备份。

引用固定到版本，追溯时读到的是保存时的内容，见 [ADR · 实体模型](./entity-model.mdx)。观测预览随时会变，所以不能被引用。一种类型需要在事实结束前就被引用时，Observer 对它选择及时提交，保存中间的版本。

观测预览引用的目标必须已保存，后端才能像校验版本一样校验它，读取方也能沿引用读到观测内容。观测内容在时段中保持不变，所以时段开始时就提交它没有额外的代价。

观测预览接在当前版本之后，用版本链判断先后：最终版本保存后，迟到的旧预览所基于的已不是当前版本，后端拒绝它，结束的时段不会重新显示为进行中。

放弃的方案：

- **每次确认都保存一个版本。** 一段两小时的前台时段形成七千多个版本，读取和追溯都要跳过它们。
- **观测预览保存在 PostgreSQL 中。** 权威在 Observer 本地的草稿，后端持久保存的那一份还要和它保持一致，每秒一次的覆盖写入也要付出存储的代价。
- **读取方引用观测预览时，由后端替 Observer 保存一个版本。** 陈述由 Observer 负责，后端只校验和保存 Observer 交来的版本。

## 代价 [#costs]

- 后端重启后，到 Observer 下一次写入观测预览之前，读取方读不到进行中的观测。
- 进行中的观测不能作为输入。例如晚上的推断运行时，仍在前台的那一段不能列入它的 InputSet。
- 观测预览只暂存在一个后端进程的内存中。部署多个 API 实例时，观测预览要换到实例之间共享的位置。
- 读取方要分别读取已保存的观测和观测预览，再组合成完整的时间线。
- Runtime 要为每份观测预览维护递增的序号，并持续写入后端。
