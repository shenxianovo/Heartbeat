## 背景 [#context]

用户有一台 Mac、一台服务器，以后还有手机。每台机器上的 Runtime 托管自己的 Observer，用户却想在任何一个客户端里看到全部 Observer：服务器上的应用识别 Observer 是否在运行，Mac 上的前台状态 Observer 有没有待发送的数据，并且能停用、修改设置或更新它们。

设备会离线。用户在断网的 Mac 上停用前台状态 Observer，它应当立即停下，联网后再让其他客户端知道。与此同时，用户可能在另一个客户端里改了同一个实例。管理操作还要能删除一个程序实例，并且删除之后它不再以旧身份提交。

Core 中 Observer 是业务实体承担的角色，人也可以是 Observer。这里管理的是由程序承担的 Observer，也就是 Runtime 托管的程序实例。

## 决定 [#decision]

- 后端为每个 Runtime 保存一条托管方登记，为它托管的每个程序实例保存一条实例登记。登记是管理数据的权威位置，不是 Core 的实体，也不能从版本推导。
- 每个 Runtime 有自己的托管方身份 `hostId`。一台机器可以运行多个 Runtime，它们是不同的托管方。
- 实例登记保存两项配置：启用和设置。客户端修改配置，只有所属的 Runtime 执行配置并报告实例的状态。
- Runtime 本地持久保存配置和待同步的修改。本机的修改先保存、立即生效，联网后再同步；后端不可用不妨碍本机管理。
- 同步只携带改动的字段。同一字段以后端最后接受的修改为准，不比较设备的时钟；设置是一个 JSON 对象，整体替换。
- Runtime 为每个实例的本机修改分配持久递增的序号，按序发送，重发沿用同一个序号和内容。后端用序号去重，并为每次接受的配置变化递增实例的修订号。
- 配置、实际运行、发送和连接是四项独立的信息。后端接受停用，不表示设备已经停止。
- 安装、更新、卸载、重试和读取可安装的包是在线操作，只在 Runtime 连接着后端时执行，不持久排队。没有收到明确结果时报告“结果未确认”，重连后不自动重放。
- Runtime 主动连接后端：所有调用都是 Runtime 发出的 HTTP 请求，后端用长轮询把配置变化和在线操作交给它。设备不需要开放入站端口。
- 删除实例永久结束一个程序实例：后端在一个事务中把实例登记标记为已移除，并删除它的 Core 实体。删除实体的接口作用于受管理的程序实例时，做同样的事。已移除的登记不能被配置同步恢复。
- 用户再次使用同一个程序时，显式创建新实例，得到新的 EntityId。
- Runtime 通过一次性的配对码接入后端，得到自己的托管方身份和凭证；后端只保存凭证的摘要。配对码只保存在 API 进程的内存中。
- 移除托管方撤销它的凭证，作用于它对后端的全部访问。已移除的托管方可以用为它签发的新配对码重新接入，恢复原来的身份。
- 管理入口的认证尚未决定。在此之前，不带托管方凭证的请求按管理入口处理，所以 API 只通过绑定本机的入口提供。
- 安装包可以声明每个部署只能有一个实例，后端在实例首次登记时检查。
- 长轮询、配对码和在线操作的状态保存在 API 进程的内存中，所以一个部署运行一个 API 进程。

## 理由 [#rationale]

管理登记记的是“这台 Mac 上的前台状态 Observer 应当启用”这样的运行配置，以及凭证和移除标记。它们不是用户的经历，不进入 Core；配置和凭证也无法从 Observation 推导，所以它们是权威数据，和 Core 的投影分开。

离线先生效，用户在断网时的操作才有意义。按字段同步，Mac 改启用、手机改设置时两项都保留。同一字段的冲突以后端接受的顺序为准：例如 Mac 离线时停用，手机在线时启用，Mac 联网后提交停用，结果是停用。这个“最后”不一定是用户最后点击的时刻，但规则简单、可以解释，也不依赖各设备的时钟。拒绝离线的旧修改要比较修订号，还要为冲突设计确认界面，个人用户很少遇到这种冲突，换来的复杂度不值得。

序号只解决重发：响应丢失后 Runtime 用同一个序号重发，后端认出已经接受过，不会用旧内容覆盖之后的修改。修订号描述后端配置本身的变化，Runtime 据此判断收到的配置是不是比自己已有的新。两者用途不同，所以分开。

启停和设置是长期的配置，设备重连时执行最新的配置即可。安装、更新、卸载和重试是一次性的动作：离线排队的“更新”可能在几天后执行，那时的目录和用户的意图都已经变了。所以这些动作只在线执行，界面在设备离线时禁用入口，结果不明时让用户重新读取实际状态。

Runtime 发出全部请求，设备在 NAT 和防火墙之后也能被管理。长轮询仍是普通的 HTTP，契约都写在 `openapi.json` 中，不需要另一套消息格式，也不引入新的外部服务。

删除实例时同时删除 Core 实体，程序实例的身份才真正结束：旧的进程或离线的 Runtime 继续用这个 EntityId 提交，都会按 [HISTORY-7](../core/rules/history.mdx#history-7) 被拒绝。两个删除入口都更新管理登记，否则从 Web 的实体页删掉 Observer 实体后，Runtime 仍会以旧身份运行并不断被拒绝。卸载只移除程序，所以重装沿用身份；删除实例之后，再次使用要显式新建，旧身份不会被自动恢复。

配对码让用户在管理入口签发一次接入，新设备凭它换取长期凭证，凭证不出现在配对码中。每个 Runtime 一份凭证，移除一台设备只撤销它自己；后端只保存摘要，数据库泄露也拿不到凭证。重新接入要用为这台设备签发的新配对码，普通的重试和旧凭证都恢复不了它。

管理入口的认证之后接入 OAuth。在此之前保持现在的本机入口，托管方凭证先把每个 Runtime 的身份分开：Runtime 只能登记、同步和报告自己的实例。

应用识别 Observer 需要全局一致的产品目录，两个实例并行调用模型会为同一款软件各建一个产品。首次登记时检查就够了：这一类实例在后端接受登记之前不启动，所以第二个实例不会运行。

放弃的方案：

- **一张持久的命令表，离线排队远程操作。** 要设计命令的状态机、过期和重放；排队的一次性操作在设备重连时可能已经不符合用户的意图。
- **按设备时钟决定冲突，或者弹出冲突让用户确认。** 设备的时钟不可靠；确认界面让用户为很少发生的冲突处理额外的流程。
- **CRDT 或分布式数据库。** 两项配置不需要合并算法。
- **WebSocket 或其他推送通道。** 要另写一份消息契约，并处理连接的生命周期；管理消息的频率很低，长轮询已经足够及时。
- **服务端专用的托管和三张专用表。** 托管方要实现两份，见 [ADR · Runtime 与进程托管](./observer-runtime.mdx#rationale)。

## 代价 [#costs]

- 同一字段的结果取决于后端接受的顺序，可能不是用户最后点击的那一次。
- 设置整体替换：两台设备离线时修改了设置中的不同项，后接受的一份覆盖前一份。
- 远程设备离线时不能安装、更新、卸载或重试，也不能立即停止它。
- 在线操作的结果可能不确定，界面要显示“结果未确认”，由用户重新读取状态。
- 一个部署只能运行一个 API 进程；API 重启后，配对码和进行中的在线操作都失效。
- 管理入口的认证接入之前，API 不能对外开放。
- 删除实例不可撤销；之后同一个程序只能以新身份运行。
