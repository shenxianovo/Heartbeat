## 背景 [#context]

[ADR · 单向写入与托管的分工](./data-capability.mdx) 定了程序怎样写入。还要决定 Runtime、客户端和 Observer 的进程怎样连接，程序实例的身份和业务数据放在哪里，更新和卸载之后它们怎样保留，以及在服务器上运行的 Observer 由谁托管。

服务器上的 Observer 依据全部已保存的数据形成观测，例如[应用识别 Observer](../observers/application-identity/index.mdx)。它和设备上的 Observer 一样需要持久的身份、安装和更新，以及用户能看到的启停和状态。

## 决定 [#decision]

- 设备和服务器运行同一个 Runtime。设备上由设备端客户端启动它，服务器上由服务管理器或容器以服务方式启动它。
- Runtime 启动每个启用的程序实例的进程。Observer 是一个普通进程：运行上下文从环境变量读取，标准输入关闭时结束，诊断写入标准错误，见 [Protocol · Observer 进程](../hosting/protocol.mdx#observer-process)。
- Runtime 用本地转发收下程序的写入，按顺序交给后端，不解释内容，见 [ADR · 单向写入与托管的分工](./data-capability.mdx)。
- 设备上的客户端通过另一对管道向 Runtime 发出管理指令、读取状态，并取得数据连接。服务方式的 Runtime 没有客户端管道，只经后端接受远程管理，见 [ADR · Observer 的统一管理](./observer-management.mdx)。
- Runtime 持久保存每个程序实例的 EntityId，启动进程时交给它。业务对象的 EntityId 仍由各 Observer 的业务规则确定。
- 业务代码自己的持久数据放在实例的数据目录中，由业务代码解释。
- 程序文件和实例数据分开保存：`packages/<package-id>/<version>/` 是解压后的包，`instances/<entity-id>/` 是实例的数据。安装登记记录包和程序实例的对应关系。
- 数据目录是程序实例的身份和业务状态的权威位置。服务器部署必须持久保存它。
- 设备上的 Runtime 随客户端运行，客户端退出时一起退出。服务方式的 Runtime 由服务管理器启停。
- 服务器上的 Observer 是独立的安装包，和设备上的 Observer 使用同一种包格式、安装流程和 SDK。API 进程不运行 Observer。
- 开发时不启动客户端，用同一个 Runtime 在命令行中运行 Observer。
- Runtime 不是 Observer，没有自己的实体。它在后端有一条管理登记，见 [ADR · Observer 的统一管理](./observer-management.mdx)。
- 以上是桌面平台和服务器的做法。移动平台承担相同的职责，运行机制另定。

## 理由 [#rationale]

环境变量和标准输入的关闭在每种语言中都有，接入一种新语言不需要额外的通信库。Runtime 自己启动进程，所以运行上下文只交给这个程序实例。本地转发只监听回环地址，写入的端口写在运行上下文中。

客户端只发管理指令和读取，不在写入的路径上，Swift 代码因此只处理界面和进程。

身份和数据放在实例目录，目录名不含包版本，所以更新、卸载后重装都找回同一个程序实例，见 [OBSERVER-4](../core/model/observer.mdx#observer-4)。程序文件在独立的版本目录中，更新时可以先完整准备新版本，再切换过去。

业务代码自己的状态，例如助手会话 Observer 的读取进度，含义只有业务代码清楚，所以留在实例的数据目录中。业务对象的身份不属于这种状态，它们与 Runtime 无关，见 [ADR · 数据能力与托管的分工](./data-capability.mdx#rationale)。

服务器也用 Runtime，托管方只有一份实现：安装、更新、卸载、启停、重启和远程管理在两端相同，服务器上的 Observer 可以独立于 API 发布和升级，它的故障也不影响 API 进程。代价是服务器上多一个常驻进程和一个持久目录。

开发和产品使用同一个 Runtime，Observer 只有一种运行方式，测试覆盖的就是用户运行的路径。

Runtime 只运行进程，陈述由形成它的 Observer 负责，见 [OBSERVER-6](../core/model/observer.mdx#observer-6)。

放弃的方案：

- **客户端转发 Observer 的数据。** Swift 代码进入数据的路径，多一次交接。
- **服务器上的 Observer 作为模块运行在 API 进程中，身份和业务状态存进 PostgreSQL。** 少一个进程和一次 HTTP 封装，但托管方要实现两份：安装、启停、状态和写入在两端各不相同；Observer 只能随 API 发布和启停，它的故障会影响 API。

## 代价 [#costs]

- Runtime 是一台机器上所有 Observer 共用的进程。它崩溃时所有采集都会中断，由客户端或服务管理器重新启动；标准输入关闭时 Observer 退出，还没有写入的数据随之丢失。已交给本地转发的写入保留。
- 受托管的 Observer 必须能作为子进程运行。
- 每个 Observer 的进程各自带着自己语言的运行库。
- 卸载后，实例的身份和数据仍留在本机。
- 服务器部署要为 Runtime 保留持久目录。目录丢失后，其中的程序实例和业务状态都无法从后端恢复。
