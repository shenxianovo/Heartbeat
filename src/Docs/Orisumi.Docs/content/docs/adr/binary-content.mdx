## 背景 [#context]

前台状态 Observer 能读到应用的图标，其他设备上的客户端也要显示它。版本内容是 JSON，存不下文件。之后的截图、音频片段也是文件，体积大，同一份文件常被很多版本使用：一个应用的图标出现在它的每个前台时段中。

文件要满足版本已有的要求：已保存的版本读到的内容不变，离线的 Runtime 能可靠补交，删除后不留副本。

## 决定 [#decision]

- 业务字段可以声明为 `binary`。值是文件的描述：摘要、媒体类型和大小。
- 二进制内容以 SHA-256 摘要标识，同样的字节只保存一份。
- 文件由使用它的业务字段承载，不另设文件实体。例如应用图标是前台时段的 `icon` 字段。
- 写入方先上传内容，再提交使用它的版本。
- 后端保留仍有已保存版本使用的内容；使用它的最后一个版本删除时，内容一并移除。
- 后端把内容保存在 PostgreSQL 的 `contents` 表中。
- 业务代码把字节放在批次中交给 Runtime，字节和版本在同一个本地事务中保存；Runtime 发送版本前先上传它用到的内容。

## 理由 [#rationale]

摘要由字节算出，所以描述一旦保存，字节就确定了，[VERSION-2](../core/model/version.mdx#version-2) 直接覆盖文件，不需要另一条“文件不可替换”的规则。重试时比较描述的 JSON，就是比较字节，[VERSION-7](../core/model/version.mdx#version-7) 不用改。同一个图标出现在上千个时段中，后端只保存一份，读取方也只下载一次。

媒体类型和大小写在描述中。读取方读到版本就知道怎样显示，也能判断要不要下载；同样的字节可以在不同的字段中按不同的类型使用。

文件放在使用它的字段中，删除就跟随使用它的实体：删除一段时段，它的图标在没有其他时段使用后随之移除。用途由字段名表达，例如 `icon`。业务上需要文件有自己的身份时，例如用户整理的一组照片，由对应的 Observer 定义一种带 `binary` 字段的业务类型。

先上传、后提交，与只引用已保存的版本（[ENTITY-6](../core/model/entity.mdx#entity-6)）是同一个顺序：版本保存时，它用到的一切都已在后端。上传按摘要幂等，响应丢失后原样重传。

业务代码交出批次、收到本地回执，数据就已本地保存（见 [Hosting · 回执](../hosting/submission.mdx#receipts)）。字节和版本在同一个事务中保存，回执对文件同样成立，离线和重启后照常补交。

一个 1024×1024 的图标几百 KB，去重后总量很小。PostgreSQL 已经是后端唯一的依赖，内容与版本在同一个事务中保存和删除，保留规则直接由事务保证。

放弃的方案：

- **通用附件实体，由业务字段引用它的版本。** 文件多了一层身份和版本链，删除使用方后附件仍然留下，要用户另外删除。
- **把字节以 Base64 写进版本内容。** 版本的体积放大三分之一，同一个图标在每个时段中重复保存，所有读取版本的请求都要带上它。
- **版本中保存下载地址。** 地址会改变或过期，版本读到的内容就不再确定。
- **为每次上传分配 UUID。** 相同的字节要另外去重，判断两个版本相同还要比较字节。
- **对象存储。** 增加一项部署依赖，内容与版本的保存和删除跨越两个系统。体积大的文件出现时再评估。

## 代价 [#costs]

- 后端要为每个版本记录它用到的内容，删除时据此判断内容是否还有使用方。
- 上传后长时间没有提交的内容会被清理，Runtime 提交时被拒绝，要重新上传。
- 任何读到摘要的读取方都能读取这份内容，内容的读取不区分它被哪个版本使用。
- 读取方要按描述中的媒体类型解释字节，下载接口本身不带类型。
- 大文件占用数据库的空间和备份，单份内容受大小上限约束。
