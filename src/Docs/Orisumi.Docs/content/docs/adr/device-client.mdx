## 背景 [#context]

前台状态 Observer 是一个命令行程序：在终端里启动，终端关闭后采集就停了；发送状态写在标准错误中，用户平时看不到。用户需要一个常驻的程序来运行 Observer，并能看到它们是否正常工作。

Observer 会越来越多，用户只想运行其中一部分。新增一个 Observer 或修复它，也应该不必等客户端发布新版本。

Observer 停下来的原因有很多：用户停用它、卸载它，或者它崩溃了。这时它已经形成的数据还在本机，要能继续送到后端。

## 决定 [#decision]

- 每个设备平台有一个原生客户端：macOS、Windows 和 Android 各用自己平台的界面技术，macOS 客户端用 SwiftUI 编写。桌面平台的客户端常驻在菜单栏或系统托盘。
- 客户端通过 [Runtime](./observer-runtime.mdx) 托管本机的 Observer：安装、更新和卸载，启用和停用，故障后重启，显示运行和发送状态，管理设置和登录时启动。其他机器上的 Observer 经后端管理，见 [ADR · Observer 的统一管理](./observer-management.mdx)。
- 陈述由各 Observer 负责，客户端只托管它们，所以客户端没有自己的实体。
- 每个 Observer 单独安装。安装包是每个操作系统和架构一个 ZIP，包含清单 `observer.json`、可运行的入口和可选的资源。
- 客户端从官方目录安装 Observer。官方目录是一个通过 HTTPS 读取的静态 JSON 列表，给出每个包的下载地址和 SHA-256。随客户端附带的 Observer 走同样的安装流程，只省略下载。
- 发布方提供能直接在目标设备上运行的完整产物。安装时不执行包中的脚本，也不调用语言的包管理器。
- Observer 安装后直接开始采集，用户可以停用它。
- Observer 的更新由用户确认后安装。新包完整准备好之后才替换旧版本，身份、设置和启用状态保持不变。
- Observer 意外退出后，Runtime 有限次数地自动重启它，仍然失败时显示故障，等用户重试。
- 卸载 Observer 时保留它的身份、设置和本地数据，重新安装后沿用。
- 桌面客户端关闭窗口后继续运行。退出客户端时，采集和发送都停止，下次启动时恢复。
- 客户端为每个 Observer 显示运行和发送状态，以及最近的数据。Observer 的专用视图用原生界面实现，随对应平台的客户端发布。客户端经 Runtime 读取数据，Runtime 合并后端已保存的和本地还没发送的部分。更早的数据和追溯用 Web 控制台。

## 理由 [#rationale]

原生界面直接提供菜单栏、登录项和权限请求，外观和交互也与系统一致。在 .NET 中做这些要靠 AppKit 互操作。Observer 作为单独的程序运行，可以用别的语言编写，例如前台状态 Observer 是 .NET 程序。

客户端只安装、运行、展示和停止，陈述由形成它的 Observer 负责，见 [OBSERVER-6](../core/model/observer.mdx#observer-6)。所以客户端不需要身份，记录中也不出现它。

Observer 单独安装，新增来源或修复采集只需发布这个 Observer，客户端的版本不变。附带的 Observer 走同一套安装和管理，客户端只维护一条路径；用户卸载了附带的 Observer，客户端启动或升级时也不会把它装回来。

ZIP 和 JSON 清单任何语言的构建都能产生。包中是完整的产物，安装只是校验、解压和登记，在每台设备上结果都一样。官方目录是静态文件，不需要后端新增接口。摘要让客户端确认下载的内容就是目录中列出的那一份。

用户安装一个 Observer，就是想让它开始记录，所以安装后直接采集。

更新可能改变采集的内容，所以由用户决定什么时候安装。新包准备失败时旧版本继续运行，用户不会因为一次失败的下载丢掉采集。

崩溃多是暂时的，自动重启能接上采集；连续失败说明问题不会自己消失，这时停下来报告错误，等用户处理。

卸载后保留身份，重新安装的 Observer 就是原来的程序实例，见 [OBSERVER-4](../core/model/observer.mdx#observer-4)。卸载前后的记录归在同一个 Observer 下。

用户打开客户端，最常问的是“今天用了什么”。专用视图回答这类问题，例如前台应用的时间线。视图用原生界面写在客户端中，所以新增一种专用视图要发布新的客户端；Observer 的采集照样可以单独更新。没有专用视图的 Observer 也有公共的状态和最近数据，安装后就能使用。

读取经过 Runtime：已保存的数据从 API 读取，客户端重启后仍然完整，和 Web 控制台看到的是同一份；还没发送的部分只在 Runtime 的本地数据中，由 Runtime 补上。Observer 停用或崩溃时，数据照样能读到。其他日期和追溯需要完整的读取界面，留给 Web 控制台。

macOS 按应用授予权限。Observer 由客户端启动的 Runtime 启动，系统把它的权限算在客户端名下，用户只需授权一个应用。

放弃的方案：

- **Observer 和客户端用同一种语言。** 前台状态 Observer 和 Runtime 都要用 Swift 重写，以后的 Observer 也不能按来源选择语言。
- **客户端用 .NET 编写。** 菜单栏、登录项和权限引导都要靠 AppKit 互操作。
- **Observer 打包在客户端中，随客户端更新。** 新增或修复一个 Observer，都要发布新的客户端。
- **Observer 在包中附带网页视图，客户端用 WebView 承载。** 原生客户端中出现网页，外观和交互与系统不一致，还要维护网页和客户端之间的桥接。
- **Observer 附带动态加载的原生视图。** 每个平台都要一套插件接口、二进制兼容和签名规则。
- **安装时执行包中的脚本。** 安装的结果取决于每台设备的环境，也很难确认脚本做了什么。
- **退出客户端后仍在运行的发送服务。** 要多维护一个常驻进程，用户退出客户端后，本机仍有 Orisumi 的程序在运行。

## 代价 [#costs]

- 每个设备平台各写一个原生客户端，每种专用视图在每个平台各实现一次。
- 新增专用视图要发布新的客户端。
- 每个 Observer 要为每个支持的操作系统和架构各发布一个包，包中带着自己语言的运行库。
- 要维护官方目录、包的兼容和各平台的签名。
- 卸载后，Observer 的身份、设置和本地数据仍留在本机。
- 停用和退出期间没有读数，这段时间在记录中是空白。
- 读取依赖 API 和 Runtime。断网时只能显示本地的部分，统计可能不完整。
