## 背景 [#context]

前台状态 Observer 是一个命令行程序：在终端里启动，终端关闭后采集就停了；发送状态写在标准错误中，用户平时看不到。用户需要一个常驻的程序来运行 Observer，并能看到它们是否正常工作。

Observer 会越来越多，用户只想运行其中一部分。新增一个 Observer 或修复它，也应该不必等客户端发布新版本。

Observer 停下来的原因有很多：用户停用它、卸载它，或者它崩溃了。这时它已经形成的数据还在本机，要能继续送到后端。

## 决定 [#decision]

- 每个设备平台有一个客户端。桌面平台的客户端常驻在菜单栏或系统托盘，macOS 客户端用 SwiftUI 编写。
- 客户端托管本机的 Observer：安装、更新和卸载，启用和停用，故障后重启，显示运行和发送状态，管理设置和登录时启动。
- 陈述由各 Observer 负责，客户端只托管它们，所以客户端没有自己的实体。
- 每个 Observer 单独安装。客户端从官方列表安装 Observer，新的 Observer 不用更新客户端就能安装。随客户端附带的 Observer 也按同样的方式安装和管理。
- Observer 安装后直接开始采集，用户可以停用它。
- SDK 的发送随客户端运行。Observer 停用、崩溃或卸载后，已经交给 SDK 的数据继续发送。
- 卸载 Observer 时保留它的身份、设置和待发送的数据，重新安装后沿用。
- 桌面客户端关闭窗口后继续运行。退出客户端时，采集和发送都停止，下次启动时恢复。
- Observer 的更新由用户确认后安装。Observer 崩溃后，客户端自动重启它，连续失败后停止重启。
- 客户端展示每个 Observer 今天的统计和最近的数据，包括还没发送的部分。Observer 可以提供自己的视图。更早的数据和追溯用 Web 控制台。

## 理由 [#rationale]

SwiftUI 直接提供菜单栏、登录项和权限请求，这些在 .NET 中都要靠 AppKit 互操作实现。Observer 作为单独的程序运行，可以用别的语言编写，例如前台状态 Observer 和它使用的 SDK 是 .NET 程序。各语言的 SDK 承担相同的职责，见 [ADR · 提交与 SDK](./submission.mdx)。

客户端只安装、运行、展示和停止，陈述由形成它的 Observer 负责，见 [OBSERVER-6](../core/model/observer.mdx#observer-6)。所以客户端不需要身份，记录中也不出现它。

Observer 单独安装，新增来源只需发布这个 Observer，客户端的版本不变。附带的 Observer 走同一套安装和管理，客户端只维护一条路径。

用户安装一个 Observer，就是想让它开始记录，所以安装后直接采集。

发送跟着客户端，不跟着单个 Observer。Observer 停用、崩溃或卸载时，它已经形成的版本留在本地，发送照常进行。客户端退出时发送一起停止，所以不需要一个独立的后台服务；待发送的数据在本地，下次启动后继续。

卸载后保留身份，重新安装的 Observer 就是原来的程序实例，见 [OBSERVER-4](../core/model/observer.mdx#observer-4)。卸载前后的记录归在同一个 Observer 下。

更新可能改变采集的内容，所以由用户决定什么时候安装。崩溃多是暂时的，自动重启能接上采集；连续失败说明问题不会自己消失，这时停下来报告错误，等用户处理。

用户打开客户端，最常问的是“今天用了什么”。这些数据从 API 读取，客户端重启后记录仍然完整，看到的和 Web 控制台是同一份数据。尚未发送的部分只在本地，所以客户端把它们补上。每种数据适合怎样展示，由形成它的 Observer 决定，所以视图跟着 Observer 安装，新增 Observer 的视图也不用更新客户端。其他日期和追溯需要完整的读取界面，留给 Web 控制台。

macOS 按应用授予权限。Observer 由客户端启动，系统把它的权限算在客户端名下，用户只需授权一个应用。

开发和测试时，Observer 也可以作为命令行程序单独运行，这时由进程内的 SDK 发送。

放弃的方案：

- **Observer 和客户端用同一种语言。** 前台状态 Observer 和 .NET SDK 都要用 Swift 重写，以后的 Observer 也不能按来源选择语言。
- **客户端用 .NET 编写。** 菜单栏、登录项和权限引导都要靠 AppKit 互操作。
- **Observer 打包在客户端中，随客户端更新。** 新增或修复一个 Observer，都要发布新的客户端。
- **每个 Observer 的进程自己发送。** Observer 停用、崩溃或卸载后，待发送的数据停在本地。
- **退出客户端后仍在运行的发送服务。** 要多维护一个常驻进程，用户退出客户端后，本机仍有 Orisumi 的程序在运行。

## 代价 [#costs]

- 客户端和它托管的 Observer 用不同的语言编写，彼此通过进程间的协议交互。
- 每个桌面平台各写一个客户端外壳。
- 客户端要维护官方列表、Observer 的安装和更新，以及版本兼容。
- SDK 的发送与采集分开运行，客户端要能接入各种语言的 SDK。
- 卸载后，Observer 的身份、设置和待发送的数据仍留在本机。
- 停用和退出期间没有读数，这段时间在记录中是空白。
- 客户端依赖 API 的读取接口。每个时段的内容要单独读取一次，读过的版本在客户端缓存。
