description: "事物只有身份，一切内容都是有作者的 Observation；陈述用不可变的版本保存，引用事物写 EntityId，引用陈述固定到版本"
---

## 背景 [#context]

Orisumi 保存的数据来源各异：前台应用、输入事件、浏览历史、健康数据，还有模型的推断和用户的确认、否定。字段各不相同，读取方却要用同一种方式定位数据、遍历关系、按时间查找事实。

数据会变化：时段延长、应用改名、时区被纠正、字段结构演进。只保留最新值的话，推断依据的内容会在事后变样，读取方看不到推断形成时用的内容。

上一版模型把一件事拆成内容实体和 Observation 两个实体，关系有业务字段引用、关系实体和按值匹配三种写法。实际数据说明这些拆分用处很小：没有一个内容被第二个 Observer 观测过，内容和 Observation 始终 1:1；9 个引用字段中 8 个指向设备、会话这类对象，约 0.15% 的业务引用指向目标的旧版本。粒度规则也一直在把模型推向另一个方向：会话只留身份，产品只留名称，会变的部分都拆成单独的类型。

## 决定 [#decision]

- 所有数据都是实体，用 EntityId 标识。用户的数据只有两种：事物和 Observation。
- 事物只有身份，没有内容和版本，第一次被提到时创建。
- Observation 是一份陈述。谁负责、说了什么、怎么来的、依据什么、事实何时成立，都在它的同一个版本中。
- Observation 的内容保存在版本中。每次保存形成一个不可改写的新版本，有自己的 VersionId。
- 每个有版本的实体只有一条版本链。
- 一份 Observation 只有一个作者。
- 引用事物时写 EntityId，引用陈述时写 VersionId。
- 实体之间的关系都写成 Observation 中的引用，不再有单独的关系实体。
- 新版本只能引用已保存且未被删除的版本。
- EntitySchema 和 InputSet 是支撑结构，由 Core 定义。
- 一个 EntitySchema 定义一种业务类型，它的每个版本是一个 Schema 版本。Observation 固定引用它所用的 Schema 版本。
- 引用的位置由 Core 或 Schema 版本声明，可以出现在顶层字段、对象成员和数组元素中。
- 只有 Observation 保存事实时间。

## 理由 [#rationale]

事物回答“在说谁”，Observation 回答“说了什么”。把它们分开之后，模型的很多规则都不需要了。

事物没有内容，所以没有并发和覆盖的问题，任何 Observer 都能提到同一台设备。这也让采集不需要先写入被引用的对象，读不到后端也能写。

陈述只有一个作者，后端可以直接检查，所以“同一个实体的内容由一个写入方决定”从约定变成了规则。

版本固定只对陈述有意义。推断要指向它当时读到的那一版，否则依据会在事后漂移。设备这样的事物没有内容，也就没有漂移，设备改名只是一条陈述的新版本，引用它的数据都不受影响。

关系都是 Observation 中的引用，所以每条关系都有时间、责任和形成方式，前端可以把所有引用字段画成同一种边。“设备上的应用”和模型判断的“123 是本人”是同一种东西。

每个版本都带着自己的时间，版本就不用区分补全、纠正和来源对象的变化：时间相同、内容不同是纠正，时间不同是变化。

合并之后，读取也变简单了：查询一次就拿到内容和时间，删除一件事也只是删除一个实体。

只引用已保存的版本，引用就不会成环。反例：观测 A 引用尚未保存的输入集 S，观测 B 使用了 A，之后再把 B 填进 S，A 和 B 就互相依赖。

EntitySchema 由 Core 定义，否则定义会无限递归。InputSet 由 Core 定义，所有读取方按同一种方式理解输入。

业务类型的身份和 Schema 版本分开后，增减字段不用新建类型，旧数据按原来的 Schema 版本解释，不需要迁移。业务含义改变时新建类型，旧数据才不会被重新解释。

引用的位置由 Core 或 Schema 版本声明，读取方不必理解业务字段，就能枚举一个版本的全部引用。

放弃的方案：

- **内容和 Observation 分成两个实体。** 多一层间接，读取要多一步，写入要同时维护两条版本链。共用内容的能力没有用到。
- **事物保存内容。** 多个 Observer 要共用它时，内容会互相覆盖，只能规定共用的实体只放不变的内容。
- **事物的引用固定到版本。** 设备改名时，要么所有引用方都形成新版本，要么比较时按实体比较，读取到的又是旧内容。
- **关系实体和字段引用并存。** 读取方和前端要处理两套，选择哪一种也要靠判断。
- **只保留最新值，需要历史时由各业务类型另存。** 推断依据的内容会在事后改变，每种类型还要各自设计历史。
- **版本只保存差异。** 读取一个版本要从首版逐版应用差异，一版出错会影响之后所有版本。
- **引用陈述时指向实体，读取时取当前版本。** 追溯时看不到形成推断时用的内容。
- **允许引用目标晚到。** 版本之间会出现循环依赖，后端还要在目标后到时反查引用方补做检查。
- **只允许顶层字段作为引用。** 好处只是存储方便，却让物理布局限制了领域结构。
- **结构变化就新建类型和资源名。** 同一业务概念的数据散落在多个类型中。

## 代价 [#costs]

- 事物本身读不到内容，显示设备名要再查 Name。读取接口要能把事物和它的陈述一起返回。
- 事物的描述要定义成单独的业务类型，类型会变多。
- 每次保存都保留完整内容，存储随版本数增长。
- 写入方必须按依赖顺序写入 Observation，两个首次出现的版本不能互相引用。
- 业务数据保存前，所用的 Schema 版本必须已保存。
- 引用可以出现在嵌套结构中，存储和反查不能只按顶层单列设计。
- 设备当时叫什么，要按事实时间查，时间未知时查不到。
