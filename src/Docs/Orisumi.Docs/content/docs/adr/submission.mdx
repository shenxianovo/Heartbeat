## 背景 [#context]

Observer 可以用不同的语言编写，形成版本的共同步骤却只应实现一次：生成 VersionId、接好版本链、对齐 EntitySchema、上传二进制内容、提交。本 ADR 讲程序实例怎样把版本交给后端，Observer 的划分见 [ADR · Observer 与输入集](./observers-and-evidence.mdx)。

Observer、Runtime 与 SDK 的模型正在重新讨论。为了让讨论从最简单的正常路径开始，这一版假设提交总能完成，不处理断网、崩溃和重启后的继续。

## 决定 [#decision]

- Runtime 解决各 Observer 共用的提交问题：持久保存程序实例的身份，登记 EntitySchema，把业务代码交来的批次形成版本，提交给后端。
- 所有程序实例都经 Runtime 提交，设备和服务器上相同，见 [ADR · Runtime 与进程托管](./observer-runtime.mdx)。
- 程序实例的身份持久不变。
- 业务代码通过所用语言的 SDK 与 Runtime 通信。各语言共用一个 Runtime；SDK 只把业务操作交给 Runtime，不保存数据。
- Runtime 用 .NET 编写。
- 一次业务变化作为一个有序批次交给 Runtime。Runtime 把它形成一次提交，收到后端的响应后把结果或错误交给业务代码。
- Runtime 不在本机保留版本。提交失败时，整个批次都没有保存，由业务代码决定之后怎么做。
- 后端整体保存一次提交：全部通过才保存，任何一个版本被拒绝，整次提交都不保存，见 [VERSION-13](../core/model/version.mdx#version-13)。
- 一段事实何时结束、何时提交它的 Observation，由 Observer 的业务代码判断。

## 理由 [#rationale]

共同步骤放进一个公共的 Runtime，每种新语言只需写一层很薄的 SDK。

前台状态 Observer 切换应用时，要形成本机应用、前台时段的内容和 Observation。这些版本必须一起成立，所以一次业务变化整批交给 Runtime，后端整体保存。批内的操作可以引用前面操作的结果，例如前台时段引用本机应用的版本，不必为了取得 VersionId 拆成几次交接。

提交在业务代码等待时完成，业务代码收到结果时版本已保存。应用识别 Observer 判断下一条线索之前，能读到上一条形成的产品，不需要另外等待最终结果。

整体保存让写入方只面对两种结果：全部保存，或全部没有保存。被拒绝之后，写入方不必弄清哪些版本已经保存。

放弃的方案：

- **每个 Observer 自己实现提交。** 版本链、Schema 对齐和二进制内容的上传会在每个 Observer 中重复。
- **每种语言各写一份提交。** 同样的步骤要在每种语言中实现，并保持一致。
- **Runtime 先把版本存在本机，再在后台发送。** 断网和重启时不丢数据，但要维护本机版本的状态、发送队列、请求去重和恢复，业务代码还要处理“已交给 Runtime 但还没保存到后端”的状态。模型重新讨论期间不承担这些。

## 代价 [#costs]

- 后端不可用时，提交失败，进行中的数据可能丢失。
- 进程意外退出时，还没有提交的数据丢失。
- 每次业务变化都要等后端响应后才能继续。
- 进行中的事实在业务代码提交它的 Observation 之前读不到。
- SDK 能用的操作受 Runtime 限制，新的操作要先加进 Runtime。
- Runtime 和各语言的 SDK 之间有一份协议，两边都要按协议版本兼容。
