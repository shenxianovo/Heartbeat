## 为什么验证 [#why]

草稿决定后端会收到几个版本，冻结决定版本何时不再改写、按什么顺序发送。两种提交策略的区别只在草稿何时冻结。约定见 [Submission · 版本的状态](../../hosting/submission.mdx#states) 和 [提交策略](../../hosting/submission.mdx#strategies)。

## 前置条件 [#setup]

Runtime 的本地保存使用独立的 SQLite 文件，后端是记录每次请求、按需返回响应的 HTTP 处理器。

## 操作与预期结果 [#steps]

| 操作 | 预期结果 |
| --- | --- |
| 形成一份 Observation 的草稿，再补全一次 | VersionId 和 `previousVersionId` 不变 |
| 业务代码引用一个实体，之后再补全它 | 被引用的版本已冻结，补全形成新版本，`previousVersionId` 指向被引用的版本 |
| Observation 引用一个仍是草稿的观测内容，然后冻结 Observation | 观测内容先冻结；发送时观测内容排在 Observation 之前 |
| 结束后提交：通知结束前发送一次，通知结束后再发送 | 第一次没有发送这份 Observation；第二次只发送一个版本，内容是最终结果 |
| 及时提交：形成草稿后发送，再补全并发送 | 后端依次收到两个版本，第二个的 `previousVersionId` 指向第一个 |
| 结束后提交：重启 Runtime，再通知结束并发送 | 发送的是重启前那份草稿的 VersionId |
| 写入观测预览：形成 Observation 的草稿，再补全一次 | 观测内容先发送；确认保存后写入观测预览，两次写入的 `sequence` 递增，第二次带补全后的内容 |
| 写入观测预览：重启 Runtime 后再补全 | `sequence` 大于重启前的最后一次 |
| 写入观测预览时后端返回 `409`，`rule` 为 `VERSION-6` | Runtime 停止写入这份观测预览，本地草稿不变 |
| 通知结束并发送 | 不再写入这份观测预览；发送一个版本，内容是最终结果 |
| 写入观测预览时，Observer 的进程意外退出 | 本地草稿保留，没有被结束；Runtime 不再写入这份观测预览；已冻结的观测内容继续发送 |

## 测试实现 [#implementation]

以下方法位于 `tests/Orisumi.Integration.Tests/`，对应本页的预期范围：

- 草稿合并保持身份和前驱、结束前不发送该 Observation、重启后沿用草稿身份并发送最终内容：`RuntimeStoreTests.DraftMergesFreezeDependenciesAndRecoverInOrder`。
- 引用草稿使其冻结，之后补全形成后继版本：`RuntimeStoreTests.ReferencingDraftFreezesItAndCompletionCreatesSuccessor`。
- 冻结 Observation 时先冻结并发送其内容依赖：`RuntimeStoreTests.FreezingObservationSendsItsDraftContentFirst`。
- 及时提交的两次发送形成相连版本：`RuntimeStoreTests.ImmediateSubmissionSendsTwoLinkedObservationVersions`。
- 写入观测预览时后端返回 `VERSION-6`，Runtime 停止写入；之后本地补全或重启 Runtime，都不再写入这份观测预览，发送也不报错：`ObserverPreviewTests.VersionConflictStopsPublishingEvenAfterLocalUpdatesAndRestart`。
- 未覆盖：进程意外退出后的草稿。

观测内容先于观测预览保存、`sequence` 递增且重启后继续递增，以及通知结束后不再写入、只发送一个版本，由前台状态 Observer 的测试检查：`RuntimeStoreTests.ForegroundUploadsOnlyFinishedPeriods` 和 `ObserverPreviewTests.LivePreviewRecoversAcrossServerAndStoreRestartsAndCompletesOnce`。它们关联 [Foreground Submission](../observers/foreground-submission.mdx)，执行结果在那一页显示。
