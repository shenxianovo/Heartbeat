## 为什么验证 [#why]

Web 控制台按[归属](../../observers/application-identity/index.mdx#membership)把各设备上的本机应用合并为应用产品，用户在这里改正模型的判断。修改要以用户本人的身份陈述，并且只改变产品，不改变采集到的数据。约定见 [Web · 应用](../../clients/web.mdx#applications)。

## 前置条件 [#setup]

API 连接独立的测试数据库。测试直接提交本机应用、前台时段和应用产品，再在控制台中操作。

## 操作与预期结果 [#steps]

| 操作 | 预期结果 |
| --- | --- |
| 两个本机应用的线索在同一个产品中 | 名称和时长按一个产品显示，时长是两者之和 |
| 本机应用的线索不在任何产品中 | 按本机应用单独显示为未归属 |
| 一条线索同时出现在两个产品中 | 本机应用归到当前版本保存时间最晚的产品 |
| 第一次修改，还没有用户本人 | 提交中先保存 User 的 EntitySchema 和用户本人；之后的修改沿用它 |
| 把一条线索加入新产品 | 一次提交：InputSet、新产品的首版、原产品的新版本、两份 Observation，Observer 都是用户本人；页面按新产品合并 |
| 修改之后 | 本机应用、前台时段和之前的 Observation 保持原样 |
| 产品改名 | 产品形成新版本，页面显示新名称 |
| 合并两个产品 | 线索都在保留的产品中，另一个产品被删除 |
| 修改期间产品被另一方更新 | 提交被拒绝，控制台提示用户并重新读取 |

## 测试实现 [#implementation]

- 按产品合并、时长相加、彼此之间不算切换：`src/lib/day.test.ts` 的 `groupThings`。
- 线索匹配、保存得最晚的产品优先、未归属和只有本机线索的安装：`src/lib/applications.test.ts` 的“归属”。
- 每种修改提交的版本、顺序、InputSet 的成员和用户本人的 Observation，合并后删除：`src/lib/applications.test.ts` 的“修改”。
- 第一次修改时先保存 User 的 EntitySchema 和用户本人；把线索加入新产品；拖到另一个产品；删除产品；没有本机应用时的空状态：`tests/e2e/applications.spec.ts`，后端由路由拦截在内存中模拟。
- 修改期间产品被另一方更新时的提示：未覆盖。

这些是 Vitest 和 Playwright 的测试，结果不进入 TUnit 报告。
