export const caseId = 'foreground-submission';

## 为什么验证 [#why]

前台状态 Observer 采用结束后提交并写入观测草稿：进行中的时段以草稿实时可读，每个时段只保存一个版本。程序异常退出时，进行中的时段要在下次启动时结束于最后一次确认，停机期间不计入时段。约定见 [Foreground State · 提交](../../observers/application-activity/index.mdx#submission)。

## 前置条件 [#setup]

SDK 使用独立的 SQLite 文件，读数是模拟的。需要后端的行通过 `WebApplicationFactory` 启动 API，连接一个独立的测试数据库，见 [Database](../database.mdx)。

## 操作与预期结果 [#steps]

| 操作 | 预期结果 |
| --- | --- |
| 确认应用在前台并延长当前时段，然后发送 | 后端读到观测内容；读取这份 Observation 返回 `404` |
| 同一应用连续确认多次 | 读取草稿得到最近一次确认的 `endAt`；这份 Observation 没有版本 |
| 切换应用 | 旧时段保存一个版本，`endAt` 是切换的时刻；旧时段的草稿被移除，新时段有自己的草稿 |
| 后端重启，之后继续确认 | 重启后读不到草稿，下一次写入后恢复；本地草稿和已保存的版本不变 |
| 结束当前时段，然后发送 | 后端能读到观测内容和 Observation |
| 延长到第 1 秒后重新打开 SQLite 文件，恢复两次 | 遗留的时段结束于第 1 秒，开始时间不变，只结束一次 |
| 另一个程序实例打开同一个 SQLite 文件 | 报错，原有的待发送版本保留 |
| 切换应用时，写入新时段前本地写入失败 | 旧时段的结束和新时段一起回滚；之后结束的仍是原来的时段 |
| 同一应用时段中标题变化多次 | 每个标题时段引用这个应用时段的观测内容；应用时段的 Observation 不因标题变化形成版本 |
| 两个应用时段的应用和名称相同 | 两个时段的观测内容是不同的实体，各自的标题归属各自的时段 |

## 测试实现 [#implementation]

以下方法位于 `tests/Orisumi.Integration.Tests/`，对应本页的预期范围：

- 进行中不上传 Observation、结束后可读到内容和 Observation：`ObserverSdkTests.ForegroundUploadsOnlyFinishedPeriods`。这个方法按旧的约定检查进行中也读不到观测内容，需要改为检查观测内容已保存。
- 重启后按最后确认恢复且只结束一次，以及另一程序实例打开同一文件时报错并保留队列：`ForegroundSubmissionTests.ActivePeriodStaysLocalAndRestartClosesLastCheckpointExactlyOnce`。
- 切换时写入失败，结束旧时段与新建时段一起回滚：`ForegroundSubmissionTests.FailedTransitionRollsBackBothOldPeriodAndNewCheckpoint`。
- 未覆盖：观测草稿的读取、切换后移除、后端重启后恢复，以及窗口标题的归属。观测草稿和窗口标题尚未实现。
