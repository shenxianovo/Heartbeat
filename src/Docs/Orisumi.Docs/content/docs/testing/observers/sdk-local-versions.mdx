## 为什么验证 [#why]

草稿决定后端会收到几个版本，冻结决定版本何时不再改写、按什么顺序发送。两种提交策略的区别只在草稿何时冻结。约定见 [Submission · 版本的状态](../../observers/submission/index.mdx#states) 和 [提交策略](../../observers/submission/index.mdx#strategies)。

## 前置条件 [#setup]

SDK 使用独立的 SQLite 文件，后端是记录每次请求、按需返回响应的 HTTP 处理器。

## 操作与预期结果 [#steps]

| 操作 | 预期结果 |
| --- | --- |
| 形成一份 Observation 的草稿，再补全一次 | VersionId 和 `previousVersionId` 不变 |
| 业务代码引用一个实体，之后再补全它 | 被引用的版本已冻结，补全形成新版本，`previousVersionId` 指向被引用的版本 |
| Observation 引用一个仍是草稿的观测内容，然后冻结 Observation | 观测内容先冻结；发送时观测内容排在 Observation 之前 |
| 结束后提交：通知结束前发送一次，通知结束后再发送 | 第一次没有发送这份 Observation；第二次只发送一个版本，内容是最终结果 |
| 及时提交：形成草稿后发送，再补全并发送 | 后端依次收到两个版本，第二个的 `previousVersionId` 指向第一个 |
| 结束后提交：重启 SDK，再通知结束并发送 | 发送的是重启前那份草稿的 VersionId |
| 写入观测草稿：形成 Observation 的草稿，再补全一次 | 观测内容先发送；确认保存后写入草稿，两次写入的 `sequence` 递增，第二次带补全后的内容 |
| 写入观测草稿：重启 SDK 后再补全 | `sequence` 大于重启前的最后一次 |
| 写入观测草稿时后端返回 `409`，`rule` 为 `VERSION-6` | SDK 停止写入这份草稿，本地草稿不变 |
| 通知结束并发送 | 不再写入这份草稿；发送一个版本，内容是最终结果 |

## 测试实现 [#implementation]

以下方法位于 `tests/Orisumi.Integration.Tests/`，对应本页的预期范围：

- 草稿合并保持身份和前驱、结束前不发送该 Observation、重启后沿用草稿身份并发送最终内容：`ObserverSdkTests.DraftMergesFreezeDependenciesAndRecoverInOrder`。
- 引用草稿使其冻结，之后补全形成后继版本：`ObserverSdkTests.ReferencingDraftFreezesItAndCompletionCreatesSuccessor`。
- 冻结 Observation 时先冻结并发送其内容依赖：`ObserverSdkTests.FreezingObservationSendsItsDraftContentFirst`。
- 及时提交的两次发送形成相连版本：`ObserverSdkTests.ImmediateSubmissionSendsTwoLinkedObservationVersions`。
- 未覆盖：观测草稿的写入。SDK 尚未实现这部分。
