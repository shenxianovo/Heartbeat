export const caseId = 'runtime-rejections';

## 为什么验证 [#why]

被拒绝的版本可能被后面的版本引用，继续发送只会得到更多拒绝。Runtime 要把它和依赖它的版本一起交给业务代码，并在业务代码丢弃、改写或采用已保存的版本后继续发送。约定见 [Submission · 被拒绝的版本](../../hosting/submission.mdx#rejections)。

## 前置条件 [#setup]

Runtime 的本地保存使用独立的 SQLite 文件，后端是记录每次请求、按需拒绝某个位置的 HTTP 处理器。待发送的版本依次是 EntitySchema、业务版本和引用业务版本的 InputSet，业务版本被拒绝。

## 操作与预期结果 [#steps]

| 操作 | 预期结果 |
| --- | --- |
| 发送，业务版本因 `VERSION-6` 被拒绝；再发送一次 | EntitySchema 已保存；发送状态给出被拒绝的业务版本和依赖它的 InputSet；第二次没有发出请求 |
| 重启 Runtime | 被拒绝的版本仍在等待处理 |
| 丢弃被拒绝的版本 | InputSet 一起丢弃，其余版本继续发送 |
| 读取实体新的当前版本，基于它改写被拒绝的版本 | 发送改写后的版本和 InputSet |
| 后端的当前版本与被拒绝的版本内容相同，采用已保存的版本 | InputSet 改为引用当前版本后发送；之后引用这个实体时得到当前版本 |
| Runtime 中有两个程序实例，其中一个的版本被拒绝 | 这个实例的发送暂停，另一个实例照常发送 |
| 版本被拒绝后停用这个 Observer，再重启 Runtime | 拒绝状态保留，Observer 保持停用，不为处理拒绝而启动；再次启用后，业务代码收到被拒绝的版本 |
| 用批次中的普通操作改写被拒绝的版本 | Runtime 拒绝这个批次，被拒绝的版本不变 |

## 测试实现 [#implementation]

以下方法位于 `tests/Orisumi.Integration.Tests/`，对应本页的预期范围：

- 拒绝后暂停、恢复拒绝状态，以及采用内容相同的已保存版本并替换依赖：`RuntimeStoreTests.PartialRejectionPausesPersistsAndAdoptsEqualSavedVersion`。
- 丢弃被拒绝版本和依赖，继续其他版本：`RuntimeStoreTests.DiscardingRejectedVersionDiscardsDependentsAndResumesOthers`。
- 读取当前版本后改写被拒绝版本及依赖，再发送：`RuntimeStoreTests.RewritingRejectedVersionUsesReadCurrentVersionAndResendsDependents`。
- 未覆盖：实例之间的隔离、停用期间保留拒绝、普通操作不能改写被拒绝的版本。
