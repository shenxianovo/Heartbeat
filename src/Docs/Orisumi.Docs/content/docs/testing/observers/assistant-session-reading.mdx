## 为什么验证 [#why]

日志在读取时仍在追加，也可能被移动、截短或清理。[助手会话 Observer](../../observers/assistant-sessions/index.mdx#collection) 靠来源身份和读取进度保证每次交互只形成一次，并且不漏掉已写入的记录。

## 前置条件 [#setup]

使用临时的来源目录和独立的 Runtime 数据目录。轮询间隔可以由测试控制，Runtime 可以模拟回执丢失和进程退出。

## 操作与预期结果 [#steps]

| 输入 | 预期结果 |
| --- | --- |
| 来源目录中有大量历史文件，导入期间另一个文件不断追加 | 每一轮都读到追加的记录；历史最终全部导入 |
| 文件末尾是半行，或在一个多字节字符中间截断 | 这一轮不读它；写完后形成一次交互 |
| 一行完整但不是合法的 JSON | 记下诊断，后面的行照常形成交互 |
| 会话文件被复制到另一个路径，或从 `sessions` 移进归档并压缩 | 不形成新的交互 |
| 文件被截短后重新写入，或被同名的新文件替换 | 从头重读；已有的记录对应到原来的交互，新的记录形成新的交互 |
| 两条记录文本相同，`uuid` 不同 | 形成两次交互 |
| 交出批次后、写入进度前程序退出 | 重启后用原来的请求标识重发，得到原来的回执；交互的 EntityId 不变，没有重复 |
| 本地回执丢失 | 同上 |
| 断网期间持续写入 | 交互在本地保存，联网后补发 |
| 来源清理了旧的会话文件 | 已导入的交互保持不变 |
| 用户在 Orisumi 中删除一次交互，之后文件被重读 | 这次交互不再提交，也不以新的身份出现 |
| 一次交互连同原始记录超过批次的上限，或一行超过长度的上限 | 记下诊断，读取进度越过它，后面的记录照常形成交互 |

## 测试实现 [#implementation]

以下方法位于 `tests/Orisumi.Integration.Tests/`：

- 半行和多字节字符截断、无效的行记下一次诊断：`AssistantReadingTests.PartialUtf8WaitsForNewlineAndInvalidCompleteRowsDoNotBlockFollowingRows`。
- 复制、截短、同名替换、文本相同的两条记录，以及来源文件被删除：`AssistantReadingTests.CopyTruncationAndSameSizeReplacementDoNotLoseOrDuplicateOccurrences`。
- 会话移进归档并压缩，不依赖外部的 zstd 命令，解压的文件读完后删除：`AssistantReadingTests.ZstdArchiveReusesIdentitiesAndDoesNotRequireExternalExecutable`。
- 导入历史期间新文件每一轮都被读到，历史最终导完：`AssistantReadingTests.LiveInputIsProcessedWhileHistoryAdvancesInBoundedSlices`。
- Runtime 本地保存之后、回执返回之前出错，重启后重发原批次：`AssistantReadingTests.LostReceiptAndRestartReplayTheExactBatchBeforeAdvancingProgress`。
- 一次交互超过批次的上限、一行超过长度的上限，各记下一次诊断，后面的记录照常形成交互，上限由测试注入：`AssistantReadingTests.InteractionsAndLinesBeyondTheLimitsAreDiagnosedAndSkipped`。
- 删除的交互不再提交，删除会话后跳过它之后的交互，使用真实的 API 和独立的测试数据库：`AssistantSubmissionTests.DeletionDoesNotResurrectAndDeletedSessionsSuppressFutureInteractions`。

未覆盖：断网期间的本地保存和补发，这由 Runtime 负责，见 [Confirmation](../hosting/confirmation.mdx)。
