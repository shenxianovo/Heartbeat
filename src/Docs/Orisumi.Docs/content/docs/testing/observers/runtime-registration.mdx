## 为什么验证 [#why]

其他版本都引用程序实例和 Schema 版本，所以登记必须最先提交。新旧两个版本的 Observer 同时运行时，各自引用自己那一版 Schema，Schema 不会被来回改写。约定见 [Submission · 登记](../../observers/submission/index.mdx#registration)。

## 前置条件 [#setup]

通过 `WebApplicationFactory` 启动 API，连接一个独立的测试数据库，见 [Database](../database.mdx)。Runtime 的本地保存使用独立的 SQLite 文件，经 Runtime 进程运行时使用独立的数据目录；离线时使用总是网络失败的 HTTP 处理器。

## 操作与预期结果 [#steps]

| 操作 | 预期结果 |
| --- | --- |
| 离线时登记程序实例和 EntitySchema，再交来一个业务版本；联网后发送 | 程序实例和 EntitySchema 先于业务版本提交，全部保存 |
| 后端的 EntitySchema 有两个版本，业务代码给出的内容与首版相同 | 业务版本引用首版，版本链仍是两个版本 |
| 业务代码给出的内容与链中每个版本都不同 | Runtime 在当前版本之后形成新的 Schema 版本，业务版本引用它 |
| Runtime 第一次启动一个程序实例，之后重启进程、重启 Runtime | 每次 `init` 交来同一个 EntityId，业务版本的 Observer 都是这个实体 |
| 重启后，程序实例的信息变化，例如程序版本升级 | 形成同一个实体的新版本，之后的版本引用新版本，见 [OBSERVER-4](../../core/model/observer.mdx#observer-4) |

## 测试实现 [#implementation]

以下方法位于 `tests/Orisumi.Integration.Tests/`，对应本页的预期范围：

- 离线登记后按依赖顺序提交程序实例、EntitySchema 和业务版本：`RuntimeStoreTests.OfflineRegistrationPrecedesBusinessVersionsWhenConnectionReturns`。
- 复用已有内容相同的 Schema 版本，版本链不增长：`RuntimeStoreTests.SchemaRegistrationReusesHistoricalContentAndOfflineDraftReferencesAreRemapped`。
- 新的 Schema 内容延长版本链并被业务版本引用：`RuntimeStoreTests.NewSchemaContentExtendsCurrentChainAndBusinessReferencesIt`。
- 重启后程序信息改变，形成并引用后继版本：`RuntimeStoreTests.ChangedInstanceInformationAfterRestartCreatesReferencedSuccessor`。
- 后端离线时，经 Runtime 的登记不等待后端：`RuntimeProtocolTests.HostedRegistrationDoesNotWaitForAnOfflineBackend`。
- Runtime 重启后交来同一个 EntityId：`RuntimeHostingTests.UninstallReinstallKeepsIdentityAndDisabledStateSurvivesRestart`。
