---
title: "Server Hosting"
description: "服务端托管怎样在 API 进程中运行服务端 Observer，保管它的身份，并可靠地提交它形成的版本"
---

服务端托管是 API 进程中的一个模块，运行依据全部已保存数据形成观测的服务端 Observer，例如[应用识别 Observer](../observers/application-identity/index.mdx)。它承担托管方的职责，见 [Overview · 分工](./index.mdx#division)。为什么这样托管，见 [ADR · 服务端托管](../adr/server-observer-hosting.mdx)。

例如后端保存了一个新的本机应用，它的跨设备线索还没有认出。应用识别 Observer 在一轮中把这条线索交给模型，判断它属于哪个应用产品，形成产品的新版本和一份 Observation。服务端托管先把这组版本保存为未决提交，再交给实体服务保存，然后把结果交还业务代码；下一轮读取时，上一轮的结果已经可见。

## 身份 [#identity]

服务端托管为每个程序实例保存一条管理记录，按稳定的标识找到它的 EntityId；第一次运行时生成 EntityId，之后一直沿用，见 [OBSERVER-4](../core/model/observer.mdx#observer-4)。每一轮开始时，它把 EntityId 交给业务代码。

## 轮次 [#rounds]

Observer 的业务代码按轮次工作，服务端托管启动每一轮。同一个程序实例的轮次依次运行，上一轮结束后才开始下一轮。

## 提交 [#submission]

业务代码把一次业务变化作为一组有序的版本交给服务端托管。服务端托管先把它们保存为未决提交，再交给实体服务按顺序逐个保存，然后把结果交还业务代码：全部已保存，或者被拒绝的版本和它的 `rule`。

## 恢复 [#recovery]

保存的结果不确定时，服务端托管用原来的 VersionId 和内容重发未决提交。进程重启后，它先完成未决提交，再开始新的一轮。

## 被拒绝的版本 [#rejections]

之前的版本已保存，未决提交随之结束。业务代码按自己的规则重新读取并处理，例如应用识别 Observer 在产品的新版本被拒绝后重新读取产品。

## 业务状态 [#state]

业务代码需要持久保存的状态由服务端托管保存在 PostgreSQL 中，含义由业务代码定义，例如应用识别的未知线索。

管理记录、未决提交和业务状态都在后端的 PostgreSQL 中，与实体和版本分开保存，见 [Storage · Server Hosting](../storage/server.mdx)。

## 报告 [#reporting]

服务端托管随 API 启动它托管的全部程序实例，所以它们总是启用的。运行和发送两项状态，以及读取、调用外部服务或保存失败的诊断，写入日志。
