title: "Submission"

---

Observer 通过所用语言的 SDK 把批次交给 [Runtime](./runtime.mdx)，Runtime 形成版本，直接提交给后端，设备和服务器上相同。本页按一个程序实例运行的先后，写业务代码要做什么、Runtime 怎样处理。业务代码和托管方的分工见 [Overview · 分工](./index.mdx#division)，消息的格式见 [Protocol · Observer 管道](./protocol.mdx#observer-pipe)。

## 例子 [#example]

[Walkthrough](../start/walkthrough.mdx) 那一天，前台状态 Observer 和 Runtime 这样配合：

| 时刻 | 业务代码 | Runtime |
| --- | --- | --- |
| 启动 | 读到自己的 EntityId，交来程序实例的信息和所需的 EntitySchema | [登记](#registration)，提交到后端 |
| 14:00 | VS Code 在前台，在内存中开始这一段 | — |
| 14:05 | 再次确认，把这一段的结束边界延到 14:05 | — |
| 16:00 | 切到浏览器。交来一个[批次](#batch)：VS Code 的本机应用、前台时段和 Observation | 形成版本，提交到后端，返回它们的 VersionId |

后端为 VS Code 这一段保存一个前台时段的版本和一个 Observation 的版本。16:00 之前，读取方读不到这一段。

## 登记 [#registration]

程序实例的 EntityId 由 Runtime 生成并持久保存，进程启动时交给业务代码，重启、更新和重装后都不变。启动时，业务代码把程序实例的信息和所需的 EntitySchema 交给 Runtime，Runtime 直接提交到后端。SchemaId 是写在业务代码中的常量。程序实例的信息变化时，Runtime 形成它的新版本，见 [OBSERVER-4](../core/model/observer.mdx#observer-4)。

Runtime 用 `GET /entities/{entityId}/versions` 读取 EntitySchema 的版本链。链中已有与业务代码给出的内容相同的 Schema 版本时，直接引用它；没有时，在当前版本之后形成新版本。内容是否相同按 [API · 内容相同](../api/versions.mdx#sameness) 判断。

例如两台设备上运行着新旧两个版本的前台状态 Observer，各自引用自己那一版 Schema，Schema 不会在两台设备之间来回改写。业务版本可以引用同一个 EntitySchema 中较旧的 Schema 版本，见 [ENTITY-3](../core/model/entity.mdx#entity-3)。

## 批次 [#batch]

业务代码把一次业务变化作为一个批次交给 Runtime。批次是一组有序的操作，Runtime 把它形成一次提交，后端全部保存或全部不保存，见 [VERSION-13](../core/model/version.mdx#version-13)。

16:00 的批次形成 VS Code 的本机应用、前台时段和 Observation。它们一起保存，所以记录中不会只有前台时段而没有 Observation。

| 操作 | 作用 |
| --- | --- |
| 写入 | 形成一个实体的新版本 |
| 引用 | 取得一个实体的当前版本，供后面的操作引用 |

- 后面的操作可以引用前面操作的结果。这个结果是一个确定的版本，不随实体之后的版本改变，见 [ENTITY-4](../core/model/entity.mdx#entity-4)。
- 业务代码决定 EntityId、内容和前一版本；Runtime 生成 VersionId，见 [VERSION-12](../core/model/version.mdx#version-12)。
- 实体的当前版本先看同一批次中的写入，再读后端。业务代码知道实体是新的时，指明它没有前一版本，Runtime 不再读后端。
- 更新其他写入方保存的实体时，业务代码先读取后端的当前版本，再指定它为前一版本。

写入的内容中有 `binary` 字段时，业务代码把字节放进同一个批次，例如 16:00 的批次带着 VS Code 的图标。Runtime 核对摘要，先上传内容再提交版本，见 [BINARY-3](../core/model/binary.mdx#binary-3)。

## 结果 [#result]

提交成功后，Runtime 返回批次中每个具名操作得到的 VersionId，这时版本已保存，可以被读取和引用。

提交失败时，整个批次都没有保存，Runtime 把错误交给业务代码：

| 错误 | 含义 |
| --- | --- |
| 被拒绝 | 后端按 Core 的规则拒绝了一个版本，带着它的 `rule` 和说明。通常是业务代码的错误，或者引用的实体已被删除 |
| 不可用 | 后端无法访问，或者 Runtime 还没有接入 |

业务代码按自己的规则决定之后怎么做，例如记一条[采集诊断](../core/model/observer.mdx#observer-8)，再继续处理下一次变化。

请求和响应见 [Protocol · 批次的操作](./protocol.mdx#operations) 和 [API · 提交](../api/writing.mdx#submission)。

## 事实的结束 [#ending]

一段事实何时结束，由业务代码判断。业务代码可以在事实进行中就提交 Observation，随证据形成新版本补全；也可以等事实结束后再提交，见 [TIME-4](../core/rules/time.mdx#time-4)。例子中的前台状态 Observer 等切换应用时才提交。

## 停止 [#stop]

停用前，业务代码按自己的规则结束进行中的事实，提交它们后退出，见 [Runtime · 启动与停止](./runtime.mdx#lifecycle)。进程意外退出时，还没有提交的数据随之丢失。
