Observer 通过所用语言的 SDK 把版本交给 [Runtime](./runtime.mdx)，Runtime 本地保存并发送到后端，设备和服务器上相同。本页按一个程序实例运行的先后，写业务代码要做什么、Runtime 怎样处理。业务代码和托管方的分工见 [Overview · 分工](./index.mdx#division)，消息的格式见 [Protocol · Observer 管道](./protocol.mdx#observer-pipe)。

## 例子 [#example]

前台状态 Observer 采用[结束后提交](#strategies)，并写入[观测预览](#previews)。[Walkthrough](../start/walkthrough.mdx) 那一天，它和 Runtime 这样配合：

| 时刻 | 业务代码 | Runtime |
| --- | --- | --- |
| 启动 | 读到自己的 EntityId，交来程序实例的信息和所需的 EntitySchema | [登记](#registration)，先于其他版本发送 |
| 14:00 | VS Code 在前台。交来一个[批次](#handoff)：引用 VS Code 的本机应用，形成前台时段和 Observation 的草稿 | 本地保存，返回回执。前台时段被 Observation 引用，随即冻结并发送；保存后写入观测预览 |
| 14:05 | 再次确认，把 Observation 的结束边界延到 14:05 | 合并进草稿，再写入一次观测预览 |
| 15:30 | 网络中断 | 观测预览写入失败；之后的补全继续合并进本地的草稿 |
| 16:00 | 切到浏览器。交来一个批次：通知 VS Code 的时段[结束](#updates)，引用浏览器的本机应用，形成浏览器的时段和 Observation 的草稿 | 冻结 VS Code 的 Observation，排进发送；为浏览器形成新的草稿 |
| 16:10 | 网络恢复 | 按冻结的顺序补交，确认后为浏览器写入观测预览 |

后端为 VS Code 这一段保存一个前台时段的版本和一个 Observation 的版本。下面各节依次说明每一步。

## 登记 [#registration]

程序实例的 EntityId 由 Runtime 生成并持久保存，进程启动时交给业务代码，重启、更新和重装后都不变。启动时，业务代码把程序实例的信息和所需的 EntitySchema 交给 Runtime。Runtime 先提交它们，再发送其他版本；网络不可用时，登记内容保存在本地，恢复后最先提交。SchemaId 是写在业务代码中的常量。程序实例的信息变化时，Runtime 形成它的新版本，见 [OBSERVER-4](../core/model/observer.mdx#observer-4)。

Runtime 用 `GET /entities/{entityId}/versions` 读取 EntitySchema 的版本链。链中已有与业务代码给出的内容相同的 Schema 版本时，直接引用它；没有时，在当前版本之后形成新版本。内容是否相同按 [API · 内容相同](../api/versions.mdx#sameness) 判断。

例如两台设备上运行着新旧两个版本的前台状态 Observer，各自引用自己那一版 Schema，Schema 不会在两台设备之间来回改写。业务版本可以引用同一个 EntitySchema 中较旧的 Schema 版本，见 [ENTITY-3](../core/model/entity.mdx#entity-3)。

## 版本的状态 [#states]

14:05 再次确认时，VS Code 的 Observation 还没有发送，延长直接改写它在本地的内容，后端只会收到一个版本。版本一旦被别的版本引用或进入发送，就不再改写，之后的变化形成新版本。

| 状态 | 含义 | Runtime 怎样处理 |
| --- | --- | --- |
| 草稿 | 已本地保存，尚未发送，也没有被其他版本引用 | 可以合并或丢弃 |
| 已冻结 | 已被其他版本引用，或已进入发送 | 按原样发送和重试 |
| 已保存 | 后端已确认保存 | 移出发送队列，保留它的 VersionId 供之后引用 |
| 被拒绝 | 后端拒绝了它，并给出 `rule` | 交给业务代码，见[被拒绝的版本](#rejections) |

- 新版本的 `previousVersionId` 指向这个实体在本地最新的版本，这个版本可以尚未保存。所以版本链在本地就已接好。
- 更新其他写入方保存的实体时，业务代码先读取后端的当前版本，再在草稿中指定它为前一版本，见 [Protocol · 批次的操作](./protocol.mdx#operations)。
- 合并是改写草稿的内容，草稿的 VersionId 和 `previousVersionId` 不变。
- 业务代码引用一个实体时，Runtime 给出这个实体在本地最新的版本，并冻结这个版本。
- 冻结一个版本前，Runtime 先冻结它引用的、仍是草稿的版本。所以冻结的顺序满足依赖顺序，Runtime 按这个顺序发送，见 [VERSION-13](../core/model/version.mdx#version-13)。

## 批次 [#handoff]

业务代码把一次业务变化作为一个批次交给 Runtime。批次是一组有序的操作，Runtime 在这个程序实例的一个本地事务中执行整批：全部成功才提交，任何一个操作失败，整批回滚。

16:00 的批次结束 VS Code 的时段、引用浏览器的本机应用、形成浏览器的时段和 Observation 的草稿。这几步一起提交，所以记录中不会只有旧时段结束、新时段却没有开始。

| 操作 | 作用 |
| --- | --- |
| 草稿 | 写入或补全一个实体的草稿。可以只在实体还没有本地版本时写入 |
| 引用 | 取得一个实体在本地最新的版本并冻结它 |
| 结束 | 通知一个实体的草稿已是最终结果，交给冻结和发送 |

- 后面的操作可以引用前面“引用”操作的结果。这个结果是一个确定的版本，不随实体之后的版本改变，见 [ENTITY-4](../core/model/entity.mdx#entity-4)。
- 业务代码决定 EntityId、内容和何时结束；Runtime 生成 VersionId，接好 `previousVersionId`，冻结被引用的版本，见 [VERSION-12](../core/model/version.mdx#version-12)。
- 已冻结的版本不能被批次改写，补全形成新的草稿。

本地批次只在本机生效。发送到后端时，版本仍按[发送与确认](#delivery)逐个保存。

### 回执 [#receipts]

Runtime 提交事务后返回本地回执，回执中带着批次形成的版本。收到回执，数据就已本地保存；是否已保存到后端，由[发送状态](#status)报告。

每个批次有一个请求标识。回执和数据在同一个事务中保存，所以：

- 用同一个标识重发同样的批次，Runtime 返回原来的回执，不再执行。
- 同一个标识带着不同的内容，Runtime 拒绝。

每个程序实例一次只交一个批次，收到回执后再交下一个。回执丢失时，业务代码用同一个标识重发原来的批次。

没有收到回执的数据不算本地保存。管道断开或磁盘写入失败时，Runtime 向业务代码报告错误；来源中还没交出去的读数能否找回，取决于来源本身。

## 更新与结束 [#updates]

业务代码把新形成或补全的数据交给 Runtime，并明确通知它一段事实何时结束。`endAt` 有值不能当作结束通知，因为它也可能只是最近一次确认的时刻，见 [TIME-4](../core/rules/time.mdx#time-4)。

例子中，14:05 的补全只延长了 VS Code 的 Observation；16:00 切换应用时，业务代码才通知这一段结束。

## 提交策略 [#strategies]

两种策略都在数据形成时本地保存草稿，补全合并进草稿；区别在于草稿何时冻结。同一个 Observer 可以对不同的业务类型选择不同的策略。

| 策略 | 何时冻结 | 后端保存的版本 |
| --- | --- | --- |
| 及时提交 | Runtime 每次发送时冻结当前的草稿；之后的补全形成新的草稿 | 每次发送一个版本，最后一个是最终结果 |
| 结束后提交 | 业务代码通知结束时冻结 | 一个版本，内容是最终结果 |

两种策略中，草稿被其他版本引用时都会提前冻结，见[版本的状态](#states)。之后的补全形成新的草稿，所以后端还会保存被引用的那一版。

例子中的前台状态 Observer 如果改用及时提交，联网期间 Runtime 每次发送都冻结 VS Code 的 Observation 当时的草稿，后端为这一段保存多个版本。断网期间的补全合并进同一份草稿，16:10 补交的是截至 16:00 的最终版本。

发送的时机不影响事实时间。

## 观测预览 [#previews]

Observation 的草稿可以作为观测预览写入后端，供读取方在事实结束前读到，见 [OBSERVATION-11](../core/model/observation.mdx#observation-11)。观测预览的内容就是草稿的内容，不带 VersionId。草稿是权威，观测预览丢失后由 Runtime 再写一次。业务代码按业务类型决定是否写入观测预览，两种提交策略都可以写入。

例子中，Runtime 在前台时段保存后，用 `PUT /observation-previews/{entityId}` 把 VS Code 的 Observation 的草稿写成观测预览；14:05 草稿合并了新的结束边界，Runtime 再写入一次。16:00 业务代码通知结束，Runtime 停止写入这份观测预览，冻结草稿并发送；后端保存这个版本后，移除对应的观测预览。

- 观测预览引用的版本必须已保存，它的 `previousVersionId` 也必须已保存。所以写入观测预览的 Observation，它的观测内容在草稿形成时就冻结并发送。
- 每次写入发送草稿的完整内容，以及 Runtime 为这份观测预览维护的递增 `sequence`。`sequence` 本地保存，重启后继续递增。写入的频率由 Runtime 决定。
- 写入失败时，Runtime 不重发旧的内容，下一次写入发送草稿最新的内容。后端重启或观测预览过期后，下一次写入恢复它。
- 写入因 [VERSION-6](../core/model/version.mdx#version-6) 被拒绝时，后端的当前版本已经不是草稿所基于的版本，Runtime 停止写入这份观测预览。

请求和响应见 [API · 观测预览](../api/previews.mdx)。

## 发送与确认 [#delivery]

已冻结且依赖都已满足的版本按冻结的顺序分批发送，一批就是一次 `POST /versions`，大小在请求体的上限之内。发送失败或响应不确定时，版本留在本地，等网络恢复或程序重启后继续发送。请求和响应见 [API · 提交](../api/writing.mdx#submission)。

### 确认 [#confirmation]

Runtime 按响应确认版本，不需要读回。

| 响应 | Runtime 的处理 |
| --- | --- |
| `200` | 这一批全部确认为已保存 |
| `400` 或 `409`，带 `index` | 位置在 `index` 之前的版本确认为已保存；`index` 处的版本被拒绝；之后的版本确定没有保存，可以由业务代码改写 |
| `400`，不带 `index` | 请求不符合契约，是 Runtime 的错误：停止发送，报告给业务代码 |
| `413` | 拆成更小的批，重新发送 |
| `5xx` 或网络失败 | 稍后原样重发 |

保存成功不代表这段事实已经结束，Runtime 继续接收更新和结束通知。状态码和错误字段见 [API · 错误格式](../api/errors.mdx)。

### 重试 [#retry]

重试沿用原来的 VersionId，内容、引用和事实时间保持原样。后端已保存但响应丢失时，Runtime 原样重发，后端把已保存的版本直接确认，返回首次保存时的 `recordedAt`，见 [VERSION-7](../core/model/version.mdx#version-7)。

## 最终结果 [#outcome]

回执只说明本地保存。业务代码需要知道一个批次是否已保存到后端时，用批次的标识读取它的最终结果：已保存、仍在等待、被拒绝，或者已被修复操作丢弃。读取可以等待一段时间，结果确定时立即返回。

例如应用识别 Observer 把 InputSet、产品的新版本和 Observation 作为一个批次交给 Runtime，三个草稿都在批次中结束，随即冻结并发送。它等到结果为已保存，再处理下一条线索，这时读取产品目录一定能读到这个版本。

- 结果按批次计算，与其他批次的发送无关。
- 回执永久保留，所以进程重启后仍可以读取以前批次的结果。
- 批次中有尚未结束的草稿时，结果一直是等待，所以需要等待的业务在同一个批次中结束全部草稿。
- 结果为被拒绝时，业务代码按[被拒绝的版本](#rejections)处理；丢弃之后，结果变为已丢弃。
- 网络中断时结果保持等待，业务代码可以继续等，也可以收到 `stop` 后退出，下次启动时再读取。

请求的格式见 [Protocol · 最终结果](./protocol.mdx#outcome)。

## 被拒绝的版本 [#rejections]

Runtime 把被拒绝的版本、它的 `rule`，以及依赖它的待发送版本交给业务代码，处理完之前暂停这个程序实例的发送，其他程序实例照常发送。程序实例停用或卸载时，被拒绝的版本保留，等它再次运行时交给业务代码。业务代码可以：

- 丢弃这个版本，以及依赖它的版本；
- 读取实体新的当前版本，基于它改写这个版本，以及依赖它的版本；
- 因 [VERSION-6](../core/model/version.mdx#version-6) 被拒绝、而后端的当前版本与被拒绝的版本内容相同时，采用已保存的版本：Runtime 把待发送版本中指向被拒绝版本的引用改为指向当前版本，再继续发送。

例如同一台设备上的两个程序实例共用本机应用的登记文件，同时为同一个应用提交首版，后提交的一方采用先保存的首版。

`400` 带 `rule` 的拒绝说明版本本身违反 Core 规则，通常是业务代码的错误，需要修正后再处理。

这些处理通过 Runtime 的修复操作完成，见 [Protocol · 修复](./protocol.mdx#repair)。批次中的普通操作不能改写被拒绝或已冻结的版本。

## 发送状态 [#status]

Runtime 向业务代码报告待发送的数量、已确认的数据和被拒绝的原因，业务代码据此区分仍在本地、已保存和被拒绝的数据。它也把每个程序实例的发送状态报告给客户端，见 [Runtime · 状态](./runtime.mdx#states)。

## 停止与恢复 [#recovery]

停用前，业务代码按自己的规则通知进行中的事实结束，等收到回执后退出，见 [Runtime · 启动与停止](./runtime.mdx#lifecycle)。

程序实例的进程意外退出时，它的草稿保留在本地，Runtime 不替业务代码结束它们，也不再为它写入观测预览。Runtime 启动时恢复草稿、待发送的版本和待处理的被拒绝版本，已冻结的版本照常发送。

进程重新启动后，业务代码先读取本地已提交的状态，再按业务规则处理遗留的草稿，例如前台时段结束于最后一次确认。没有收到回执的批次按业务规则重新形成，不用新的标识重放。
