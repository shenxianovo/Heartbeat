每个 Runtime 在后端有一条托管方登记，它托管的每个程序实例有一条实例登记。客户端经后端查看和修改这些登记，Runtime 执行它们。本页写 Runtime 一侧的做法和登记的含义；HTTP 接口见 [API · Management](../api/management.mdx)，表见 [Storage · Management](../storage/management.mdx)，理由见 [ADR · Observer 的统一管理](../adr/observer-management.mdx)。

例如用户的 Mac 断网时，用户在菜单栏停用前台状态 Observer。Runtime 先把停用和一项待同步的修改写进安装登记，再停止进程。网络恢复后，Runtime 把这项修改发给后端；后端接受后，Web 控制台显示前台状态 Observer 已停用，Runtime 报告的状态是已停止。

## 身份 [#identities]

| 身份 | 谁分配 | 用途 |
| --- | --- | --- |
| `hostId` | 后端，配对时 | 一个 Runtime，也就是一个数据目录 |
| 程序实例的 EntityId | Runtime，第一次安装时 | 程序实例在 Core 和管理登记中的身份，见 [OBSERVER-4](../core/model/observer.mdx#observer-4) |
| 登记标识 `instanceKey` | Runtime | 托管方内找到这个实例的标识。一个 Runtime 中每个安装包最多一个实例，所以登记标识就是安装包的 `id` |
| 安装包的 `id` | 发布方 | 安装和更新时找到同一个包，见 [Packages · 清单](./packages.mdx#manifest) |

三者分开：同一个安装包在 Mac 和服务器上各有一个实例；删除实例后再安装，登记标识相同，EntityId 和实例目录是新的。

## 接入 [#pairing]

Runtime 用一次性的配对码接入后端。用户在管理入口签发配对码，再把它交给 Runtime：

- 设备上，用户在客户端中输入配对码，客户端经 [`pair`](./protocol.mdx#management) 交给 Runtime。
- 服务器上，配对码作为 `--pairing-code` 交给以服务方式启动的 Runtime，见 [Server · 接入](./server.mdx#pairing)。

Runtime 调用 `POST /runtime/pair`，把得到的 `hostId`、凭证和 API 地址写进数据目录的 `host.json`，文件只有 Runtime 的用户可以读写。之后它的每个请求都带着这份凭证。

还没有接入的 Runtime 照常运行 Observer、本地保存和读取本地数据，不发送版本，也不登记实例；发送状态的 `error` 说明尚未接入。接入后，它登记全部实例，再开始发送。

## 配置 [#configuration]

每个实例有两项配置：启用 `enabled` 和设置 `settings`。Runtime 在安装登记中为每个实例保存：

| 内容 | 含义 |
| --- | --- |
| 生效的配置 | Runtime 正在执行的 `enabled` 和 `settings` |
| 后端的配置 | 最近一次从后端收到的配置和它的 `revision` |
| 待同步的修改 | 还没被后端接受的本机修改，每项带一个序号和改动的字段 |
| 下一个序号 | 这个实例下一项本机修改的序号，从 1 开始，只增不减 |

生效的配置等于后端的配置，再按序号依次叠加待同步的修改。安装登记整个替换写入，所以这几项总是一起保存。

### 本机修改 [#local-changes]

用户在本机客户端中启用、停用或修改设置时：

1. Runtime 分配下一个序号，把修改加入待同步的修改，算出新的生效配置，写入安装登记。
2. 按新的生效配置启动或停止进程，或者重启进程交给它新的设置。
3. 已接入时，把修改交给同步。

后端不可用不影响前两步。一项修改只携带改动的字段；`settings` 是整个对象。

### 同步 [#sync]

Runtime 为每个实例按顺序同步，同一时刻只有一个请求：

1. 实例还没有登记时，用 `PUT /runtime/instances/{entityId}` 登记，带着生效的配置和它已经包含的最大序号。
2. 依次发送待同步的修改，一次一项，等到响应后再发下一项。响应丢失或请求失败时，用同一个序号和同样的内容重发。
3. 每个响应都带着后端当前的配置、`revision` 和 `lastLocalSequence`。Runtime 移除序号不大于 `lastLocalSequence` 的待同步修改；`revision` 比已有的大时，替换后端的配置。然后重新算出生效的配置，变化时执行它。

后端返回 `sequence_gap` 时，Runtime 从 `lastLocalSequence + 1` 继续发送；它没有这个序号的修改时，在状态中报告错误，停止这个实例的同步。

### 收到后端的配置 [#remote]

Runtime 通过[长轮询](../api/management.mdx#poll)收到其他客户端的修改。它按同步第 3 步合并：替换后端的配置，叠加仍待同步的修改。后端的配置不成为待同步的修改，所以不会被再上传一次；比已有 `revision` 小的配置是旧的响应，被忽略。

### 合并 [#merge]

两个字段各自合并，同一字段以后端最后接受的修改为准。

| 情况 | 结果 |
| --- | --- |
| Mac 离线时停用，手机在线时启用，Mac 联网后提交停用 | 停用：Mac 的修改最后被接受 |
| Mac 修改启用，手机修改设置 | 两项都保留 |
| Mac 和手机修改了设置中的不同项 | 后接受的整个设置对象生效 |
| 同步期间用户又在本机修改 | 新的修改排在后面，旧请求的响应只移除它自己的序号 |

### 安装维护与配置 [#maintenance]

安装和重新安装把 `enabled` 设为 `true`，作为一项本机修改，和用户手动启用走同一条路。更新和卸载不改变配置。远程发起的安装由 Runtime 执行，同样形成一项本机修改。

## 状态报告 [#status]

Runtime 用 `PUT /runtime/instances/{entityId}/status` 报告每个实例的状态，后端把收到的时刻记为 `reportedAt`：

| 字段 | 含义 |
| --- | --- |
| `packageId`、`version`、`installed` | 安装包和已安装的版本 |
| `enabled` | 正在执行的启用配置 |
| `appliedRevision` | 已经合并的后端配置的 `revision` |
| `pendingChanges` | 待同步的修改数 |
| `state`、`error`、`diagnostic` | 进程的状态、故障原因和最近一条采集诊断，见 [Runtime · 状态](./runtime.mdx#states) |
| `delivery` | 发送状态，与 [Protocol · 管理](./protocol.mdx#management) 中 `list` 的 `delivery` 相同 |

- 状态变化时报告，同一个实例 5 秒内最多一次；连接期间每 60 秒至少报告一次。
- 接入后、长轮询第一次返回后，报告全部实例。

客户端把四项信息分开显示：

| 信息 | 来源 | 例子 |
| --- | --- | --- |
| 配置 | 实例登记的 `enabled`、`settings` | 已请求停用 |
| 同步 | `revision` 与 `appliedRevision` 是否相同 | 等待设备同步 |
| 运行 | `status.state` | 已停止 |
| 连接 | 托管方的 `connected` | 设备离线，上次报告于 18 分钟前 |

托管方没有连接时，`status` 只说明 `reportedAt` 那一刻的情况，客户端把运行状态显示为未知，并写出报告的时刻。还没有报告的实例显示为未知。

## 在线操作 [#operations]

安装、更新、卸载、重试和读取可安装的包，由管理入口发起，经长轮询交给 Runtime：

1. Runtime 收到操作后，按本机客户端发起时的同样规则执行，见 [Clients · Device Clients](../clients/device.mdx)。
2. 执行结束后，用 `POST /runtime/operations/{operationId}/result` 报告结果。报告失败时重试，直到后端返回 `204` 或 `404`。

Runtime 不保存收到的操作。执行中退出时，这个操作不再继续，管理入口看到的是结果未确认。

## 删除实例 [#removal]

管理入口删除一个实例，或者删除它的 Core 实体时，后端在一个事务中把实例登记标记为已删除，并删除它的实体，见 [API · 删除实例](../api/management.mdx#removal)。Runtime 在长轮询或同步的响应中看到 `removed` 为 `true`，或者登记返回 `instance_removed` 时：

1. 停止这个实例的进程，在安装登记中标记它已删除，丢弃它待同步的修改。
2. 之后不再启动它，也不再为它写入观测预览。
3. 报告一次状态，`state` 为 `stopped`。客户端据此把“已删除，等待停止”显示为“已停止”。

离线的 Runtime 在下次连接时执行这些步骤，在那之前程序实例可能仍在运行。

待发送的版本照常发送，按 Core 的规则处理：这个实例自己的版本、以及引用它的 Observation 会被拒绝。实例不再运行，被拒绝的版本留在发送状态中，`rejection` 说明原因，Runtime 不为它新建身份。读取时，Runtime 按[读取](./protocol.mdx#reading)的规则，不显示后端已删除的实体的本地副本。

安装一个实例已删除的包时，Runtime 要求显式新建实例：本机客户端的 `install` 和远程的 `install` 都要带 `newInstance`，否则返回 `conflict`。新实例得到新的 EntityId 和实例目录，旧实例目录保留到它的版本发送完。

## 移除托管方 [#revocation]

后端返回 `credential_revoked` 时，Runtime 停止发送、登记、同步和长轮询，在 `list` 中报告连接已撤销，不自动重试。Observer 照常运行，本地数据保留。

用户在管理入口为这个托管方签发重新接入的配对码，交给 Runtime 后，Runtime 用原来的 `hostId` 接入，得到新的凭证，然后继续同步和发送。没有发出去的版本仍在本地，重新接入后照常发送。

## 每个部署一个实例 [#singleton]

清单中 `scope` 为 `deployment` 的安装包，在一个部署中最多有一个未删除的实例，例如[应用识别 Observer](../observers/application-identity/index.mdx#instance)。

- Runtime 登记这样的实例时带上 `scope`，后端发现其他托管方已有它的实例，返回 `deployment_singleton`。
- 后端接受登记之前，Runtime 不启动这样的实例；`list` 中它的 `state` 为 `stopped`，`error` 说明等待登记。登记被拒绝时，`state` 为 `failed`，用户可以卸载它。
