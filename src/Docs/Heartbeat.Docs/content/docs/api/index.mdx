Heartbeat API 保存和读取实体。实体模型见 [Heartbeat Core](../core/index.mdx)。请求字段与响应结构以各接口页为准。

Observation、EntitySchema 和 Observer 都是实体。各保存入口采用相同的实体保存语义。路径声明模型类别。后端按类别分表保存，调用方无需在 PUT 请求体中填写 `category`。所有实体使用同一个按标识读取入口。

## 服务入口

NGINX 使用 `/api` 作为 API 服务前缀。OpenAPI 的 `servers` 声明相对地址 `/api`，请求地址由服务前缀和接口路径组成。例如，`GET /entities/{id}` 对外为 `GET /api/entities/{id}`。

8080 提供业务/API 入口。3000 提供文档入口，并转发 `/api/entities/…` 请求。接口页的调试面板（Playground）使用文档站的同源入口。

## 实体提交

| 路径 | 提交模型 | 接口参考 |
| --- | --- | --- |
| `PUT /entities/observations/{id}` | [Observation](../core/model/observations/observation.mdx) | [保存观测](/api/saveObservation) |
| `PUT /entities/observers/{id}` | [Observer](../core/model/observations/observer.mdx) | [保存观测主体](/api/saveObserver) |
| `PUT /entities/schemas/{id}` | [EntitySchema](../core/model/observations/schema.mdx) | [保存实体定义](/api/saveEntitySchema) |
| `PUT /entities/{resourceName}/{id}` | 资源名绑定的业务实体模型 | [保存业务实体](/api/saveBusinessEntity) |

### 资源登记

保存 EntitySchema 时，`properties.resourceName` 登记业务资源名。例如，`example-records` 登记后的保存入口为 `PUT /entities/example-records/{id}`。每个资源名绑定一个 SchemaId。

`name` 是显示名称，可以使用中文；`resourceName` 是接口资源名，默认数据库表名由后端按[业务表命名规则](../storage/index.mdx#业务表命名)生成。资源名只使用小写英文字母、数字和连字符，以字母开头，例如 `local-applications`、`foreground-application-periods`。资源名全局唯一，且不能使用 `schemas`、`observers`、`observations`。插件可以自行加前缀，例如 `acme-local-applications`；系统不另设命名空间。

首次提交时，后端将定义保存、资源登记和首次建表作为一次完整操作。全部成功后才返回成功；任一步骤失败时一起回滚，不留下部分结果。重复提交相同请求不新增定义、资源绑定或业务表。资源名已被其他 SchemaId 占用时返回 `409`。

业务保存入口根据资源名找到 EntitySchema，按定义校验请求，再通过存储映射保存到对应业务表。资源名未登记时，后端返回 `404 Not Found`，不创建实体内容、统一实体索引或业务表。后端使用公共逻辑处理已登记资源。业务实体继续使用 `GET /entities/{id}` 读取。

### 输入

路径声明模型类别。路径中的 `id` 必须是创建方生成的 UUIDv7。

请求体外层只能包含 `references` 和 `properties`，且两者必须出现。两个字段的值都必须是 JSON 对象。`references` 保存具名实体引用，`properties` 保存其他业务属性。没有引用时，`references` 必须为 `{}`。引用字段不得在 `properties` 中重复。实体标识由路径提供。`properties` 不得包含实体自身的 `id`。字段与完整 JSON 示例见各接口页。

请求体上限为 10 MiB（10,485,760 字节），按完整请求体的字节数计算。超过上限时，NGINX 或后端返回 `413`。

JSON 字段名与字符串值必须是有效的 Unicode。如果内容包含未配对的代理码点，后端返回 `400`。字段名区分大小写。固定模型与业务实体都拒绝未声明字段，包括嵌套对象成员；校验失败返回 `400`。字段定义本身也拒绝未声明配置，`fields` 仅用于 `object`，`items` 仅用于 `array`。

Observation 的 `references` 必须包含 `observerId`、`contentId` 和 `schemaId`。Observation 的 `properties` 必须包含时间边界和事实时区。未知值必须为 `null`。

Observer 和 EntitySchema 的 `references` 必须为 `{}`。`properties.name` 必须出现，且不得为 `null`。EntitySchema 还必须提供 `properties.resourceName` 与 `properties.fields`。

### 保存行为

后端组合路径中的 `id`、具名引用和其他业务属性，并校验实体：

- 实体不存在时，后端创建实体并登记统一索引。
- 实体已存在且模型类别与保存路径一致时，后端替换内容。业务实体还必须属于路径资源名绑定的 Schema。
- 实体已存在且模型类别与保存路径不一致时，后端返回 `409 Conflict`，并保留原内容。
- 重复提交相同请求时，保存结果不变，后端不新增实体。

单个实体的索引和内容在同一事务中保存。如果保存失败，后端回滚事务。已有内容保持不变，首次保存不留下索引。

同一个 EntitySchema 标识的 `resourceName` 在首次登记后固定，后续提交必须保持原值。尝试修改已登记的资源名时，后端返回 `409 Conflict`，并保留原定义与资源绑定。修改显示名称 `name` 不改变资源名或接口地址。

同一个 EntitySchema 标识的模型结构、约束和业务含义固定。如果模型变化，创建方使用新 ID。修改已登记的 `fields` 返回 `409`，并保留原定义、绑定和业务表；对象键顺序不影响比较。如果仅修改名称或说明文字，且模型含义不变，可以保留原 ID。规则见[定义更新](../core/model/observations/schema.mdx#定义更新)。

### 成功响应

| 条件 | 状态码 | 响应体 |
| --- | --- | --- |
| 首次创建实体 | `201 Created` | 无 |
| 替换已有实体或重复提交 | `204 No Content` | 无 |

### 错误响应

| 条件 | 状态码 |
| --- | --- |
| 请求不符合契约，例如标识无效、JSON 无效、缺少必填字段、包含额外根字段或 `references` 与 `properties` 包含同名字段 | `400 Bad Request` |
| 内容超出 PostgreSQL JSON 或文本表示范围 | `400 Bad Request` |
| 业务保存入口中的资源名未登记 | `404 Not Found` |
| 保存路径声明的模型类别与已有实体不一致，或业务实体所属 Schema 与资源绑定不一致 | `409 Conflict` |
| 登记的资源名已被其他 SchemaId 占用，或尝试修改已登记的资源名、字段定义 | `409 Conflict` |
| 请求体超过 10 MiB | `413 Content Too Large` |
| 后端因未预期错误而保存失败 | `500 Internal Server Error` |

错误响应使用[错误格式](#错误格式)。

## 按标识读取

### 输入

[读取实体](/api/getEntity)使用 `GET /entities/{id}`。`id` 必须是实体的 UUIDv7。后端通过统一索引定位内容所在的表。

### 成功响应

读取成功时，后端返回 `200 OK` 和 JSON 响应体。所有类别使用同一响应结构。

| 字段 | 内容 |
| --- | --- |
| `category` | 实体的模型类别 |
| `references` | JSON 对象；键是业务定义的引用名称，非空值是目标实体的 UUIDv7；字段定义允许空值时可以为 `null`；没有引用字段时为 `{}` |
| `properties` | 其他业务属性，不重复引用字段 |

`category` 使用以下取值：

| 取值 | 模型 |
| --- | --- |
| `entity` | 通用领域实体，包含观测内容和具体关系实体 |
| `observation` | Observation |
| `observer` | Observer |
| `entity_schema` | EntitySchema |

`references` 与 `properties` 的划分与对应保存请求一致。实体标识由请求路径提供。Observation 的已知时间边界返回 UTC 时间。

### 错误响应

| 条件 | 状态码 |
| --- | --- |
| `id` 不是有效的 UUIDv7 | `400 Bad Request` |
| 实体不存在 | `404 Not Found` |
| 后端因未预期错误而读取失败 | `500 Internal Server Error` |

错误响应使用[错误格式](#错误格式)。

## 字段表示

实体引用的统一枚举契约见 [Core](../core/model/contracts/entity.mdx#约定)。具名引用的 HTTP 表示见[读取实体](/api/getEntity)。业务定义引用名称。通用遍历使用引用对象中的目标标识。

OpenAPI 的 `components/schemas` 定义属性类型和必填项。

| OpenAPI Schema | 内容 |
| --- | --- |
| `Observation` | 观测提交格式，引用与事实时间分开放置 |
| `Observer` | 观测主体提交格式，包含空引用对象和名称 |
| `EntitySchema` | 实体定义提交格式，包含显示名称、资源名和业务字段定义 |
| `BusinessEntity` | 按已登记资源提交的业务实体，按对应 EntitySchema 校验 |
| `EntityResponse` | 模型类别、具名引用和其他业务属性 |

未知时间或时区必须写为 `null`。

API 字段使用 `camelCase`，C# 属性使用 `PascalCase`，数据库列名使用 `snake_case`。例如，`observerId`、`ObserverId` 和 `observer_id` 表示同一属性。

业务实体的字段由 EntitySchema 定义。实体定义直接通过 `properties.name` 声明名称，通过 `properties.resourceName` 登记业务资源名，通过 `properties.fields` 声明业务字段。`fields` 以业务字段名映射字段定义。普通属性和实体引用都在 `fields` 中声明，通过 `type` 区分。`type: "reference"` 表示实体引用，其值在业务实体的提交和读取结构中放入 `references`；普通属性值放入 `properties`。独立业务实体和观测内容都可以拥有自己的 EntitySchema。

EntitySchema 只允许顶层字段使用 `reference`。对象成员和数组元素不允许使用 `reference`，这一规则适用于任意嵌套层级。`references` 按引用名称保存目标实体标识，不使用嵌套对象或数组表示引用。

对象字段使用 `fields` 声明内部成员。成员沿用字段定义格式，必须明确提供 `type`、`required` 和 `nullable`。示例见 [EntitySchema 对象成员](../core/model/observations/schema.mdx#对象成员)。

数组字段使用 `items` 定义每个元素。元素定义必须明确提供 `type` 和 `nullable`，不使用 `required`。对象元素通过 `items.fields` 声明成员。数组字段必填不表示数组至少包含一个元素。示例见 [EntitySchema 数组元素](../core/model/observations/schema.mdx#数组元素)。

业务字段的省略与显式 `null` 分别保存，读取时保留这个区别。存储系统列 `__omitted_fields` 由后端生成，不作为业务顶层字段提交，也不出现在响应中。存储规则见[字段省略与空值](../storage/index.mdx#字段省略与空值)。

字段类型为 `string`、`boolean`、`integer`、`number`、`reference`、`object` 和 `array`。类型含义与值的例子见 [EntitySchema](../core/model/observations/schema.mdx#字段类型)。

每个字段定义必须明确提供 `type`、`required` 和 `nullable`，三项配置没有隐含默认值。字段定义通过 `required` 声明字段是否必须出现，通过 `nullable` 声明字段值是否允许为 `null`。两项约束分别判断。例如，`required: true` 与 `nullable: true` 表示必须提交字段，但字段值可以为 `null`。

实体标识和非空实体引用使用 UUIDv7 字符串，定义见 [EntityId](../core/model/contracts/entity.mdx#entityid)。

## 实体引用约束

后端校验所有非空实体引用的 UUIDv7 格式，包括业务引用和 Observation 的 `observerId`、`contentId`、`schemaId`。业务引用不限制目标模型。后端允许引用尚未入库的实体。被引用实体入库后，后端即可按引用标识读取。Observation 无须修改。

## 时间表示与职责

`startAt` 和 `endAt` 的边界含义见 [ITimed](../core/model/contracts/timed.mdx)。UTC 是协调世界时（Coordinated Universal Time）。

| 组件 | 职责 |
| --- | --- |
| 采集程序 | 提供事实时间，提交以 `Z` 结尾或带明确 UTC 偏移的字符串 |
| 后端 | 转换为 UTC，以微秒精度保存和读取，读取时返回以 `Z` 结尾的字符串 |
| 前端 | 按浏览器或系统时区显示时间 |

例如，提交 `2026-10-06T09:00:00+08:00`，读取时返回 `2026-10-06T01:00:00Z`。两者表示同一时刻。

Observation 的 `timeZone` 保存事实所属的 IANA 时区 ID，例如 `Asia/Shanghai`。后端使用时间字符串中的 UTC 偏移转换时刻。

如果 `timeZone` 非空，运行环境必须能将其解析为 IANA 时区 ID。如果两个时间边界都已知，`startAt` 必须早于或等于 `endAt`。如果校验失败，后端返回 `400`。

## 错误格式

错误响应使用 `Content-Type: application/problem+json`，结构遵循 [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)。

| 必填字段 | 内容 |
| --- | --- |
| `type` | 固定为 `about:blank` |
| `title` | HTTP 状态的简短名称 |
| `status` | 实际 HTTP 响应的状态码 |
| `detail` | 本次错误的具体说明 |

调用方按状态码处理错误。`detail` 供人阅读。

## 后端路由

保存新实体时，后端按路径声明的模型类别选择存储表。业务保存入口根据资源名找到 SchemaId，再通过存储映射选择业务表。保存已有实体时，后端通过统一索引定位存储，并校验模型类别。

每个业务 SchemaId 对应一张业务表。后端根据 EntitySchema 的模型声明创建业务表，并提供通用存取。Core 不依赖数据库列类型或建表语句。表名属于存储配置。职责见 [ADR 0011](../adr/0011-entity-schema-driven-storage.mdx)，保存与读取协议见 [ADR 0003](../adr/0003-entity-submission-entry-points.mdx)。

## 契约来源

`content/docs/api/openapi.json` 是 HTTP 契约的权威来源。维护者将用户在讨论中确认的结果写入对应接口。后端、客户端、测试和接口说明文档按契约同步，不反向修改契约。权威来源见 [ADR 0001](../adr/0001-documentation-source-of-truth.mdx)。

Fumadocs 根据契约文件提供 `/api/<operationId>` 接口页。接口页的复制和导出提供 OpenAPI JSON，编辑链接指向契约源文件。
