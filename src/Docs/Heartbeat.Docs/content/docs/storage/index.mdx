Heartbeat Storage 定义实体的索引、内容存储和数据库约定。实体结构见 [Heartbeat Core](../core/index.mdx)，读写协议见 [Heartbeat API](../api/index.mdx)。

## 数据库

实体索引和内容使用 PostgreSQL。AppHost 固定镜像为 `postgres:18.6-alpine`。服务和测试使用同一版本。

数据库通过 Docker 运行，API 使用本机进程。数据库健康后，Aspire 运行 Entity Framework Core（EF Core）迁移程序。迁移成功后，Aspire 启动 API。PostgreSQL 初始化时创建统计扩展，职责见 [ADR 0005](../adr/0005-backend-project-organization.mdx#本地启动)。

### 后端数据访问

EF Core 管理固定表映射和 Initial migration。Npgsql 访问 PostgreSQL；后端使用参数化 SQL 创建和读写业务表，表名与列名按标识符规则引用。

`global.json` 固定 .NET SDK 为 `10.0.401`，允许同功能版本的维护更新。运行时镜像和 EF Core 使用 `10.0.12`，配置见后端 Dockerfile 和 `Directory.Packages.props`。

重写期间直接修改 Initial migration 和模型快照。

迁移和模型快照位于 Infrastructure 的 `Database/Migrations/`。仓库的 EF 工具以 Api 为启动项目生成文件。Api 引用 `Microsoft.EntityFrameworkCore.Design`，版本集中管理，且设置 `PrivateAssets="all"`。

Api 从 `ConnectionStrings:Heartbeat` 读取连接字符串。如果配置缺失或为空，Api 启动失败。环境变量对应 `ConnectionStrings__Heartbeat`。

Infrastructure 通过 `AddHeartbeatInfrastructure(connectionString)` 注册 Npgsql 和 `HeartbeatDbContext`。数据库上下文使用 `Scoped` 生命周期。

`NpgsqlDataSource` 使用单例生命周期，由应用服务容器创建和释放。各请求的数据库上下文共用连接池，宿主释放时关闭连接池。

### 测试数据库

测试数据库使用与服务相同的 PostgreSQL 版本和 EF Core 迁移。实例生命周期、用例隔离和公共工具见 [Heartbeat Testing](../testing/database.mdx)。

### 程序映射

`observations`、`observers`、`entity_schemas` 直接映射 `Heartbeat.Core` 中的 `Observation`、`Observer`、`EntitySchema`。

统一索引 `entities` 使用 Infrastructure 中的 `EntityIndexRow`。数据库上下文 `HeartbeatDbContext` 通过构造参数接收 `DbContextOptions<HeartbeatDbContext>`，数据库配置由外部提供。

| DbSet 属性 | C# 类型 | 表 |
| --- | --- | --- |
| `Entities` | `EntityIndexRow` | `entities` |
| `Observations` | `Observation` | `observations` |
| `Observers` | `Observer` | `observers` |
| `EntitySchemas` | `EntitySchema` | `entity_schemas` |

每张固定表使用独立的 `IEntityTypeConfiguration<T>` 配置类，位于 `Database/Configurations/`。`HeartbeatDbContext` 显式注册这些配置。业务表在登记 EntitySchema 时创建，不使用预先生成的 EF 实体映射。Core 不依赖数据库配置。

`Database/Converters/EntityIdValueConverter.cs` 在写入时将 `EntityId` 转换为 `Guid`，在读取时将 `Guid` 转换为 `EntityId`。标识保持不变。`HeartbeatDbContext.ConfigureConventions` 将转换器应用于所有 `EntityId` 属性，包括观测的三个引用。

### 统计与诊断

数据库使用以下统计与诊断配置：

| 项目 | 配置 | 用途 |
| --- | --- | --- |
| `pg_stat_statements` | 启用扩展，`pg_stat_statements.track=top` | 按查询结构汇总客户端 SQL 的调用次数、执行耗时和块读写 |
| `track_io_timing` | `on` | 记录数据文件 I/O 等待耗时 |
| `track_wal_io_timing` | `on` | 记录 WAL I/O 等待耗时，包括同步落盘 |
| `track_activities` | 保留默认 `on` | 记录当前会话活动 |
| `track_counts` | 保留默认 `on` | 采集数据库、表和索引的累计统计 |
| `log_min_duration_statement` | `500ms` | 记录耗时达到阈值的 SQL |
| `log_lock_waits` | `on` | 记录超过 `deadlock_timeout` 的锁等待 |
| `deadlock_timeout` | 保留默认 `1s` | 控制死锁检查和锁等待日志的触发时间 |
| `pg_stat_statements.track_planning` | 保留默认 `off` | 默认不采集规划统计 |
| `auto_explain` | 暂不开启 | 需要执行计划解释慢查询时启用 |

`pg_stat_statements` 必须由 `shared_preload_libraries` 预加载。仓库已在 AppHost 中配置预加载，并在初始化 SQL 中创建扩展。

在其他数据库启用扩展时，需要重启数据库，现有连接会中断。

1. 将 `pg_stat_statements` 加入 `shared_preload_libraries`。
2. 重启 PostgreSQL。
3. 在目标数据库执行：

   ```sql
   CREATE EXTENSION pg_stat_statements;
   ```

4. 验证：`pg_extension` 中存在 `extname = 'pg_stat_statements'` 的记录。

扩展配置见 [pg_stat_statements](https://www.postgresql.org/docs/current/pgstatstatements.html)。慢 SQL 和锁等待日志见[日志配置](https://www.postgresql.org/docs/current/runtime-config-logging.html)，锁等待阈值见[锁配置](https://www.postgresql.org/docs/current/runtime-config-locks.html)。

可以直接查询以下内置视图：

| 视图 | 用途 |
| --- | --- |
| `pg_stat_activity` | 当前 SQL、会话状态和等待事件 |
| `pg_stat_io` | 实例的 I/O 行为 |
| `pg_stat_user_tables` | 表扫描、行更新、死元组和 vacuum 统计 |
| `pg_stat_user_indexes` | 索引使用情况 |
| `pg_stat_database` | 数据库级事务、缓存命中和临时文件统计 |

输入输出（I/O）计时记录 I/O 等待耗时。判断 CPU 瓶颈时，还需检查锁等待和执行计划。总耗时减去 I/O 耗时不能直接作为 CPU 时间。两种 I/O 计时都会增加读取系统时钟的开销，实际成本取决于运行平台。见[统计配置](https://www.postgresql.org/docs/current/runtime-config-statistics.html)和[统计视图](https://www.postgresql.org/docs/current/monitoring-stats.html)。

如果慢查询诊断需要执行计划，可以启用 `auto_explain`。开启 `log_analyze` 后，采集开销可能影响未达到慢查询阈值的语句。见 [auto_explain](https://www.postgresql.org/docs/current/auto-explain.html)。

## 命名

| 位置 | 命名格式 | 示例 |
| --- | --- | --- |
| API 字段 | `camelCase` | `observerId`、`startAt` |
| C# 属性 | `PascalCase` | `ObserverId`、`StartAt` |
| 数据库表名和列名 | `snake_case` | `entity_schemas`、`observer_id`、`start_at` |

固定表的数据库约束名使用 `snake_case`：

| 约束 | 命名规则 | 示例 |
| --- | --- | --- |
| 主键 | `pk_<表名>` | `pk_entities` |
| 内容表到统一索引的外键 | `fk_<内容表>_entities_id` | `fk_observations_entities_id` |
| 时间顺序检查 | `ck_<表名>_time_order` | `ck_observations_time_order` |

各表文档使用数据库列名，并列出对应的 C# 属性。

### 业务表命名

后端根据 EntitySchema 的 `resourceName` 生成默认业务表名：先将资源名中的每个连字符 `-` 替换为下划线 `_`，再加上 `entity_` 前缀。

| 资源名 | 默认物理表名 |
| --- | --- |
| `example-records` | `entity_example_records` |
| `local-applications` | `entity_local_applications` |
| `foreground-application-periods` | `entity_foreground_application_periods` |

SchemaId 标识模型，资源名用于 HTTP 路径，物理表名用于数据库访问。后端通过资源名找到 EntitySchema，再按上述规则生成默认表名。同一 SchemaId 的资源名固定，默认表名也保持不变。修改显示名称 `name` 不改变表名。

登记 EntitySchema 时，后端检查生成的表名是否符合数据库长度限制、是否与其他表重名。检查失败时，定义保存、资源登记和首次建表一起失败。重复提交相同定义仍使用原表，遵循[资源登记约定](../api/index.mdx#资源登记)。

此规则用于业务实体表。EntitySchema 本身仍保存在固定表 `entity_schemas` 中。对象整体保存的规则见[业务字段映射](#业务字段映射)。

### 业务列命名

后端将顶层业务字段名转换为 `snake_case`，作为默认列名。普通属性和实体引用使用同一规则。

| 业务字段 | 默认列名 |
| --- | --- |
| `name` | `name` |
| `localApplicationId` | `local_application_id` |
| `executablePath` | `executable_path` |
| `identifiers` | `identifiers` |

HTTP 将普通属性放在 `properties` 中，将引用放在 `references` 中。存储层将两类字段映射为同一张业务表的列，列名不加 `properties_` 或 `references_` 前缀。读取时，后端按 EntitySchema 还原业务字段名和所属对象。

`id` 列保存实体自身标识，`__omitted_fields` 列保存省略的顶层字段名。顶层业务字段及转换后的列名不能占用这两个系统列。此限制不影响整体保存在 JSON 列中的对象成员名。

登记 EntitySchema 时，后端检查转换后的列名。如果不同字段对应同一列名、业务字段占用系统列或数据库内置列，或列名超过数据库长度限制，后端拒绝登记，不自动改名。定义保存、资源登记和首次建表一起失败。

对象和数组各占一列。

## 列类型

| 内容 | 数据库类型 |
| --- | --- |
| 实体标识和实体引用 | `uuid` |
| 表名、名称和 IANA 时区 ID | `text` |
| 业务对象、数组和实体定义的 `fields` | `jsonb` |
| 已知时间边界 | `timestamptz` |

### 业务字段映射

EntitySchema 声明业务字段的结构。存储层根据字段类型决定数据库列。本阶段使用默认映射，不提供自定义表名或对象展平配置。

| EntitySchema 字段类型 | PostgreSQL 列类型 |
| --- | --- |
| `string` | `text` |
| `boolean` | `boolean` |
| `integer` | `bigint` |
| `number` | `numeric` |
| `reference` | `uuid` |
| `object` | `jsonb` |
| `array` | `jsonb` |

对象字段整体保存在一个 `jsonb` 列中，读取时保留原来的对象结构。

数组字段整体保存在一个 `jsonb` 列中，不自动拆出其他业务表。后端按模型声明校验对象成员和数组元素。

PostgreSQL 类型含义见[数据类型](https://www.postgresql.org/docs/current/datatype.html)。以 `jsonb` 保存的字段遵循 [jsonb 存储语义](#内容存储)。

### 字段省略与空值

每张业务表增加 `text[] NOT NULL` 系统列 `__omitted_fields`，记录本行省略的顶层业务字段名。记录使用 EntitySchema 中的原字段名，例如 `localApplicationId`。普通属性与引用字段使用同一规则；没有省略字段时，记录为空列表。

例如，`name` 允许省略，也允许为 `null` 时：

| 提交的属性 | `name` 列 | `__omitted_fields` 保存的列表 | 读取的属性 |
| --- | --- | --- | --- |
| `{}` | SQL `NULL` | `["name"]` | `{}` |
| `{"name": null}` | SQL `NULL` | `[]` | `{"name": null}` |
| `{"name": "示例"}` | `"示例"` | `[]` | `{"name": "示例"}` |

后端按以下规则保存和还原：

1. 按 EntitySchema 校验字段。缺少必填字段，或字段值违反 `nullable` 时，拒绝保存。
2. 根据本次提交重新生成省略列表，只记录模型中已定义且本次没有提供的顶层字段。每个字段名只记录一次。
3. 在同一事务中保存业务值、省略列表和统一实体索引。保存已有实体时按完整替换处理，省略字段不保留旧值。
4. 读取时，省略列表中的字段不出现在响应中。其他字段按保存的值返回，再按模型划分到 `properties` 或 `references`。

省略列表必须与业务值一致。列入省略列表的字段不能同时保存业务值；必填字段不能列入省略列表。后端负责维护这些约束，直接修改数据库时也必须遵守。

`__omitted_fields` 属于存储元数据，由后端生成。Observer 和其他提交方只提交业务字段；HTTP 请求与响应不包含这个系统列，业务模型也不能将它声明为顶层字段。

该列表只记录顶层字段。整体保存在 JSON 列中的对象自行保留内部成员是否出现；数组内对象同样处理。

## 存储结构

后端必须保留提交的实体标识。存储中的实体标识必须唯一。每个实体必须只有一份权威内容。

后端使用四张固定表，并为每个业务 SchemaId 创建一张业务表：

| 表名 | 内容 |
| --- | --- |
| [entities](./entities.mdx) | 统一实体索引，保存 `id` 和 `table_name` |
| [observations](./observations.mdx) | 观测的内容 |
| [observers](./observers.mdx) | 观测主体的内容 |
| [entity_schemas](./entity-schemas.mdx) | 实体定义的模型声明 |
| [业务表](./business-entities.mdx) | 符合对应 EntitySchema 的业务实体 |

## 统一索引

后端使用 [entities](./entities.mdx) 维护实体标识与存储位置的对应关系。读取实体时，后端先根据标识查询索引，再从索引指向的表读取内容。

## 表约束

所有表都以 `id` 为主键。固定内容表和业务表的 `id` 通过外键引用 `entities.id`。各列的 SQL `NOT NULL` 约束见各表文档。业务列的 SQL `NULL` 配合 `__omitted_fields` 区分字段省略和显式空值。

内容表到统一索引的外键使用 `ON DELETE CASCADE`。删除统一索引行时，自动删除同 ID 的内容行。

Observation 和业务实体的引用字段不建立外键。后端允许先保存引用方、再保存被引用实体。

`observations` 使用 `CHECK (start_at <= end_at)`。两个边界均已知时，开始时间必须早于或等于结束时间。任一边界未知时允许保存。

后端通过事务保证索引表名与内容表匹配，并保证每个实体只有一份权威内容。内容表通过外键保证每行内容都有对应的统一索引。

## 查询索引

固定表与业务表保留主键索引，`entity_schemas.resource_name` 另有唯一索引。出现新的查询需求时，结合 `pg_stat_statements`、慢 SQL 日志和执行计划判断是否新增索引。

## 写入一致性

后端保存一个实体时，必须在同一事务中写入统一索引和实体内容。两者必须同时成功或同时失败。

如果写入失败，后端回滚事务。已有索引和内容保持不变。

所有保存事务先取得同一把事务级 advisory 锁：EntitySchema 登记使用独占锁，其他实体保存使用共享锁，然后再锁定实体索引行。该顺序防止动态建表的外键锁与索引写入互相等待。事务提交或回滚时释放锁。

四类实体共用以下保存步骤：

1. 用 `INSERT ... ON CONFLICT DO NOTHING` 登记索引。
2. 用 `SELECT ... FOR UPDATE` 锁定该 ID 的索引行。
3. 校验模型类别；业务实体还须匹配资源绑定的 Schema。如果冲突，回滚事务；否则继续。
4. 写入或替换内容。
5. 提交事务。

同一 ID 的并发保存通过索引行锁依次执行。

## 模型类别

后端根据索引中的 `table_name` 映射模型类别：

| 存储表 | 模型类别 |
| --- | --- |
| [observations](./observations.mdx) | `observation` |
| [observers](./observers.mdx) | `observer` |
| [entity_schemas](./entity-schemas.mdx) | `entity_schema` |
| EntitySchema 对应的业务表 | `entity` |

读取时，后端使用映射得到的类别填充响应中的 `category`。

保存已有实体时，后端比较保存路径声明的类别与映射得到的类别。如果两者不一致，后端必须返回 `409 Conflict`，并保留已保存的内容。

## 内容存储

业务实体按 EntitySchema 保存到对应业务表。业务对象、数组和 `entity_schemas.fields` 使用 `jsonb`。对象键名遵循领域定义。存储不保留 JSON 的空白和对象键顺序；同一对象中的重复键只保留最后一个值。

`jsonb` 不接受超出 PostgreSQL `numeric` 范围的数值、`\u0000` 和无效的 Unicode 代理对。类型约束见 [PostgreSQL JSON 类型](https://www.postgresql.org/docs/current/datatype-json.html)。

文本也不能包含空字符。如果内容违反上述表示约束，API 返回 `400`。后端回滚事务，不保留部分写入。

观测内容的身份、记录粒度和历史保留方式见[观测内容](../core/model/observations/content.mdx)。

## 时间存储

后端将模型中的已知时间边界转换为 UTC，使用 `timestamptz` 保存。存储和读取的时间精度为 1 微秒。未知边界保存为 SQL `NULL`。

EF 实体读写使用 `Database/Converters/UtcDateTimeOffsetValueConverter.cs`。转换器在写入前转换为 UTC，读取时返回 UTC，保留 `null`。`HeartbeatDbContext.ConfigureConventions` 将转换器应用于 `DateTimeOffset` 属性及其可空形式。

后端使用参数化 SQL 保存 Observation。提交时间参数前，后端调用 `ToUniversalTime()`。读取时，EF Core 转换器返回 UTC。可空边界保持 `null`。

带偏移的时间转换后表示同一时刻。例如，`2026-10-06T09:00:00+08:00` 转换为 `2026-10-06T01:00:00+00:00`；带 `Z` 的输入已经是 UTC。

`timestamptz` 保存时刻，事实所属的 IANA 时区 ID 由 Observation 的 `time_zone` 列单独保存。

时间的程序表示与精度见 [ITimed](../core/model/contracts/timed.mdx)。传输和展示约定见 [Heartbeat API](../api/index.mdx#时间表示与职责)。

## 存储职责

统一索引的 `table_name` 指向实体唯一的权威内容。一个业务 SchemaId 对应一张业务表；模型变化使用新的 SchemaId 和资源名，不覆盖原表的模型。

存储决策见 [ADR 0004](../adr/0004-entity-storage-authority.mdx) 和 [ADR 0011](../adr/0011-entity-schema-driven-storage.mdx)。
