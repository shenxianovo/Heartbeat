本节保留第一阶段模型压力实验的结论；以下“本次改动”指该阶段。后续真实来源接入及剩余缺口见 Observers 的[来源采集](../../observers/sources/index.mdx)与[100 场景接入目录](../../observers/sources/coverage.mdx)，不要把两阶段的覆盖范围混为一谈。

## 一句话结论

当前这组小模型，足以把本次 100 个场景的已知事实表达清楚；暂时没有证据要求增加新的核心实体。但“能表示”和“已经好用”之间，仍有身份映射、历史保留、时间投影和查询能力的距离。

此次实际改动很小：拒绝 JSON 重复字段，避免解析器或数据库悄悄只留下最后一个值；业务实体读回返回其 `schemaId`，让通用客户端能找到定义；增加可重复执行的场景与回归测试。没有扩充 Observation，没有加入通用 Relation，也没有给 EntitySchema 加有效期。

## 反复出现的四道坎

1. **身份要靠证据。** 相同 URL、PID、文件路径或时间戳，并不能证明是同一件事。外部 ID 要加来源范围，并持久保存到 UUIDv7 的映射。
2. **历史不会自动留下。** PUT 是完整替换。旧 Observation 如果仍引用被改写的内容，就不能当作旧快照；需要保留历史时，保存独立内容版本。
3. **一条时间轴不能假装知道一切。** 纳秒、单调时钟、本地日期、浮动时间、来源边界语义应保留明确字段。来源不知道的绝对时间保持未知。
4. **能连起来，还不等于能查回来。** 普通实体能表达成员与多元关系；当前 API 只有按 ID 读取，没有列表、逆向引用或图遍历。仅知道父节点 ID 时，不能自动找回所有成员。

## 不把问题藏在原始 JSON 里

对象、数组和普通关系实体可以保留业务结构。原始字节仅用于确实依赖精确字节的材料，例如 Git 签名、二进制文件或密文。原始字节留得住，并不能证明语义可查询。

同样，通用类型校验不会判断置信度是否合理、图是否有环、目标是不是正确类型、来源版本是否更新。这些边界必须写在具体 Schema 与采集程序的规则里。

## 本次没有做的扩张

- 不因很多场景需要关系，就添加核心 Relation：普通业务实体已经能表达具名关系及其属性
- 不为每种采集元数据给 Observation 加字段：事实内容可以由 Schema 声明
- 不强制不可变的全部实体：当前状态与历史版本有不同用途；本次只说明何时必须留旧版本
- 不仓促加通用查询层：缺少逆向查询是真实限制，应该用具体检索任务决定最小接口与索引
