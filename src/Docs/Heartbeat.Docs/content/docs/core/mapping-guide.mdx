## 先问五个问题

1. 这条记录究竟声称什么事实？是“曾发生过事件”，还是“此时读到了状态”？
2. 来源实际给了什么？没有稳定标识、时区或结束时间，就不要补造
3. 哪个业务实体需要稳定身份？哪份内容必须保留为历史版本？
4. 时间是绝对时刻、本地日期、相对位置还是单调时钟？不要强行混用
5. 读回时需要怎样找到这份内容、它的定义和关联成员？能保存不等于能发现所有关联

## 一次事实，几种身份

以“同一封邮件被两个采集程序先后读到”为例：

- 邮件：业务规则识别的同一对象，使用稳定实体身份
- 内容版本：需要历史时，正文 A 与正文 B 分别保留
- Observation：每次独立形成的观测各有标识，可以引用相同或不同内容
- Observer：实际负责形成判断的主体；纯转发程序不改原主体
- EntitySchema：解释内容及事实时间的定义；语义或结构变化使用新标识

网络重试不是重新形成事实。同一份已保存输入重放时，沿用输入到实体标识的持久映射。丢失映射后，UUIDv7 本身不能帮你找回这段对应关系。

## 时间：只填已知的部分

Observation 使用已知事实边界。两端都相等表示时间点，递增表示左闭右开区间；`null` 只表示未知。

| 来源给的信息 | 映射方式 |
| --- | --- |
| 明确 UTC 或偏移的事件时刻 | 填入事实时间；来源没有 IANA 时区则 TimeZone 仍为空 |
| 只有“当地某天”或无时区的本地时间 | 保留声明过的本地日期/时间字段；无法推出的绝对边界保持未知 |
| 启动后的单调计数 | 保存计数、单位和启动范围；只有可靠锚点才转换绝对时刻 |
| 纳秒或特殊边界定义 | 保留原始精度及边界语义；系统时间投影只有微秒精度 |
| 暂停、取消、抑制、数据缺失 | 用明确业务状态，不挪用 null 时间表达 |

这不是新增时间模型，而是避免把不同事实硬塞进同一组边界。具体业务要说明原始字段与时间投影之间的关系。

## 引用：值只存一次，含义由业务说清

普通具名引用放在 `references`，其他业务字段放在 `properties`。字符串里的外部 ID 不会自动成为关系图边。

目前引用声明只允许顶层标量。多个附件、带属性的成员、顺序敏感的 Git 父节点，可以建普通成员/关系实体；每个实体声明自己的顶层引用及顺序、角色等属性。无需核心 Relation 类型。

必须同时承认操作成本：当前 API 不能从父节点反查全部成员，采集程序或调用方需要保留成员 ID。当前也不验证引用目标存在、目标类别或业务语义是否正确。

## 历史：不要让旧观测悄悄变成新内容

PUT 完整替换实体。它适合更新“当前状态”，但不能自动保证历史保真。

需要历史时：稳定业务对象保留身份，历史内容分别保存版本，旧 Observation 保持指向原版本。重试同一输入沿用原版本标识。把旧内容覆盖掉之后，单靠旧 Observation 的时间无法恢复它。

## 读回：先找到定义，再解释字段

业务实体读取响应的顶层 `schemaId` 指明其 EntitySchema。客户端先按该 ID 读取定义，再按字段声明解释内容。它是后端已知的读取元数据，不是业务新增的引用字段。

不要把“能读到 Schema”理解为“所有语义都有机器约束”。范围、单位、联合类型互斥、来源版本与图结构等规则仍需要明确领域约定和采集校验。
