按以下顺序设计一个新来源的接入，将已确认结论写入 [Observer 与实体文档](./template/index.mdx)。未确认项列入“待定”，不要用示例值代替业务决定。提交与恢复遵循[提交机制](./submission/index.mdx)，HTTP 契约见 [API](../api/index.mdx)。

## 1. 事实

先写明一条记录声称的事实。区分一次事件、某时刻读到的状态与一段连续事实，例如消息编辑、当前文件内容与应用处于前台。

确定何时延续同一条观测，何时形成独立记录。用业务例子检查粒度，不把每次读取都当成新观测。共用规则见 [HISTORY-1](../core/rules/history.mdx#history-1)。

将结论写入 Observer 的职责说明和实体页的“记录粒度”。

## 2. Observer

确定谁依据证据形成观测并对判断负责。内部模块只提供证据时，使用所属主体；模块独立形成观测时，使用对应主体。只传输已有观测时，保留原 ObserverId。

说明实例身份如何保存、重启后如何沿用，以及什么情况属于独立实例。把结论写入 Observer 的“实例身份”，边界依据见 [Observer](../core/model/observer.mdx)。

## 3. 实体

列出需要独立身份的业务对象、内容版本与关系实体。对每个实体说明它是否承担观测内容角色，以及与其他实体的引用关系。

例如，同一封邮件被两个主体读到时，邮件可以保持对象身份，两份 Observation 分别引用对应内容。需要保留编辑历史时，为正文 A 和正文 B 保存独立内容版本，见 [HISTORY-5](../core/rules/history.mdx#history-5)。

关系需要自己的身份、时间或属性时，将关系定义为普通业务实体。不要在普通字符串中放入标识后，就将其当作实体引用。

## 4. Schema

为每种业务实体声明字段与引用。每个字段明确填写 `type`、`required` 与 `nullable`；对象声明成员，数组声明元素。将实体含义、记录粒度、身份、时间、Schema 与示例集中写在同一实体页。

实体引用只声明为顶层 `reference` 字段。外部标识保留为普通属性，只有实体引用参与关系图。若需要多个关联对象，按业务含义定义相应引用或关系实体。

为定义选择稳定的 SchemaId 和唯一资源名。结构、约束或业务含义变化时，使用新 SchemaId。完整声明规则见 [EntitySchema · 字段约束](../core/model/schema.mdx#constraints)。

## 5. 身份

说明来源标识在哪个账号、设备、仓库或日历范围内有效。明确来源标识到 EntityId 的映射如何持久保存，不将范围不同的同名标识合并。

来源没有稳定标识时，写明可用证据与识别方式。证据不足的字段保持未知，不补造来源身份。

区分重试、补全和独立观测。重试或重放已保存输入时沿用原身份；同一连续事实的补全也可以沿用身份；新的独立观测使用新身份。内容相同本身不证明属于同一次发生或观测，见 [IDENTITY-3](../core/rules/identity.mdx#identity-3)。

## 6. 时间

说明 Observation 的事实时间取自哪些来源字段，按 [Observation · 事实时间](../core/model/observation.mdx#fact-time) 表达时间点、时段与未知边界。不要用观测、接收或标识生成时间填补未知的历史事件时间。

只有状态读取时刻可用时，先确认业务表达的是“此刻读到的状态”，再将读取时刻作为事实时间。来源只有本地日期、无时区的本地时间或相对计数时，先在内容中保留原值；只有取得可靠换算依据后才填写绝对边界。

需要保存更高精度或特殊边界含义时，在内容中保留原值，并说明公共微秒时间的转换方式。用业务字段表达暂停、取消或抑制，不能用时间边界代替这些状态。

写明进行中的证据与记录结束条件，不根据 `endAt` 是否为空判断是否结束，见 [TIME-4](../core/rules/time.mdx#time-4)。不要用形成观测、接收或保存的时刻填补事实时间，见 [TIME-1](../core/rules/time.mdx#time-1)。

## 7. 历史

确定业务需要保留原始材料、当前状态还是历史版本。需要原始材料时，在 Schema 中声明保存方式；需要旧观测保持原貌时，保留它所引用的内容。

当前状态可以更新同一实体；历史内容可以使用独立版本。例如，本机应用可以保持身份，而不同时段的名称由各自内容保留，见 [HISTORY-5](../core/rules/history.mdx#history-5)。状态变化形成新的 Observation，不改写已保存的 Observation，见 [HISTORY-3](../core/rules/history.mdx#history-3)。

检查完整替换的结果：省略字段不保留旧值，见 [API · 保存](../api/index.mdx#保存)。

## 8. 提交

接入时，将稳定的 Observer 身份与所需 Schema 交给所在运行环境的 SDK，不等待第一条观测。按记录类型选择及时提交或结束后提交，并说明业务何时通知更新和结束。

在 Observer 页写明所用 SDK 与策略，链接[共同提交约定](./submission/index.mdx)。SDK 负责本地可靠保存、发送、确认与恢复；事实判断、记录身份与历史保留仍由业务负责。

## 9. 读回

用实体页的示例检查保存与读取的对应关系，确认以下内容：

- 业务实体响应的顶层 `schemaId` 指向定义。Observation 只引用 Observer 和内容，内容的类型由内容自己的 `schemaId` 给出。
- Observation 响应带有后端赋值的 `recordedAt`，提交时不要携带它。
- 引用与属性分开放置，省略字段与显式 `null` 保持区别。
- 读取引用方不要求引用目标已经入库。

当前 API 只按 ID 读取，不提供列表与反向引用查询。按当前接口实现接入时，保存所需成员 ID。读取结构见 [API · 读取](../api/index.mdx#读取)。
