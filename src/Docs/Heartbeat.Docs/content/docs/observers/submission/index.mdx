程序实例通过所在运行环境的 SDK 把数据交给后端。Observer 的业务代码负责形成事实、维护身份和选择提交策略；SDK 负责本地保存、发送、确认和恢复。这样分工的理由见 [ADR · 提交与 SDK](../../adr/submission.mdx#decision)。

## 分工 [#division]

| Observer 的业务代码 | SDK |
| --- | --- |
| 定义 EntitySchema，识别对象，形成观测内容和 Observation | 接入时提交程序实例和所需的 EntitySchema |
| 决定粒度、身份和历史保留 | 本地保存交来的数据和待发送的更新 |
| 选择提交策略，明确通知更新和结束 | 安排发送、处理确认、断网重试和恢复 |

应用是否切换、事实是否仍在持续、两份数据能否合并，都由业务代码判断。后端按 EntitySchema 校验并保存。

## 接入 [#setup]

### 连接后端 [#connection]

业务代码提供后端地址和要提交的实体。SDK 按 [API](../../api/index.mdx) 组织请求、解析响应和错误；网络库和请求方式由各平台的 SDK 决定。

### 登记 [#registration]

接入时，业务代码把程序实例的身份和所需的 EntitySchema 交给 SDK，SDK 立即提交，第一份观测形成之前就完成登记。程序重启后，程序实例的身份和 SchemaId 都保持不变。

登记使用普通的实体提交：后端保存程序实例和 EntitySchema，并按 EntitySchema 登记业务资源和存储表。程序实例和 EntitySchema 之间的关联，由每份观测的引用表达。

网络不可用时，SDK 保留登记内容，恢复后继续提交。业务实体发送前，它的 EntitySchema 必须已经登记。

## 提交策略 [#strategies]

同一个 Observer 可以对不同的业务类型选择不同的策略。

| 策略 | 首次形成 | 后续补全 | 业务代码通知结束后 |
| --- | --- | --- | --- |
| 及时提交 | 本地保存，并安排上传 | 沿用身份，安排更新 | 提交最终结果 |
| 结束后提交 | 本地保存 | 在本地补全 | 安排上传完整结果 |

两种策略都在数据形成时就本地保存。及时提交可以把多次采样合成一次发送：同一份数据尚未发送的连续补全可以合并，不同的数据分别保留。发送的时机不影响事实时间。

### 更新与结束 [#updates]

业务代码把新形成或补全的数据交给 SDK，并明确通知 SDK 一段事实何时结束。`endAt` 有值不能当作结束通知，因为它也可能只是最近一次确认的时刻。

例如 10:00 确认 Codex 在前台，10:05 再次确认，业务代码把同一份 Observation 补全到 10:05。10:08 切换应用时，业务代码才通知这一段结束，并为新应用形成新的观测。连续补全见 [TIME-4](../../core/rules/time.mdx#time-4)。

补全可以替换后端同一 ID 的较早内容，后端仍按契约校验。发送失败时，实体的身份、引用和事实时间保持原样。

## 可靠交付 [#delivery]

### 本地保存与发送 [#outbox]

SDK 先本地保存待发送的内容，再安排发送。发送失败或响应不确定时，内容留在本地，等网络恢复或程序重启后继续处理。

后端保存成功、返回 `201 Created` 或 `204 No Content` 后，SDK 确认对应的待发送项，不需要再读回。一次确认只作用于它对应的那次更新，之后形成的补全仍然保留。保存成功也不代表这段事实已经结束，SDK 继续接收更新和结束通知。

SDK 启动时恢复待发送项；退出前只需把已接收的内容保存到本地。

### 幂等重试 [#idempotency]

对同一入口、同一 ID 重复提交相同的内容，结果和提交一次相同，见 [API](../../api/index.mdx)。

- 传输重试保留原来的 ID、引用、属性和事实时间。
- 后端已保存但响应丢失时，SDK 重发同一个请求，后端返回成功，实体仍然只有一个。
- 补全是同一实体的新内容。SDK 按这个实体的更新顺序发送和重试，已经成功的旧更新不再重发。

例如 10:00 首次保存的响应丢失，重试时后端返回 `204`，SDK 据此确认。10:05 的补全沿用同一个 ID，提交新的结束边界。

### 发送状态 [#status]

SDK 向业务代码报告待发送的数量、已确认的数据和失败原因，业务代码据此区分仍在本地、已保存和失败的数据。

### 断网示例 [#offline-example]

前台应用采用及时提交时：

| 时刻 | 发生的事 | SDK 的处理 |
| --- | --- | --- |
| 接入 | 程序实例和所需的 EntitySchema 已确定 | 提交程序实例和 EntitySchema |
| 10:00 | Codex 开始处于前台 | 保存观测内容和 Observation，安排上传 |
| 10:02 | 网络中断 | 保留未确认的更新，采集继续 |
| 10:08 | 切换到浏览器 | 保存 Codex 的最终时段和浏览器的新时段 |
| 10:10 | 网络恢复 | 补交 Codex 的完整时段，以及浏览器截至最近一次确认的时段 |

Codex 时段的多次延长可以合并成一次提交；网络恢复时，Codex 和浏览器的时段都要提交。如果采用结束后提交，Codex 的时段在结束后安排上传，浏览器的时段继续在本地补全，等业务代码通知结束。
