Observer 通过所在运行环境的 SDK 登记 Observer 与 Schema、提交实体和观测。业务负责形成事实、维护身份并选择提交策略；SDK 负责本地可靠保存、发送、确认与恢复。职责依据见 [ADR · Observer 的责任与提交](../../adr/observer-responsibility.mdx#decision)。

## 职责分工

| 业务负责 | 平台 SDK 负责 |
| --- | --- |
| 定义 Schema，识别对象，形成内容与观测 | 接入时提交 Observer 与所需 Schema |
| 决定记录粒度、身份与历史保留 | 持久保存交来的记录与待发送更新 |
| 选择提交策略，明确通知更新和结束 | 安排发送、处理确认、断网重试与恢复 |

后端按 Schema 校验并保存。SDK 不判断应用是否切换、事实是否仍在持续，也不替业务决定不同记录能否合并。

## 接入准备

### 后端连接与协议封装

业务提供后端地址与实体。SDK 按[实体协议](../../api/index.mdx)组织请求、解析成功响应和错误。网络库与请求执行方式由平台实现决定。

### 接入登记

Observer 接入时，将稳定的主体身份与所需 Schema 交给 SDK，不等待第一条观测形成或结束。重启沿用原 Observer 身份，SchemaId 也不随程序启动重新生成。

SDK 使用既有实体入口提交主体与定义。后端保存主体，按 Schema 登记业务资源和存储表。登记不要求同时存在业务内容或 Observation，也不增加能力清单或主体到 Schema 的绑定字段。每份观测通过自己的引用关联主体和定义。

网络不可用时，SDK 保留登记内容，恢复后继续提交。业务实体发送前，相应定义须已登记。

## 记录提交

### 提交策略

业务按记录类型选择策略，同一个 Observer 可以采用多种策略。

| 策略 | 首次形成 | 后续补全 | 业务通知结束 |
| --- | --- | --- | --- |
| 及时提交 | 本地保存并安排上传 | 沿用身份，安排更新 | 提交最终结果 |
| 结束后提交 | 本地保存 | 本地补全 | 安排上传完整结果 |

两种策略都先持久保存，结束后提交也不能等记录结束才首次落盘。及时提交不要求每次采样都发送请求。同一条记录尚未发送的连续补全可以合并，不同记录分别保留。发送安排不改变事实时间。

### 更新与结束

业务将新记录或补全交给 SDK，并明确通知记录何时结束。`endAt` 非空不能作为结束通知，因为它也可以表示最近一次确认到的边界。

例如，10:00 确认 Codex 在前台，10:05 确认它持续处于前台，业务可以将同一条 Observation 补全到 10:05。10:08 切换应用时，业务才通知旧记录结束，并形成新应用的记录。连续补全见 [TIME-4](../../core/rules/time.mdx#time-4)。

业务补全可以替换远端同一 ID 的较早内容，后端仍按契约校验。发送失败不改变实体身份、引用或事实时间。

## 可靠交付

### 本地保存与发送

SDK 先持久保存待发送内容，再安排发送。失败或响应不确定时保留内容，网络恢复或程序重启后继续处理。

后端完成保存并返回 `201 Created` 或 `204 No Content` 后，SDK 确认对应待发送项，不要求额外读回。较早更新的成功确认不得删除后来形成的新补全。保存成功也不表示业务记录已经结束，SDK 继续接收更新与结束通知。

SDK 启动时恢复待发送项；退出前将已接收内容保存到本地，不要求等全部上传后才退出。

### 幂等重试

同一入口、同一 ID 与相同内容的重复提交保持实体结果不变，见 [API · 保存](../../api/index.mdx#保存)。

- 传输重试保留原 ID、引用、属性与事实时间。
- 后端保存成功但响应丢失时，SDK 重发同一请求，不产生新实体。
- 业务补全是同一实体的新内容。SDK 按该实体的更新顺序发送和重试，成功处理的旧更新不再重放。

例如，10:00 的首次保存响应丢失，重试成功时返回 `204`，SDK 即可确认。10:05 的补全沿用 ID，提交新的结束边界，更新已有观测。

### 发送状态反馈

SDK 向调用方提供待发送数量、已成功确认的记录与失败原因。调用方据此区分本地等待、已保存与失败的记录。

### 断网示例

前台应用采用及时提交时，处理过程如下：

| 时刻 | 业务事实 | SDK 处理 |
| --- | --- | --- |
| 接入 | 主体与所需 Schema 已确定 | 提交主体与定义 |
| 10:00 | Codex 开始处于前台 | 保存内容与 Observation，安排上传 |
| 10:02 | 网络中断 | 保留未确认更新，采集继续 |
| 10:08 | 切换到浏览器 | 保存 Codex 的最终时段与浏览器的新记录 |
| 10:10 | 网络恢复 | 补交 Codex 的完整时段，以及浏览器截至最近确认的记录 |

同一 Codex 时段的多次延长可以合并，但不能只保留恢复网络时的浏览器记录。若采用结束后提交，Codex 结束后安排上传；浏览器记录继续本地保存，等待业务通知结束。
