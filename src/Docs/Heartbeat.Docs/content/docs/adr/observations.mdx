## 背景 [#context]

一份观测可能在事实进行中形成，随后不断补全。传输可能重试，来源也可能缺少时间。如果这些情况没有统一规则，同一个事实会被保存成重复的记录，或者旧值被覆盖。

## 决定 [#decision]

- 业务决定实体身份和记录粒度。
- 事实时间未知时保持未知。
- 后端在首次保存 Observation 时赋值 `recordedAt`，之后不再改变。
- 已保存的 Observation 只能补全，补全只增加证据。
- 业务决定历史的保留范围，后端不保留历史。

## 理由 [#rationale]

只有业务掌握来源的含义，例如两次读数之间应用是否一直在前台。后端如果按内容合并或拆分记录，会把巧合当成同一个事实。

`recordedAt` 要回答“后端什么时候第一次知道这件事”。如果补全会更新 `recordedAt`，这个问题就无法回答。

只允许补全，读取方读到的就始终是 Observer 当时形成的判断，不会被事后改写成另一个事实。

放弃的方案：

- **后端按内容去重或合并。** 内容相同不说明是同一次观测。
- **用其他时刻填补未知的事实时间。** 填补后，读取方无法区分“确实在这一刻”和“不知道是什么时候”。
- **在 Core 中定义纠正和撤回。** 纠正需要一种所有读取方都认识的结构，目前没有读取方需要它。

## 代价 [#costs]

- 需要沿用的 EntityId 必须持久保存，例如 Observer 实例和进行中的时段。
- 错误的观测目前无法在 Core 层面纠正或撤回，只能删除。
- 业务需要历史时，要自己设计保存历史的实体。
