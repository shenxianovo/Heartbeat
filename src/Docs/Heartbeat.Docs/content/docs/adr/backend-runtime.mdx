## 背景 [#context]

后端需要让模型规则独立于 HTTP 和数据库。本地开发需要同时运行 API、文档站、Web 控制台、PostgreSQL 和反向代理，并支持断点调试和热更新。

## 决定 [#decision]

### 项目分工 [#components]

| 项目 | 职责 |
| --- | --- |
| `Heartbeat.Core` | 实体、契约和模型规则 |
| `Heartbeat.Application` | 实体操作和应用规则 |
| `Heartbeat.Infrastructure` | PostgreSQL 映射、事务和迁移 |
| `Heartbeat.Api` | HTTP 请求校验、响应映射和启动组装 |

- 四个项目组成一个后端进程，不增加只转发调用的层。
- Core 和 Application 不依赖 HTTP 或数据库。
- 迁移由独立的步骤执行，API 启动时不应用迁移。

### 本地环境 [#local-environment]

- Aspire AppHost 是本地资源、依赖关系和启动顺序的唯一来源，只用于本地开发。
- 需要调试的应用进程在本机运行，PostgreSQL 和 NGINX 在容器中运行。

### HTTP 入口 [#http-entry]

- NGINX 为 API、文档站和 Web 控制台提供只绑定本机的同源入口。

### 遥测 [#telemetry]

- API 默认只输出控制台日志，只有配置了 OTLP 地址时才导出遥测。遥测不采集请求体和数据库参数值。

## 理由 [#rationale]

Core 和 Application 不依赖 HTTP 和数据库，模型规则就可以不启动数据库而测试。四个项目放在一个进程中，是因为目前没有需要独立部署的部分。

迁移不在 API 启动时执行，多个 API 实例启动或 API 重启时不会重复建表。

本机运行应用进程可以直接调试和热更新，容器只用于不需要调试的依赖。通过 NGINX 同源访问 API，浏览器端不需要配置跨域。遥测默认关闭，API 可以脱离 Aspire 独立运行。

放弃的方案：

- **按层拆成多个服务。** 目前没有需要独立扩展或部署的部分，拆分只增加网络调用。
- **全部在容器中运行。** 断点调试和热更新会变得麻烦。

## 代价 [#costs]

- 本地验证不证明部署环境的行为。
- Aspire 不用于部署，部署需要另外的配置。
