ADR（Architecture Decision Record）记录一项架构决定、作出决定的原因和带来的影响。规则本身写在 Core、API、Storage 和 Observers 中，ADR 回答“为什么这样规定”。

## 何时写 ADR [#when]

以下三类决定写成 ADR：

- 责任归哪个组件。
- 协议的语义。
- 某类数据的权威位置。

较小的决定写入对应的类型页、规则页或契约。单个 Observer 的实现决定，例如识别规则、分段阈值和本地存储，写在该 Observer 的文档中。模块的运行和操作说明写在模块 README 中。

## 结构 [#structure]

| 部分 | 内容 |
| --- | --- |
| 背景 | 需要作出决定的问题 |
| 决定 | 确定的做法，每条一句，只写决定本身 |
| 理由 | 为什么这样做，放弃了哪些方案 |
| 代价 | 接受了哪些成本或限制 |
| 规则位置 | 承载具体规则的文档 |

ADR 不复述规则。条件、例外和细节写在 Core、API、Storage 或 Observers 中，ADR 链接过去。

流程类的决定在 Core 中没有对应的页面。这类 ADR 在“决定”之后增加“规则”一节，直接承载规则，例如 [文档的权威与传播](./documentation-authority.mdx)。

## 命名 [#naming]

每篇 ADR 用主题的英文 slug 命名，例如 `entity-model.mdx`。引用时写 ADR 的标题并链接文件，例如 [ADR · 实体模型](./entity-model.mdx)。代码注释中写 slug，例如 `ADR entity-model`。

ADR 没有编号。阅读顺序由侧边栏决定：按侧边栏依次读，每篇 ADR 只依赖排在它前面的 ADR。

- 重写期间，ADR 直接改成当前的决定，不保留被取代的版本。合并、拆分或改名时，同时更新所有引用。
- 重写完成后，slug 固定。决定被取代时，新写一篇 ADR，并在旧 ADR 的开头链接新 ADR。
