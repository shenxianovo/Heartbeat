## 背景 [#context]

Observer 可能离线运行，不能等后端分配 ID。如果每新增一种业务实体就新增一套接口，客户端和后端都要跟着修改。

## 决定 [#decision]

- 创建方生成 EntityId，后端不重新分配。
- 保存路径声明类别：Core 类型各有固定入口，业务实体按登记 EntitySchema 时绑定的 `resourceName` 保存。请求体不包含类别。
- 请求体分为 `references` 和 `properties`，引用字段放在前者，其他字段放在后者。
- 保存是幂等的完整替换。
- 所有类别都按 ID 用同一个入口读取。业务实体另外返回所属的 SchemaId，由后端提供。

## 理由 [#rationale]

创建方生成 ID，离线运行的 Observer 可以先在本地建立引用，再按任意顺序上传。保存是完整替换并且幂等，响应丢失时重发同一请求就是安全的。

业务实体共用一个入口，新增一种业务实体只需要登记 EntitySchema，不需要修改后端代码。`references` 和 `properties` 分开放，通用读取方不需要了解业务字段就能遍历引用。

放弃的方案：

- **后端分配 ID。** 离线时无法建立引用，重试也可能产生重复的实体。
- **每种业务实体一套接口。** 每新增一种类型都要修改后端和客户端。
- **部分更新。** 重放部分更新的结果取决于当前内容，不再幂等。

## 代价 [#costs]

- 没有部分更新。修改一个字段也要提交完整内容，省略的字段不保留旧值。
- 客户端必须自己生成 UUIDv7。
- 业务实体保存前，EntitySchema 必须已经登记。
