---
title: "ADR 0013：业务实体读回时携带定义身份"
---

## 背景

业务实体可以独立存在，不要求总能从 Observation 到达它。附件、Git 树、问卷答案、成员关系等场景中，调用方可能只拿到一个实体 ID。

旧读取响应只有 `category: entity`、具名引用和业务属性，不能告诉通用客户端这些字段遵循哪份定义。数据库在读取时已经根据实体所在表查到了 EntitySchema；缺失发生在读取协议边界，不需要新增核心概念。

## 决定

- `GET /entities/{id}` 对业务实体返回顶层 `schemaId`，指向实际用于读取该实体的 EntitySchema
- `observer`、`observation`、`entity_schema` 固定类别不返回该顶层字段，它们由固定协议解释
- `schemaId` 是读取元数据，由存储层已有的权威映射提供，经 Application 交给 API；调用方不能在业务保存请求里自行覆盖它
- 业务 `references` 和 `GetReferences()` 不因此增加引用；Observation 自己的 `references.schemaId` 继续保持原有含义

同一 ID 的结构或语义定义仍不可变；本次不改变 Schema 生命周期、资源登记或历史保留规则。

## 结果与限制

通用客户端可以先读实体、再按 `schemaId` 读取定义，区分结构相似但含义不同的业务实体。100 个场景的读回测试逐项检查这个链路。

这不提供列表、逆向引用、图遍历、目标类型校验或多实体原子提交。若只知道父节点 ID，仍然不能自动发现所有成员关系。

## 考虑过的替代方式

- 让所有业务实体额外声明一个 Schema 引用：会重复后端权威映射，并混淆业务图与传输元数据，因此不采用
- 要求所有业务实体必须绑定 Observation：会破坏业务实体独立存在的既有约定，因此不采用
- 只返回资源名：资源名用于保存入口；返回稳定的定义身份后，客户端能从定义取得资源名和字段，因此不重复两个字段

协议以 [OpenAPI](/api/getEntity) 为准。
