# Physical and calendar file imports

These adapters read explicit local synthetic or user-supplied files. They do not connect to private calendars, request grants, operate GPS devices, or claim provider acquisition. Both accept `SourceReadContext.Input`, `Scope`, and `CaptureKey`; neither substitutes import time for a source fact time.

## `icalendar-ics`

Bounded [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545) iCalendar 2.0 `VEVENT` projection. UTF-8, content-line unfolding, quoted parameter delimiters, TEXT escaping, UID, RECURRENCE-ID (including RANGE), SEQUENCE, DTSTART/DTEND, DTSTAMP, summary/description/location/status, RRULE, EXDATE and RDATE are supported. UID and recurrence identity are scoped to the calendar feed supplied in `Scope`. SEQUENCE affects evidence, not entity identity. Replaying the same capture is idempotent; a new capture produces new evidence. Duplicate UID/recurrence/sequence within a capture is rejected rather than selected implicitly.

DATE, floating DATE-TIME, TZID DATE-TIME and UTC DATE-TIME are distinct typed source values. Only explicit UTC DTSTART/DTEND become absolute observation boundaries. All-day dates and floating times have null absolute boundaries; TZID values are retained without consulting the machine time zone database or guessing a custom VTIMEZONE. DTEND remains the source's exclusive bound. Missing DTEND is unknown; no default end or DURATION arithmetic is invented. DTSTAMP is source metadata, not event time. Cancelled recurrence instances remain status-bearing event evidence.

This is not a full iCalendar validator or recurrence engine. RRULE/EXDATE/RDATE content lines and DURATION are retained verbatim, not expanded, evaluated or fully grammar-validated. Other event properties, nested alarms, VTIMEZONE definitions, and other component types are not projected. Leap-second calendar timestamps, custom timezone conversion, invitation scheduling, recurrence occurrence generation, VTODO, attendees, attachments and calendar synchronization are unsupported. Parameter and selected singleton-property ambiguity, malformed dates, incompatible start/end types, conflicting DURATION/DTEND and duplicate event evidence are rejected. Source records do not imply that every item in an exported calendar was imported.

## `gpx-xml`

Bounded [GPX 1.1](https://www.topografix.com/GPX/1/1/) XML waypoint/track projection. Track and segment entities are emitted with real membership references; points preserve document order, coordinates, optional elevation and source time, name, fix type, satellite count and HDOP/VDOP/PDOP. DOP values are dilution measurements, not meter accuracy estimates. Repeated identical points are distinct because their ordinal within a captured track segment is part of identity. Track, segment and waypoint identities include scope and capture key: GPX does not provide a persistent fix ID, and importing another capture does not establish cross-file track or waypoint identity.

Source times with offsets or Z become instants at .NET DateTimeOffset precision, including backward clock movement; sub-tick fractions are explicitly truncated rather than rounded across a second boundary, and the original time string is retained without precision loss. The common persistence runtime subsequently truncates to microseconds. Absent times and XSD dateTime values without an offset remain null absolute boundaries. GPX has no native IANA timezone field; none is inferred. No boot-relative clock, GPS uncertainty radius, speed, inferred track interval, route import, device acquisition, extension interpretation or cross-capture deduplication is claimed. Unsupported routes are explicitly rejected; metadata, links and extensions are ignored. Selected singleton fields are checked for duplicates. XML DTDs/external entities are prohibited, external resolution is disabled, nesting is limited to 32, input is limited to 8 MiB and output to 10,000 records. Both adapters check cancellation and reject oversized decoded selected fields.

## Evidence

`PhysicalCalendarSourceTests` uses native `.ics` and `.gpx` fixtures under `NativeFixtures/PhysicalCalendar`. It checks date/floating/UTC distinctions, recurrence exceptions and cancellation, stable replay and scoped identities, repeated points, track membership, backward timestamps, model schema validation, malformed input, XML entity rejection, size limits and cancellation. C11/C12/C14 are alternate-format semantic coverage, not Google Calendar API coverage. C13 is native iCalendar coverage. GPX partially exercises C02/C03; it cannot establish the Android timezone/boot-clock/uncertainty claims of the original examples. The tests never imply that all physical fixtures have native collectors.
